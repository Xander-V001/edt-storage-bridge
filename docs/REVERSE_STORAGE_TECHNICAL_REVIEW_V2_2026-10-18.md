# Техническая экспертиза EDT → классическое хранилище 1С

**Дата:** 2026-10-18. **Версия:** 2, после сверки первичных источников и кода стороннего решения.  
**Режим:** только исследование; **НИ ОДНА операция в рабочем хранилище/ИБ не выполнялась**.  
**Цель:** быстрый и полный перенос изменений из Git/EDT в классическое хранилище без повреждения чужих объектов.  
**Приоритет:** этот документ заменяет прежние гипотезы из `EDT_TO_CLASSIC_STORAGE_PUSH_ARCHITECTURE.md`, `OUTGOING_IMPLEMENTATION_STATUS.md` и экспериментальные `Outgoing*` как архитектурное решение.

## 1. Короткий ответ на главный вопрос

**Да, область передачи можно определять по Git-коммиту или разнице веток.** Но содержимое
Git-файлов в формате EDT нельзя механически передать как платформенные XML/BSL-файлы:
нужна штатная операция экспорта EObject из модели EDT, после чего — корректный
список файлов для пакетной частичной загрузки 1С и отдельный список объектов
классического захвата.

**Более важный момент:** после слияния задачи и получения чужих изменений в
`master` одно сравнение `git diff <старая ревизия> master` нельзя использовать
как список своей отправки — в нём смешаны оба происхождения изменений.
Профессионально этот вопрос решают разделением **источника состояния
хранилища** и **состояния разработки**, либо прослеживанием конкретной
задачи в Git. История Git должна оставаться доказуемой.

## 2. Проверенные средства платформы

### 2.1. Штатная загрузка конфигурации ИЗ ФАЙЛОВ — подтверждена документацией

Руководство разработчика 1С:Предприятие 8.3.27, глава 2.17.5.3:

- Полная загрузка не предназначена для ИБ, подключённой к хранилищу,
  и на больших конфигурациях выполняется долго.
- **Частичная загрузка** штатно предусмотрена через пакетный
  `/LoadConfigFromFiles` с указанием отдельных файлов.
- Загружать можно **не только целый объект**, но и его **подчинённые
  ресурсы**: модуль, форму, справку.
- Пример в §2.17.5.3.6: импорт отдельного файла
  `Catalogs/Counterparties/Ext/ObjectModule.bsl`.
- **Загрузка XML с описанием объекта метаданных — иная операция.**
  Она требует всех подчинённых объектов; при отсутствии файлов некоторых
  элементов возможны ошибка или значения по умолчанию, т. е. риск потери
  свойств/форм.
- Чтобы загрузить в связанную с хранилищем ИБ, затрагиваемые объекты
  должны быть **захвачены** в хранилище.
- Отсутствие ошибок в Designer не равнозначно доказательству, что
  загрузились *только* указанные изменения; особенно при сложной
  конфигурации/поддержке.

Проверенный первичный источник:
https://1c-dn.com/library/tutorials/1c_enterprise_developer_guide_8_3_27/
(§2.17.5.2 и §§2.17.5.3.1–2.17.5.3.6).

Команды захвата и помещения:
`/ConfigurationRepositoryLock -Objects <xml>`,
`/ConfigurationRepositoryCommit -Objects <xml> -comment "..." `.
**Без `-Objects` команда выполняется над ВСЕЙ конфигурацией**.
Параметры `-force` запрещены без отдельного анализа возможных потерь.
Файл `-Objects` описывает объекты *хранилища*, не пути файлов загрузки.
Источник:
https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.27_Administrator_Guide/Appendix_7._Startup_command-line_options_of_1C_Enterprise/7.4._Running_Designer_in_batch_mode/7.4.15._Configuration_repository_operations/

### 2.2. Формат объекта: родительский .mdo может содержать больше, чем ожидается

В иерархическом платформенном XML описание документа содержит реквизиты,
их типы, табличные части и отсылки к формам. Реальные формы/модули и
внешние ресурсы располагаются в собственных каталогах/файлах.

Пример:
- **В коммите только ManagerModule.bsl:** обоснован кандидат на адресную
  передачу платформенного `Ext/ManagerModule.bsl`, **не** перезаписывая
  XML с реквизитами документа.
- **В коммите .mdo со свойством реквизита:** нельзя переносить как
  «просто XML с одним изменением». Нужно корректное описание объекта
  вместе с требуемыми подчинёнными ресурсами.
- **В коммите .mdo со свойством формы:** единый файл EDT может описывать
  свойства разных объектов захвата 1С. Нужна квалификация области
  захвата, а не догадка по расширению файла.

Сам факт наличия типа `СправочникСсылка.Сотрудники` в реквизите не означает,
что всегда требуется физически экспортировать весь справочник. Но
существование и тождество ссылочного типа в целевой конфигурации нельзя
считать доказанным по имени.

## 3. Проверенные механизмы EDT

### 3.1. Штатный экспорт, НЕ файловая подмена

Публичный EDT API:
- `IExportOperationFactory.createExportOperation(Path, Version,
  IExportStrategy, EObject...)` формирует штатную операцию экспорта
  выбранных **объектов BM/EMF** в платформенный файловый формат.
- `IExportOperation.run(IProgressMonitor)` запускает её.
- `IExportStrategy` позволяет задать экспорт подчинённых объектов,
  внешних свойств, неподдерживаемых/unknown артефактов.
- Стратегия `DEFAULT` документирована как экспорт подчинённых,
  внешних и unknown-ресурсов.
- `IQualifiedNameFilePathConverter.getFqn(...)` — штатное
  преобразование пути EDT в квалифицированное имя в модели.
- `IBmModelManager` и `IBmPlatformTransaction` позволяют читать
  реальные `EObject` внутри транзакции BM.

Источники:
https://edt.1c.ru/dev/edt/2024.2/apidocs/com/_1c/g5/v8/dt/export/IExportOperationFactory.html
https://edt.1c.ru/dev/edt/2024.2/apidocs/com/_1c/g5/v8/dt/export/IExportOperation.html
https://edt.1c.ru/dev/edt/2024.2/apidocs/com/_1c/g5/v8/dt/export/IExportStrategy.html
https://edt.1c.ru/dev/edt/2025.2/apidocs/com/_1c/g5/v8/dt/core/filesystem/IQualifiedNameFilePathConverter.html

### 3.2. Для вызовов Конфигуратора в EDT есть готовый builder

`RuntimeExecutionCommandBuilder` имеет документированные функции
`importXmlToInfobase(Path)`, `fileList(Path)`, `partial()`,
`withFormat(...)`, `updateConfigDumpInfo()`, `forInfobase(...)`,
`forExtension(...)`. Это потенциальная альтернатива самостоятельной
сборке строк командной строки, **при условии API-совместимости**.

Также есть `IInfobaseSynchronizationStateManager` и
`startUpdateInfobaseFlow(...)`, `startUpdateProjectFlow(...)` —
внутренние потоки синхронизации EDT и информационной базы.
Это **не подтверждённый публичный API помещения в классическое
хранилище**; смысл, допустимость и влияние этих flow требуют
отдельной проверки.

Источники:
https://edt.1c.ru/dev/edt/2025.2/apidocs/com/_1c/g5/v8/dt/platform/services/core/runtimes/execution/impl/RuntimeExecutionCommandBuilder.html
https://edt.1c.ru/dev/edt/2025.2/apidocs/com/_1c/g5/v8/dt/platform/services/core/infobases/sync/v2/IInfobaseSynchronizationStateManager.html

**ОГРАНИЧЕНИЕ:** открытые JavaDoc относятся к EDT 2024.2/2025.2,
а рабочая цель — **EDT 2026.2**. Без проверки target bundles
не утверждать, что сигнатуры и OSGi-инъекция совпадают.

## 4. Действительно существующая реализация PluginEDT: что написано в коде

Источник: https://github.com/ZigRinat85/PluginEDT
и описание: https://infostart.ru/1c/articles/2442956/

Изучены `ExportHandler.java`, `Designer.java`,
`V8FileBuilder.java` и `META-INF/MANIFEST.MF` версии 0.4.0.
Открытая реализация — пример механизма, не лицензия на копирование.

Фактическая последовательность из `ExportHandler.pushBranchDiff`:

1. JGit сравнивает **деревья двух веток**: `ВХ` (ветка
   хранилища) и `ВР` (ветка разработки). Это **не**
   `git diff HEAD~1`, не `git diff B master` после общей
   синхронизации и не поиск всего рабочего каталога.
   Незакоммиченные изменения в эту разницу не попадают.
2. Из DiffEntry и `IQualifiedNameFilePathConverter`
   собирается **отдельный список объектов захвата 1С**.
   У формы, макета, `.mdo`, подсистем, регистров пересчёта,
   внешних источников — собственные правила.
3. Через `ConfigurationRepositoryLock -Objects` происходит
   захват в связанной с хранилищем ИБ.
4. Если после захвата Основная конфигурация ИБ отличается от
   Конфигурации БД, решение предупреждает/останавливает
   дальнейшую загрузку, чтобы не перезаписать полученные при
   захвате изменения. **Есть опасная настройка «помещать
   даже если конфигурации различаются», брать её нельзя.**
5. Из BM EDT получаются реальные top `EObject`, запускается
   `IExportOperationFactory` с `IncrementalExportStrategy`.
   Стратегия включает дочерние и внешние свойства, но
   `exportUnknown()=false` — ещё одно ограничение.
6. `V8FileBuilder` сопоставляет Git-файлы с экспортированными
   платформенными файлами, формируя **отдельный список
   `-listFile`** для частичной загрузки. Это не прямое
   копирование файлов EDT. Например, для `.mdo` экспортируется
   XML родительского объекта плюс часть внешних файлов;
   для `.bsl` выбирается нужный `Ext/*.bsl`.
7. `Designer.loadConfigurationFromXml` запускает штатный
   `RuntimeExecutionCommandBuilder.importXmlToInfobase(...)`
   с `fileList(...)` и `updateConfigDumpInfo()`.
   После этого в EDT обновляется состояние
   `IInfobaseSynchronizationStateManager`.
8. **На этом реализация заканчивает автоматическую часть.**
   В статье автор требует **вручную** проверить загруженное
   и поместить в хранилище через Конфигуратор. В исходнике
   нет вызова `ConfigurationRepositoryCommit`.
   Следовательно, это пример **Lock + Export + Load**,
   но **не** готового end-to-end автопомещения.
9. Версия 0.4.0 заявляет EDT **2025.2**. Совместимость с
   EDT **2026.2** не подтверждена.
10. `Designer.isConfigurationSame()` определяет отсутствие
    отличий по фиксированному числу строк TXT-отчёта —
    хрупкая эвристика. Её нельзя брать за образец верификации.

**Основной результат сравнения:** штатные API экспорта и
частичной загрузки — правильная отправная точка.
Но индивидуальные правила соответствия
`Git-файл EDT → платформенный файл → объект захвата`
нужно исследовать и валидировать на разных видах объектов,
а не заменять «общим универсальным построением пути».

## 5. Исследование именно вашего Git-процесса

Пользователь делает:

1. В `master` получает состояние хранилища S0.
2. От S0 создаёт `feature`; делает доработку T; коммитит.
3. Сливает T в `master`.
4. В хранилище кто-то уже записал изменения S1.
5. Получает S1 в `master`, при объединении снимает галочку
   с собственного объекта, сохраняет его содержимое. Коммитит
   объединённый `master`.
6. Хочет отправить именно изменения T, а не полученные S1.

### 5.1. Почему diff S0 → текущий master НЕ подходит

В текущем `master` уже есть результат как T, так и S1.
`git diff S0 master` покажет обе группы изменений.
Список изменённых файлов не содержит достоверной отметки
«в этом файле только мои изменения», особенно после
взаимного редактирования одного объекта.

И отдельно: **отмена входящего изменения в EDT
не равна принятию этого изменения**. Если S1 меняет тот
же ресурс, что T, свежий `master` оставляет локальную
версию, отличающуюся от версии хранилища. Это конфликт
перед отправкой, который нельзя объявить закрытым
исключительно на основании коммита `master`.

### 5.2. Две реально объяснимые схемы, не придуманная БД

**Схема А — ветка хранилища отдельно от master разработки.**
Ветка S отражает фактическое состояние БХ/хранилища, а D
содержит разработки. Git `diff S D` даёт недоставленный
итоговый набор изменений. Именно так работает PluginEDT.
Полученные изменения S1 фиксируются в S, а в D
объединяются без потери своей работы. После успешного
помещения состояния можно синхронизировать S.
Плюс: однозначная исходная сторона сравнения.
Минус: пользовательский текущий процесс нужно адаптировать.

**Схема Б — без отдельной ветки хранения, но с конкретной
известной задачей.** По Git-истории выбрать её коммит(ы)
от исходного состояния B до вершины T; по этому
диффу определить **список кандидатов**, а экспортируемое
содержимое взять из итогового `master`. Дополнительно
проверить, не появились ли новые изменения в том же
ресурсе уже после T, и не попадут ли эти изменения в экспорт.
Нельзя произвольно взять `merge-base(master, feature)`
после успешного merge: он может уже указывать на сам T,
что даст пустой дифф. Для гарантии задачи нужен
надёжно установленный диапазон B..T из Git-истории
или явный выбор.
Плюс: может сохранить привычный master/feature.
Минус: Git-список T не является автоматической гарантией
правильного конечного **содержимого** при конфликтующих
получениях из 1С и последующих правках.

**Изученный пример** подтверждает схему А. Схема Б —
обоснованная техническая возможность Git, но
**не подтверждена готовым платформенным решением**.
Нельзя объявлять её готовой только потому, что
`git diff B T` возвращает ожидаемые пути.

### 5.3. Что будет передаваться в пользовательском примере

Предположим, T меняет `Документ.НачислениеПоСреднему.ManagerModule`
и `...Form.ФормаДокумента`, а S1 меняет чужой справочник.

**Кандидаты на передачу:** модуль менеджера и форма.
Изменения чужого справочника, полученные из хранилища
во время обновления, не включаются только из-за
обновления `master`.

**Фактическая отправка допустима**, когда:
а) выбран корректный список платформенных файлов;
б) текущая версия выбранных ресурсов в хранилище
проверена при захвате и не перезаписывается чужая работа;
в) созданный из master экспорт соответствует T,
а не включает несвязанные изменения; г) загрузка
сохранила нужные метаданные и типы.

Если в S1 тоже меняли модуль менеджера/форму, а
пользователь снял галочку, **нельзя автоматически
поместить их поверх S1 без сверки или разрешения**.

Если T изменял `.mdo`, надо рассматривать все
поля и подчинённые ресурсы, которые реально
может затронуть XML-загрузка. Нельзя обещать
«передадим только изменённый реквизит».

## 6. Альтернативы и решение

| Транспорт | Оценка |
| --- | --- |
| EDT native EObject export → platform native partial load → native Lock/Commit | **Основной технически обоснованный кандидат**: штатные операции, подтверждённый аналог |
| Вся конфигурация EDT → полная XML/CF → заменить БХ | Непригодно для типового быстрого помещения, риски огромной области изменений |
| Прямая запись в классическое хранилище через придуманный EDT API/COM | Подтверждённого поддерживаемого интерфейса для этой операции **не найдено**; не реализовывать |
| `1C-Company/GitConverter` | Официальный механизм **хранилище → Git**, обратной отправки не выполняет |
| `gitsync` | Интеграция классического хранилища и Git, не готовый EDT-native плагин для описанного обратного обмена |

Источники:
https://github.com/1C-Company/GitConverter
https://github.com/oscript-library/gitsync
https://its.1c.ru/db/content/edtdoc/src/topics/t000219.html

### Вердикт

1. **Стратегия транспорта:** native EDT export + native 1С partial load
   + штатные команды работы с классическим хранилищем.
   Не полная повторная конвертация всего EDT-проекта.
2. **Выбор содержимого:** определять по Git-изменениям
   относительно **корректной реперной стороны**; в текущем
   master-цикле нельзя смешивать коммит задачи с коммитом
   получения хранилища. Не выбирать вариант Git-ветвления
   за пользователя без проверки последствий.
3. **Степень готовности:** transport подтверждён на уровне
   документации и опубликованного исходного кода
   **для родственного решения**; работа в EDT 2026.2
   и платформе пользователя **не проверена**.
4. **Перед реализацией:** достаточно небольшого,
   чётко поставленного эксперимента на изолированной базе:
   один BSL, один документ с реквизитом ссылочного типа,
   форма, изменения `.mdo`. Проверить точное содержимое
   после native export+load, захваты, условия конкуренции.
   Не превращать эксперимент в обязательную тестовую
   базу при КАЖДОМ обычном помещении.
5. **Следом:** оформить точную спецификацию Git-диффа
   для выбранного пользователем процесса и матрицу
   `вид изменения EDT → комплект файлов 1С → захваты`
   на основании реальных результатов. Затем писать
   продуктовый код. Предварительный `Outgoing*`
   в текущей ветке — **не подтверждённая архитектура**,
   в основную ветку его не вливать.
6. **Отдельная защита:** честно указывать отсутствие
   гарантии абсолютной атомарности HEAD-check vs
   native Commit при конкурентных изменениях.

## 7. Что пока неизвестно

- Реальный набор интерфейсов/версий OSGi в EDT 2026.2.
- Версия платформы Конфигуратора в рабочей ИБ и особенности 8.5.
- Как именно 1С захватывает отдельные подчинённые
  объекты в данной платформе.
- Сохраняются ли все свойства реквизитов, типов, форм
  и команд после экспорта и выборочной загрузки на
  реальном большом проекте.
- Каков фактический latency Lock/Load/Commit по одному
  BSL и форме; измерений нет.
- Можно ли полностью автоматически выполнить Commit
  после адресной проверки без риска незаметной
  замены изменений чужого разработчика — это
