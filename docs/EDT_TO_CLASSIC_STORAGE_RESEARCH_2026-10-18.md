# Исследование: передача изменений из 1C:EDT в классическое хранилище 1С

**Дата исследования:** 2026-10-18.  
**Статус:** техническое заключение, НЕ реализация.  
**Область:** 1C:EDT 2026.2, существующая информационная база-посредник,
подключённая к классическому хранилищу. Никакого воздействия на рабочую ИБ,
хранилище или EDT-проект; CI и платформенные операции не выполнялись.

## 0. Обязательное разделение фактов и гипотез

- **[ДОК]** — подтверждено официальной документацией 1С или EDT.
- **[ПРИМЕР]** — показано в сторонней реализации/ее исходниках;
  это подтверждает существование подхода, но НЕ его корректность в нашей
  EDT 2026.2 или платформе 8.5.
- **[ВЫВОД]** — архитектурный вывод из изученных механизмов.
- **[НЕПРОВЕРЕНО]** — требуется эксперимент, нельзя использовать как
  основание для автоматической записи в реальное хранилище.

Прежние планы в `EDT_TO_CLASSIC_STORAGE_PUSH_ARCHITECTURE.md` и
`OUTGOING_IMPLEMENTATION_STATUS.md` составлялись **до** исследования;
их ранее предложенные правила/классы НЕ считать спецификацией.

## 1. Что предусмотрено платформой 1С

### 1.1. [ДОК] Классическое хранилище и право захвата

- Хранилище оперирует объектами разработки, которые не обязательно
  совпадают один-к-одному с отдельными файлами проекта EDT.
- Для помещения изменённый объект должен быть захвачен; при захвате
  могут получаться его изменения из хранилища. Это критично для риска
  перезаписи чужой работы.
- Пакетный Designer предоставляет:
  `/ConfigurationRepositoryLock -Objects ...`,
  `/ConfigurationRepositoryUnLock -Objects ...`,
  `/ConfigurationRepositoryCommit -Objects ... -comment ...`.
- При **отсутствии** `-Objects` операции могут воздействовать на ВСЮ
  конфигурацию; `-force` для снятия захвата/помещения использовать нельзя.
- `-Objects` — список захватываемых метаданных, не то же самое,
  что список путей к файлам экспорта.

Источники:
- https://its.1c.ru/db/content/metod8dev/src/developers/platform/metod/devtools/i8102287.htm
- https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.27_Administrator_Guide/Appendix_7._Startup_command-line_options_of_1C_Enterprise/7.4._Running_Designer_in_batch_mode/7.4.15._Configuration_repository_operations/

### 1.2. [ДОК] Частичная загрузка из файлов

Руководство разработчика 8.3.27, §2.17.5.3, **различает**:

1. **Загрузку целого объекта метаданных.** Такой объект загружается
   целиком, **со всеми подчинёнными объектами**. Нельзя заявлять, что
   загрузка его XML «поменяет только реквизит и не коснётся форм».
2. **Загрузку отдельного подчинённого ресурса** (модуль, форма, помощь
   и т. п.). Этот режим нужен для быстрой модульной отправки.
3. Загрузка производится в batch-режиме Designer с конкретным списком
   файлов; формат файлов должен соответствовать экспорту 1С.
4. Для базы, подключённой к хранилищу, **все загружаемые объекты
   должны быть захвачены**. Неверно считать успешную выгрузку EDT
   достаточным условием загрузки.
5. При ошибках частичной загрузки откатывается последняя
   сохранявшаяся основная конфигурация; но при запуске с несохранёнными
   чужими изменениями можно потерять эти изменения — нельзя считать
   весь режим атомарной транзакцией резервирования базы.
6. При загрузке изменяются **свойства поддержки**, если они попали в
   файловое представление; нужно отдельно исследовать работу с
   расширениями и поставками.

Источник:
- https://1c-dn.com/library/tutorials/1c_enterprise_developer_guide_8_3_27/
  разделы 2.17.5.3.1–2.17.5.3.6.

**[НЕПРОВЕРЕНО]** Полный набор аргументов, ограничения и порядок
`-listFile`, `-partial`, `-Format Hierarchical`, `-files` для нашей
фактической установленной версии Конфигуратора (особенно если это 8.5).
Не подменять проверку совместимости сходством названий ключей в
документации 8.3.27.

### 1.3. [ВЫВОД] Связи и типы метаданных

Если менялся только `ManagerModule.bsl`, должна исследоваться
адресная загрузка именно модуля: в таком режиме нет оснований
пересоздавать свойства документа, его формы и реквизит
`СправочникСсылка.Сотрудники`.

Если же изменён `.mdo` с описанием реквизита, типом,
табличной частью, формой или составными ссылками, выборочный
перенос описания объекта **не равно** выборочному изменению
одного BSL. Нужно точно знать комплект экспортируемых файлов и
семантику его загрузки. Справочник-ссылка, уже существующий
в конфигурации-получателе с тем же идентификатором, как правило,
не должен экспортироваться «на всякий случай». Но разрешимость
и тождество конкретной ссылки надо проверить.

**[НЕПРОВЕРЕНО]** Семантика изменения структуры (новый реквизит,
тип, удаление, переименование), дополнительных индексов, прав,
макетов, командных привязок форм, неизвестных ресурсов и расширений
при маршруте EDT → XML → Designer.

## 2. Штатные механизмы EDT

### 2.1. [ДОК] Модель данных — BM / EMF

1C:EDT хранит метаданные в собственном Big Model Framework (BM),
объекты модели адресуются FQN, работа с моделью должна учитывать
транзакции. Простое сопоставление файловых путей с «объектами
разработки» хранилища не является платформенным API.

Источники:
- https://edt.1c.ru/dev/ru/
- https://edt.1c.ru/dev/ru/docs/plugins/dev/model/bm/

### 2.2. [ДОК] API экспорта выбранных EObject

Публичные API EDT, опубликованные в JavaDoc:

- `IExportService.work(EObject, IExportArtifactBuilder,
  boolean exportSubordinateObject,
  boolean exportExternalProperties, IProgressMonitor)`.
- **Более подходящая высокоуровневая операция:**
  `IExportOperationFactory.createExportOperation(Path,
  Version, IExportStrategy, EObject...)`, возвращающая
  `IExportOperation` с `run(monitor)`.
- `IExportStrategy` отдельно управляет выгрузкой дочерних объектов,
  внешних свойств и **unknown-артефактов** (не поддержанных EDT
  метаданных). `DEFAULT` включает дочерние, внешние и неизвестные
  артефакты.
- `OrdinaryDirectoryBuilder` предоставляет построение
  файлового артефакта в целевой каталог.

Источники:
- https://edt.1c.ru/dev/edt/2025.2/apidocs/com/_1c/g5/v8/dt/export/IExportService.html
- https://edt.1c.ru/dev/edt/2024.2/apidocs/com/_1c/g5/v8/dt/export/IExportOperationFactory.html
- https://edt.1c.ru/dev/edt/2024.2/apidocs/com/_1c/g5/v8/dt/export/IExportStrategy.html
- https://edt.1c.ru/dev/edt/2024.2/apidocs/com/_1c/g5/v8/dt/export/OrdinaryDirectoryBuilder.html

**[НЕПРОВЕРЕНО]** Совместимость API в релизе EDT 2026.2.
Часть открытых JavaDoc — от 2024.2/2025.2. Проверить именно
target bundles 2026.2 и экспорт в отдельном экспериментальном плагине,
в том числе полученную структуру в каталоге, отсутствие неполных
ресурсов и корректность свойства `exportUnknown`.

### 2.3. [ДОК] EDT и классическое хранилище — разные системы

В официальной методике постепенного перехода аналогом операций
`Lock/Commit/Pull` классического хранилища при *чисто EDT*
разработке выступает **Git**. Сам Git-коммит EDT НЕ является
помещением в классическое хранилище. При гибридной разработке
внесение в основное хранилище остаётся отдельным действием.

Источник:
- https://its.1c.ru/db/content/edtdoc/src/topics/t000219.html

## 3. Исследованы существующие решения

### 3.1. [ПРИМЕР] PluginEDT, ZigRinat85

Статья:
https://infostart.ru/1c/articles/2442956/

Репозиторий:
https://github.com/ZigRinat85/PluginEDT

Изучены **не копируя исходники**:
`ExportHandler.java`, `Designer.java`,
`V8FileBuilder.java`, README.

Фактический подход:
1. Git diff между веткой разработки и веткой, отражающей
   хранилище. Неучтённые в коммитах изменения диффом не видны.
2. Сопоставление изменённых файлов EDT с объектами захвата 1С.
   Варианты с дочерними объектами и специальными видами метаданных
   обрабатываются отдельно.
3. Native BM API → top `EObject` → штатный
   `IExportOperationFactory.createExportOperation(...,
   IExportStrategy, ...)`.
4. По различиям EDT собирается отдельный список файлов
   **платформенного XML/BSL**, а не просто файлы проекта EDT.
5. В существующей подключённой к хранилищу ИБ:
   захват `ConfigurationRepositoryLock -Objects`,
   проверка конфигурации и БД через `CompareCfg`,
   адресная загрузка файлов средствами EDT Runtime Builder.
6. `ConfigDumpInfo.xml` приводится в состояние,
   соответствующее загруженному содержимому, через штатный механизм
   синхронизации EDT.
7. В статье **помещение в хранилище и проверку результата
   автор предлагает делать вручную в Конфигураторе**.
   Поэтому утверждение «готовое решение полностью автоматизирует
   Lock→Load→Commit» было бы неверным.

Важные уроки:
- `V8FileBuilder` содержит много правил сопоставления путей
  для разных классов метаданных. Это свидетельствует о сложности
  transport mapping, но не означает, что правила правильно
  работают для будущих версий.
- Форма/шаблон могут иметь некоторые свойства (синоним,
  комментарий) в `.mdo` родителя EDT, хотя в классическом
  хранилище нужны самостоятельные захваты формы/шаблона.
- Дополнительные индексы уже вызывали ошибки (по changelog).
- `CompareCfg` здесь используется как грубая дополнительная
  защита: в проверенном исходнике отсутствие изменений определяется
  числом строк TXT-отчёта. Такую эвристику нам брать нельзя.
- Публикуемый PluginEDT 0.4.0 заявляет EDT до 2025.2,
  **2026.2 не заявлена**.
- Не копировать программу или её mapping-таблицы без отдельной
  проверки лицензии/совместимости. Исследование — только эталон
  архитектуры и набор опасных пограничных случаев.

### 3.2. [ДОК] 1C-Company/GitConverter

https://github.com/1C-Company/GitConverter

Официальный проект **одностороннего** переноса:
классическое хранилище → Git/EDT. Он полезен как источник
принципов поддержания истории и базовых ревизий, но **НЕ является**
готовым решением обратного помещения EDT → классическое хранилище.

### 3.3. [ПРИМЕР] oscript-library/gitsync

https://github.com/oscript-library/gitsync

Ориентация: конфигурационное хранилище → Git,
с интеграцией инструментов batch 1С. Не считать штатным
обратным транспортом EDT → хранилище.

## 4. Сравнение трёх архитектур

| Вариант | Скорость для одного модуля | Полнота/риски | Заключение |
| --- | --- | --- | --- |
| A. EDT native selected EObject → native export → адресная загрузка через Designer | Потенциально быстрый, без полной конфигурации; зависит от числа запусков Designer | Требует правильного маппинга ресурсов, захватов и проверок версии | **Основной кандидат для эксперимента** |
| B. Полная выгрузка EDT → полный XML/CF → сравнение и замена | Низкая на большой конфигурации | Обширная область изменений, риск незапрошенных ресурсов и очень длинного запуска | **Не для обычной отправки** |
| C. Прямая запись из EDT в бинарное хранилище через предполагаемый API/COM | Неизвестна | Подтверждённого публичного API записи не обнаружено; риск повреждения | **Не выбирать без документального подтверждения** |

Вариант A **не гарантированно работает** для всякого объекта.
Он обоснован только наличием штатных EDT/Designer операций и
существующим рабочим примером класса решений. Нужна проверка
доступных сервисов в нашей EDT 2026.2 и платформе 1С.

## 5. Рекомендация: сначала квалифицировать транспорт, без UI/Commit

**Эксперимент 1: простой BSL.**

- На независимом локальном проекте в целевой EDT 2026.2
  получить `EObject`, создать native export operation и
  экспортировать один заранее определённый изменённый модуль.
- Посмотреть фактическое дерево выходных файлов; не
  прогнозировать имена файлов вручную.
- Через штатную команду Designer загрузить **только** полученный
  BSL в автономную тестовую ИБ (НИКОГДА не в действующую БХ).
- Независимо сравнить текст BSL до и после, удостовериться, что
  реквизиты документа, тип `CatalogRef.Сотрудники`, формы и
  идентификаторы не затронуты.
- Измерить отдельно время экспорта EDT и время каждого вызова 1С.
  Цифры не выдумывать.

**Эксперимент 2: структурное изменение.**

- Изменить тип или добавить реквизит документа, содержащего
  ссылку на существующий справочник.
- Штатно экспортировать объект с необходимыми дочерними и
  внешними ресурсами; изучить состав.
- Проверить частичную загрузку в копию; сравнить свойства
  и UUID, проверить, нет ли потерянных подчинённых ресурсов.
- Точно установить, какие классы таких изменений
  поддерживать, а какие пока выводить пользователю как
  «требует ручной передачи».

**Эксперимент 3: форма и другие особые случаи.**

- Изменить группу элементов без кода, командные привязки,
  свойства синонима/комментария формы, макеты и дополнительные
  индексы; квалифицировать отдельно.
- Проверить native scope захватов, контент и результат
  загрузки — не ориентироваться только на имена файлов.

**Эксперимент 4: сопоставление захватов.**

- На ТЕСТОВОМ хранилище проверить фактические права и последствия
  `ConfigurationRepositoryLock -Objects`, явное разрешение
  параллельных изменений и неудачного Lock.
- Замерить каждый вызов Designer; установить, сколько процессов
  реально нужно. Без такого замера нельзя обещать десятки секунд.

Только после этих четырёх испытаний проектировать production
операцию Commit: отдельное согласие, проверка точного списка,
повторная проверка реального состояния выбранных объектов,
устойчивый журнал неопределённого результата, постконтроль.

## 6. Отдельная задача — выбор локальных изменений

Это **не задача конвертера XML**. Нужно решить источники выбора:

- Git diff между проверенной веткой хранилища и веткой
  разработки, как в PluginEDT; легко, если такой общий предок
  существует, но требует Git-коммитов.
- Явный выбор объектов пользователем: пригоден для
  редактирования без коммита, но сложнее убедиться, что
  захваты не пропустили связанные ресурсы.
- Автоматический анализ проекта по проверенному snapshot:
  затратнее, требует надёжного baseline и разграничения
  входящих/исходящих изменений.

**Рекомендация:** для MVP разрешить вручную выбранные объекты
или Git-diff с явно указанным достоверным основанием;
автоматическое объединение этих механизмов отложить.
Любой выбранный `.mdo` требует особой классификации,
поскольку содержит свойства нескольких объектов разработки.

## 7. Критические вопросы, ещё НЕ отвеченные

1. Ровно какая версия 1С-платформы обслуживает БХ?
   Документация 8.3.27 не гарантирует одинакового поведения 8.5.
2. Какие фактические bundles/API/версии
   `IExportOperationFactory`, `IExportStrategy`,
   BM transactions и RuntimeExecutionCommandBuilder
   включены в EDT 2026.2?
3. Какие файлы формирует export для всех типов объектов?
   Достаточен ли `IExportOperationFactory` без специальной
   стратегии для unknown/external resources?
4. Можно ли с подтверждёнными правами захватить отдельный
   модуль/форму, а не весь родительский объект? Какие
   побочные получения изменений делает захват?
5. Верна ли 1С-semantics partial load выбранного `.mdo`
   для ссылок, UUID, форм и других вложенных ресурсов?
6. Как обнаруживать и защищать **другие локальные изменения
   в базе-посреднике**, пока операция ещё не началась?
7. Какой фактический latency Designer Lock, Load, Compare, Commit
   для файла, сети и размера целевой БХ?
8. Как получить доказанное исходное состояние выбранных
   объектов, если глобальный applied revision отсутствует?
9. Расширения, новые объекты, удаление и переименование:
   отдельные случаи, не включать в первую реализацию.

## 8. Окончательное решение по текущему этапу

**Рекомендовать реализацию сквозного автопомещения СЕЙЧАС рано.**

Достаточно подтверждено, чтобы **проектировать исследовательский
прототип только на отдельной базе/хранилище**, без Commit в реальное
хранилище:

1. Native EDT `IExportOperationFactory` (сначала удостовериться
   в версии 2026.2) → экспорт одного выбранного модуля.
2. Designer native partial load → в изолированную ИБ.
3. Ручная и затем автоматическая проверка, что перенесено
   только запрошенное содержимое.
4. После квалификации — адресные захваты и Commit в
   отдельном тестовом хранилище.
5. И лишь потом — пользовательская команда production
   помещения с измеренным временем исполнения.

Существующий входящий механизм оставлять неприкосновенным.
**Все созданные до исследования классы `Outgoing*` — заготовки,
не валидированный транспорт; запрещено принимать их за готовую
архитектурную спецификацию или на их основании разрешать Commit.**
