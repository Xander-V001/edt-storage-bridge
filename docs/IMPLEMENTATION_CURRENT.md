## Реальная схема

```text
                 КЛАССИЧЕСКОЕ ХРАНИЛИЩЕ 1С
                              │
                /ConfigurationRepository*
                              │
                    СУЩЕСТВУЮЩАЯ ИБ
                   (подключена к хранилищу;
                       не к EDT!)
                              │
            1cv8 DESIGNER /DumpConfigToFiles
                     │             ▲
                XML + индекс        │ LoadConfigFromFiles
                     │              │
            временный импорт EDT    │ XML из EDT
                     │              │
             штатный EDT Compare    │ штатный Export EDT
                    / Merge         │
                     ▼              │
             СУЩЕСТВУЮЩИЙ ПРОЕКТ EDT + Git
```

При получении рабочий проект меняется **только штатным Merge EDT**; Конфигуратор работает с посредником. При помещении исходящий XML загружается **в посредника**, затем штатная команда Commit отправляет изменения в хранилище. Это разные направления, разные разрешения и журналы.

## Почему упоминается 1С:ГитКонвертер

[Официальный 1С:ГитКонвертер](https://github.com/1C-Company/GitConverter) — **односторонняя** синхронизация хранилища в Git/EDT с инкрементальной выгрузкой. В нашем продукте использована архитектурная идея «не перегружать всю конфигурацию при каждой новой версии», но **не код ГитКонвертера, не его процессы формирования Git-истории и не его служебные ветки**. Ключевой транспорт нашего плагина — **штатная** `/DumpConfigToFiles -update -configDumpInfoForChanges -getChanges` и EDT API. Отправка обратно в хранилище не реализована средствами 1С:ГитКонвертера.

## Приоритеты, которые нельзя выдавать за сделанное

1. Собрать точный HEAD (после отдельного разрешения пользователя); исправить компиляцию/OSGi, если потребуется.
2. Проверить полный и инкрементальный receive на тестовой конфигурации: один BSL, форма, изменение структуры, удаление, локальный Git-конфликт, FullDump, пустой и неполный native XML. Проверить содержимое и PENDING/REVIEWED.
3. Исправить и проверить независимую верификацию после исходящего LOAD **до COMMIT**. Сейчас код `OutgoingWholeObjectWriteCoordinator` проверяет Git/HEAD, но не сравнивает фактически загруженные объекты с ожиданием: это реальный стоп-фактор.
4. Квалифицировать импорт и захваты Configuration parent для добавления/удаления метаданных; проверить безопасность для невыбранных объектов.
5. Не тестировать рабочую ИБ/хранилище, не снимать неизвестный native state и не публиковать изменения до доказательства.

## 21.10.2026: native Merge-settings observer (код, не проверенный runtime)

`NativeEdtMergeChoiceObserver` наблюдает за `IComparisonSession` через штатные
события дерева сравнения и считывает только выбранные настройки через
`runComparisonTreeReadonlyTask` до native Merge. Никакого чтения/сравнения
байтов .mdo/.bsl/.distr и никакой самостоятельной реализации Merge.
Наблюдение носит **диагностический** характер: оно не доказывает точный
выбор пользователя по каждой процедуре/объекту.

Повторная форма `chooseKeptLocalOnUi` сохранена, но отключена
`LEGACY_KEEP_LOCAL_DIALOG_ENABLED=false`, поскольку дублировала native EDT
Merge и после отмены оставляла ошибочную PENDING-очередь.
`ReceiveCompletionRecorder.reviewedNativeSelectiveUnknown` повышает только
REVIEWED после существующих проверок Git/HEAD/ИБ/области Merge; отдельные
объекты фиксирует как `unknown-choice-*`, **не** как принятые или
оставленные локальными. APPLIED не меняется. Обязательна сборка и проверка
в установленной EDT 2026.2 прежде чем считать механизм успешным.


### Первая итерация точных событий выбора EDT (21.10.2026)

В `NativeEdtMergeChoiceObserver` вместо агрегированного подсчёта введён
обработчик `IComparisonSession.IComparisonTreeListener.notify(Collection<ComparisonTreeNodeEvent>)`.
Для каждого события сохраняется `getNodeId()`; в read-only BM task через
`session.getNode(nodeId)` читаются `MergeSettings.isMustBeMerged()`,
`getMergeRule()`, `isMergeRuleSetByUser()`, флаг вложенных исключений,
а через `getTopNodeOf(node)` и `getOtherSymlink()/getMainSymlink()` —
верхний объект EDT. `REMOVED` удаляет устаревший узел из снимка.
Дополнительно делается исходный проход по `getNodesWithChangedMergeSettings()`
для первоначальных настроек, которые не породили событий после подписки.

`ReceiveChangesCoordinator` временно показывает эти строки в
`ListDialog` в режиме просмотра после успешного **выборочного** native Merge.
Прежняя форма `ListSelectionDialog` сохранена отключённой: флаг
`LEGACY_KEEP_LOCAL_DIALOG_ENABLED=false`. Текущее окно не запрашивает
повторного выбора и не влияет на записи учёта.

**Ограничение:** события изменения дерева могут порождаться EDT без щелчка
пользователя; подписка может не увидеть изначальные состояния или самое
последнее изменение перед началом Merge. До проверки EDT 2026.2 наблюдения
не используются для автоматической классификации ACCEPTED/KEPT_LOCAL,
`APPLIED` по-прежнему не меняется, решения остаются UNKNOWN.
Побайтовое сравнение не вводилось; экспорт, импорт и native Merge не менялись.
