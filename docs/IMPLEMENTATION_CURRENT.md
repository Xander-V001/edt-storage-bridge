## Реальная схема

```text
                 КЛАССИЧЕСКОЕ ХРАНИЛИЩЕ 1С
                              │
                /ConfigurationRepository*
                              │
                    СУЩЕСТВУЮЩАЯ ИБ
                   (подключена к хранилищу;
                       не к EDT!)
                              │
            1cv8 DESIGNER /DumpConfigToFiles
                     │             ▲
                XML + индекс        │ LoadConfigFromFiles
                     │              │
            временный импорт EDT    │ XML из EDT
                     │              │
             штатный EDT Compare    │ штатный Export EDT
                    / Merge         │
                     ▼              │
             СУЩЕСТВУЮЩИЙ ПРОЕКТ EDT + Git
```

При получении рабочий проект меняется **только штатным Merge EDT**; Конфигуратор работает с посредником. При помещении исходящий XML загружается **в посредника**, затем штатная команда Commit отправляет изменения в хранилище. Это разные направления, разные разрешения и журналы.

## Почему упоминается 1С:ГитКонвертер

[Официальный 1С:ГитКонвертер](https://github.com/1C-Company/GitConverter) — **односторонняя** синхронизация хранилища в Git/EDT с инкрементальной выгрузкой. В нашем продукте использована архитектурная идея «не перегружать всю конфигурацию при каждой новой версии», но **не код ГитКонвертера, не его процессы формирования Git-истории и не его служебные ветки**. Ключевой транспорт нашего плагина — **штатная** `/DumpConfigToFiles -update -configDumpInfoForChanges -getChanges` и EDT API. Отправка обратно в хранилище не реализована средствами 1С:ГитКонвертера.

## Приоритеты, которые нельзя выдавать за сделанное

1. Собрать точный HEAD (после отдельного разрешения пользователя); исправить компиляцию/OSGi, если потребуется.
2. Проверить полный и инкрементальный receive на тестовой конфигурации: один BSL, форма, изменение структуры, удаление, локальный Git-конфликт, FullDump, пустой и неполный native XML. Проверить содержимое и PENDING/REVIEWED.
3. Исправить и проверить независимую верификацию после исходящего LOAD **до COMMIT**. Сейчас код `OutgoingWholeObjectWriteCoordinator` проверяет Git/HEAD, но не сравнивает фактически загруженные объекты с ожиданием: это реальный стоп-фактор.
4. Квалифицировать импорт и захваты Configuration parent для добавления/удаления метаданных; проверить безопасность для невыбранных объектов.
5. Не тестировать рабочую ИБ/хранилище, не снимать неизвестный native state и не публиковать изменения до доказательства.

## 21.10.2026: native Merge-settings observer (код, не проверенный runtime)

`NativeEdtMergeChoiceObserver` наблюдает за `IComparisonSession` через штатные
события дерева сравнения и считывает только выбранные настройки через
`runComparisonTreeReadonlyTask` до native Merge. Никакого чтения/сравнения
байтов .mdo/.bsl/.distr и никакой самостоятельной реализации Merge.
Наблюдение носит **диагностический** характер: оно не доказывает точный
выбор пользователя по каждой процедуре/объекту.

Повторная форма `chooseKeptLocalOnUi` сохранена, но отключена
`LEGACY_KEEP_LOCAL_DIALOG_ENABLED=false`, поскольку дублировала native EDT
Merge и после отмены оставляла ошибочную PENDING-очередь.
`ReceiveCompletionRecorder.reviewedNativeSelectiveUnknown` повышает только
REVIEWED после существующих проверок Git/HEAD/ИБ/области Merge; отдельные
объекты фиксирует как `unknown-choice-*`, **не** как принятые или
оставленные локальными. APPLIED не меняется. Обязательна сборка и проверка
в установленной EDT 2026.2 прежде чем считать механизм успешным.


### Первая итерация точных событий выбора EDT (21.10.2026)

В `NativeEdtMergeChoiceObserver` вместо агрегированного подсчёта введён
обработчик `IComparisonSession.IComparisonTreeListener.notify(Collection<ComparisonTreeNodeEvent>)`.
Для каждого события сохраняется `getNodeId()`; в read-only BM task через
`session.getNode(nodeId)` читаются `MergeSettings.isMustBeMerged()`,
`getMergeRule()`, `isMergeRuleSetByUser()`, флаг вложенных исключений,
а через `getTopNodeOf(node)` и `getOtherSymlink()/getMainSymlink()` —
верхний объект EDT. `REMOVED` удаляет устаревший узел из снимка.
Дополнительно делается исходный проход по `getNodesWithChangedMergeSettings()`
для первоначальных настроек, которые не породили событий после подписки.

`ReceiveChangesCoordinator` временно показывает эти строки в
`ListDialog` в режиме просмотра после успешного **выборочного** native Merge.
Прежняя форма `ListSelectionDialog` сохранена отключённой: флаг
`LEGACY_KEEP_LOCAL_DIALOG_ENABLED=false`. Текущее окно не запрашивает
повторного выбора и не влияет на записи учёта.

**Ограничение:** события изменения дерева могут порождаться EDT без щелчка
пользователя; подписка может не увидеть изначальные состояния или самое
последнее изменение перед началом Merge. До проверки EDT 2026.2 наблюдения
не используются для автоматической классификации ACCEPTED/KEPT_LOCAL,
`APPLIED` по-прежнему не меняется, решения остаются UNKNOWN.
Побайтовое сравнение не вводилось; экспорт, импорт и native Merge не менялись.


### 2026-10-21 — Уточнение фильтрации наблюдателя по реальным отличиям
Во время испытания выборочного Merge EDT сравнила 4 владельца. Наблюдатель ранее выводил 95 узлов, в том числе 80 со сброшенным флагом и `DoNotMerge`, принадлежавших неизменённым дочерним ресурсам. Событие `COMPARISON_FINISHED` само по себе не означает отличия или действия пользователя.

Теперь перед чтением `MergeSettings` для каждого `ComparisonNode` вызывается штатный `node.getComparisonFlags().hasDiffsMainOther()`. Если флаг различий отсутствует, узел удаляется из текущего отображаемого набора; это также применяется при пересчёте того же nodeId. В журнале диагностики отдельно показывается число отфильтрованных узлов. Никаких побайтовых сравнений, изменений Merge или интерпретации `DoNotMerge` без различий. При этом наблюдения по-прежнему **не** доказывают окончательный выбор каждого изменённого дочернего элемента и **не** повышают `APPLIED`.


## 21.10.2026 — уточнение unread/UNKNOWN по реальному полному Merge

[ОПЫТ] При native FULL Merge на ревизии 29453: `PENDING=0`,
`UNKNOWN=8` (из предыдущих выборочных обзоров), диагностический
наблюдатель выдал `не прочитано=1` при 43 264 событиях. В старом коде
`unread = queued.size() + failures`; `failures` увеличивался даже
при `getComparisonSession()` во время ещё не созданной сессии.
Это не означает утрату одного события EDT.

[КОД] После исправления diagnostic различает:
- `pendingNodeReads`: действительно ожидающие или выполняемые чтения ID узлов;
- `readFailures`: ошибки read-only задачи или переполнение bounded очереди;
- `sessionNotReadyAttempts`: ранние неудачные обращения к сессии EDT,
  не считающиеся потерянными событиями.

[КОД] В ветке `pendingNow.isEmpty() && effectiveFull`, и **только после**
подтверждённого глобального native Merge и всех существующих защитных проверок,
старые `unknown-choice-*` переносятся в `full-reviewed-unknown-*` внутри
того же scoped preference journal. Сначала сохраняется архив, затем
удаляются активные метки; данные не утрачиваются при сбое между flush.
Это означает, что предыдущие изменения заново **рассмотрены**,
но не означает их принятия, доказанной идентичности исходнику или
`APPLIED`. `KEPT_LOCAL` не затрагивается. При наличии `PENDING`
автоматического архивирования старых или новых неизвестных решений нет.

Важная граница: снимок нового глобального Merge пока не является
достоверной квитанцией по каждому флажку. Информация о решении
нового глобального Merge остаётся недоказанной, и вывод в диалоге
не должен утверждать, что «всё принято».


## 21.10.2026 — корректировка UI после замечаний разработчика
Показатели `UNKNOWN` — внутренние диагностические метки неопределённого выбора,
не штатный результат EDT и **не** счётчик непринятых изменений.
Поэтому ни они, ни `KEPT_LOCAL=0` без достоверной квитанции, ни счётчики
наблюдателя не выводятся в стандартном итоговом окне. После подтверждённого
Merge показываем факт завершения, количество ожидающих изменений и
обработанную ревизию; служебная трасса выборочного сравнения остаётся
отдельной временной формой для испытаний.
Эксперимент с переносом старых UNKNOWN в `full-reviewed-unknown-*` отозван:
он скрывал реальную неопределённость без подтверждения пользовательских решений.
Действительные записи `unknown-choice-*` не подменяются принятыми и не
удаляются из уже существующего пользовательского журнала.


## 21.10.2026 — подключение штатного выбора EDT к учёту

`NativeEdtMergeChoiceObserver.Snapshot.classifyPending` сопоставляет
имена штатного `-getChanges` с EDT `TopComparisonNode` symlink.
Только узлы, на которых EDT подтвердила различия `MAIN/OTHER`,
принимают участие в решении. Для каждого изменения:
- все относящиеся узлы `[x] GetFromOther` → принять выбор;
- хотя бы один реально отличающийся узел `[ ]`,
  `DoNotMerge` или `nestedExcluded` → локальный вариант;
- отсутствие относящихся узлов / иные правила → не определено.
Завершение `MERGE_PROCESS_FINISHED`, Git/HEAD и проверка посредника
по-прежнему необходимы. Последний статус узла не выводится из
побайтового сравнения.

`ReceiveCompletionRecorder.reviewedNativeObserved` фиксирует
выбранные изменения в `ReceivePendingStore`:
`accepted` очищает прежние local/unknown, `keptLocal` сохраняет
локальное решение, `unclassified` хранит только действительно
неопределённые записи. `REVIEWED` продвигается после уже существовавших
проверок; `APPLIED` не продвигается и никакой новый архив не создаётся.
Диагностическое второе окно отключено; инструментарий чтения остаётся
внутри плагина для логов. Native EDT Merge не подменяется.
