## 0. Дисциплина источников — ЧИТАТЬ КАЖДЫЙ РАЗ

- **[ДОК]** — заявлено в официальной документации 1С, ссылка в §11.
- **[КОД]** — то, что действительно делает текущий исходник плагина, указан класс.
- **[ОПЫТ]** — фактически увидено на пользовательском запуске/логе; это НЕ универсальное свойство платформы.
- **[?]** — гипотеза/различие версий, требует безопасного воспроизведения; нельзя использовать для ослабления проверки или фиксации REVIEWED/APPLIED.
- **[ЗАПРЕТ]** — инвариант безопасности; его нарушение останавливает процесс.

**ЖЁСТКОЕ ПРАВИЛО:** прежде чем назвать файл «обязательным» или «необязательным», назвать *точную комбинацию параметров*, релиз платформы, режим, источник доказательства, результат и последствия отсутствия. Код завершения 0 **не подтверждает ни список изменённых объектов, ни полноту XML, ни состояние EDT.**

## 2. Общая оболочка запуска Конфигуратора: КАЖДЫЙ ПАРАМЕТР

Типовой массив **аргументов ProcessBuilder (НЕ строка shell)**:
```text
<absolute 1cv8.exe> DESIGNER /F <path_to_existing_infobase>
    [/N <IB-user>] [/P <IB-password>]
    [/ConfigurationRepositoryF <repository-address>]
    [/ConfigurationRepositoryN <repository-user>]
    [/ConfigurationRepositoryP <repository-password>]
    /DisableStartupDialogs /DisableStartupMessages
    /DisableUnrecoverableErrorMessage
    <ONE Designer operation and its flags>
    /Out <local-diagnostic-log>
```
**Каждая опция:**
- `DESIGNER`: режим Конфигуратор; не режим ENTERPRISE. [ДОК]
- `/F <path>`: существующая **файловая** ИБ; `/S <server\base>`: существующая **клиент-серверная** ИБ. Адрес не является адресом хранилища. [ДОК] [КОД: InfobaseLocation.switchName]
- `/N <username>`, `/P <password>`: **учётная запись ИБ**, не хранилища. Отсутствие `/P` не означает отсутствия проверки прав. [ДОК] [КОД: DesignerInfobaseAuth.addTo]
- `/ConfigurationRepositoryF` — адрес **классического** хранилища. `/ConfigurationRepositoryN` — пользователь **хранилища**, `/ConfigurationRepositoryP` — его пароль. **НЕ** путать с /F, /N, /P. [ДОК] [КОД: RepositoryUpdateCommand, ReadOnlyReportRunner]
- `/DisableStartupDialogs` — подавляет стартовые диалоги; `/DisableStartupMessages` — стартовые сообщения; `/DisableUnrecoverableErrorMessage` — диалоги фатальных ошибок. **Не** превращают сбой в успех. [КОД; точная семантика на сборке — проверить]
- `/Out <absolute file>` — файл служебных сообщений операции, **не** файл изменённых объектов и **не** XML. Может содержать пути и чувствительную информацию. [ДОК]
- `/DumpResult <absolute file>` — отдельный результат пакетной операции; **не** версия хранилища. Сейчас применяется при снимке ConfigVersionSnapshotRunner. [КОД; трактовку содержимого сверить с конкретной платформой]
- `stdout.txt` / `stderr.txt` создаёт **редирект ProcessBuilder**, а не `-getChanges`, не редактор EDT.
- **Секреты:** argv содержит пароли. НИКОГДА не писать массив аргументов в журнал, Git, markdown-диагностику; Secure Storage защищает лишь хранение до запуска. Файлы /Out проверять перед отправкой.

**Классы-источники:** `InfobaseLocation` (kind: FILE/SERVER, address), `DesignerInfobaseAuth` (validate/addTo), `RepositoryUpdateRequest` (executable, infobase, timeout, repositoryAddress, repositoryUsername, repositoryPassword, infobaseUsername, infobasePassword), `RepositoryHistoryRequest` (executable, infobase, beginVersion, endVersion, timeout), `ChangeDetectionRequest` (executable, infobase, timeout, credentials).

## 3. /ConfigurationRepositoryUpdateCfg: ПОЛУЧЕНИЕ В ИБ, НЕ В EDT

**[ДОК] Сигнатура:** `/ConfigurationRepositoryUpdateCfg [-v <revision>] [-revised] [-force] [-Objects <file>] [-Extension <name>]`.

| Опция / аргумент | Что делает | У нас |
|---|---|---|
| Нет `-v` | Получить последнюю версию хранилища для конфигурации ИБ | **ДА** |
| `-v <n>` | Запросить конкретную версию (при соответствующих условиях связи ИБ и репозитория) | НЕ используется |
| `-revised` | Получать захваченные объекты при необходимости; опасно для локальных правок в Конфигураторе | ЗАПРЕЩЕНО |
| `-force` | **Подтверждение добавления/удаления объектов** при обновлении; **НЕ** означает «сбросить Git/EDT» | **ДА**, осознанный риск для ИБ-посредника |
| `-Objects <object-list-file>` | Ограничение объектов обновления конфигурации ИБ | Нет, обновляется вся ИБ-посредник |
| `-Extension <extension>` | Работа с хранилищем расширения вместо основного | Не используется |

**[КОД]** `RepositoryUpdateCommand.arguments(request, outputFile)` создаёт команду; `RepositoryUpdateRunner.receive(request,cancelled)` запускает её, ограничивает время, проверяет exit, не изменяет рабочий EDT-проект.
**ВЫХОД:** *состояние конфигурации существующей ИБ-посредника* + `/Out`-лог. **Не выдаёт готовую EDT-модель**, не создаёт Git-коммит, не подтверждает REVIEWED или APPLIED.
**ОПАСНО:** после неопределённого завершения не запускать update повторно без диагностики ИБ и сохранённого `ReceiveAttemptLedger`.
**[?]** Версию результата подтвердить отдельной командой отчёта 1С и снимком ИБ; exit=0 недостаточен.

## 4. /ConfigurationRepositoryReport: ЧТЕНИЕ ИСТОРИИ, НЕ ПРИМЕНЕНИЕ

**[ДОК] Сигнатура:**
```text
/ConfigurationRepositoryReport <history.txt>
 [-NBegin <version>] [-NEnd <version>]
 [-DateBegin <date>] [-DateEnd <date>]
 [-GroupByObject] [-GroupByComment]
 [-DoNotIncludeVersionsWithLabels] [-IncludeOnlyVersionsWithLabels]
 [-IncludeCommentLinesWithDoubleSlash]
 [-ConfigurationVersion <version>] [-ReportFormat txt|mxl]
 [-Extension <name>]
```
- `<history.txt>` — отдельный файл отчёта, **не** служебный /Out.
- `-NBegin -1` — запрос последней версии (используется). `-NEnd` — верхняя граница при диапазоне.
- `-ReportFormat txt` — текстовый отчёт; код разбирает формат именно этого режима. При ином языке интерфейса / релизе отчёт может иметь другие заголовки: **не выдумывать** номер.
- `-IncludeCommentLinesWithDoubleSlash` — включать комментарии, начинающиеся с // (используется).
- Остальные перечисленные фильтры/группировки существуют в официальном интерфейсе, но **не используются** нашим обычным receive; их точные сочетания не обобщать.
- `ReadOnlyReportCommand.arguments(request, reportFile, serviceMessages)` создаёт базовую команду; `ReadOnlyReportRunner.commandArguments(...)` добавляет IB-/repo-авторизацию, `readHistory(...)` запускает; `RepositoryLatestRevisionReader.latest(...)` разбирает историю.
- **ВЫХОД:** `history.txt` (человеко-читаемый отчёт 1С); `designer.txt` (/Out); stdout/stderr от ProcessBuilder.
- **Важно:** номер в `history.txt` = НАБЛЮДАЕМЫЙ HEAD, не подтверждение, что в EDT прошёл Merge. Парсер может отвергать реально валидный новый формат. [КОД/ОПЫТ]

## 5. /DumpConfigToFiles: ШТАТНЫЙ XML, ЧЕТЫРЕ РАЗНЫХ РЕЖИМА

**[ДОК] Сигнатура:** `/DumpConfigToFiles <directory> [-Format <mode>] [-Extension <name>] [-AllExtensions] [-update] [-force] [-getChanges <file>] [-configDumpInfoForChanges <file>] [-listFile <file>] [-configDumpInfoOnly] [-Server [-JobsCount <n>]] [-Archive <file>] [-ignoreUnresolvedReferences]`.

**Каждый используемый параметр:**
- `<directory>`: каталог XML-выгрузки; для `-configDumpInfoForChanges` должен быть **пустым до начала**. **Не** файл отчёта.
- `-Format Hierarchical`: иерархический формат XML. Наш parser `ConfigDumpInfoIndex` принимает только `format="Hierarchical"`. Разные форматы/версии нельзя смешивать.
- `-configDumpInfoOnly`: снять текущий `ConfigDumpInfo.xml` конфигурации ИБ **без выгрузки XML объектов**. [КОД: ConfigVersionSnapshotRunner.command]
- `-update`: обновить/сформировать XML-набор по изменениям, а не «обновить ИБ из хранилища». **Не путать с /ConfigurationRepositoryUpdateCfg.**
- `-configDumpInfoForChanges <old ConfigDumpInfo.xml>`: **ВХОД**: файл версий опорной конфигурации; **не** каталог, не Git SHA и не номер версии хранилища. Применяется **вместе с -update и -getChanges**, старый файл не должен изменяться. По документации формируется новый файл версий в выходном каталоге; проверить фактический результат нужной платформы. [ДОК]
- `-getChanges <changes.txt>`: **ВЫХОД**: отдельный список изменённых имён объектов 1С (или `FullDump`), а **не XML**, **не новый ConfigDumpInfo.xml**. При отсутствии изменений *этот файл пуст*. [ДОК]
- `-listFile <object-list.txt>`: **ВХОД**: явный перечень выгружаемых объектов. Подчинённые **самостоятельно разрабатываемые** объекты (формы/макеты и др.) могут требовать отдельного имени. Это **другой формат**, чем `-Objects` хранилища. [ДОК]
- `-force` при `-update`: при несовместимости версии формата выгрузки может потребоваться полная выгрузка. **Не** копировать смысл `-force` из /ConfigurationRepositoryUpdateCfg. [ДОК]; текущая выборочная команда его не использует.
- `-Server/-JobsCount`, `-Archive`, `-ignoreUnresolvedReferences`, `-Extension/-AllExtensions`: разрешены платформой при соответствующем режиме, **не применяются** текущим путём receive. Не добавлять без проверки их эффекта и реальной необходимости.

### Режим A. Только полный индекс — БЕЗ объектов
```text
/DumpConfigToFiles <empty-dir> -Format Hierarchical -configDumpInfoOnly /Out <log> /DumpResult <result>
```
`ConfigVersionSnapshotRunner.command/capture`.
- **ВХОД:** текущая конфигурация ИБ-посредника.
- **ВЫХОД:** `<empty-dir>/ConfigDumpInfo.xml` (объекты не нужны), /Out и DumpResult. 
- Содержит инвентарь метаданных и opaque `id`/`configVersion` у записей; **НЕ** означает, что EDT получила эти объекты; **НЕ** является списком изменений.

### Режим B. Изменения от предыдущего снимка — ПАТЧ + СПИСОК
```text
/DumpConfigToFiles <EMPTY patch-dir>
 -update -configDumpInfoForChanges <OLD ConfigDumpInfo.xml>
 -getChanges <changes.txt> /Out <log>
```
`ChangedObjectsProbe.command/exportNative`; **НЕ вызывает RepositoryUpdateCfg**.
- **ВХОД:** текущая конфигурация уже обновлённой ИБ + **неизменённый** прежний `ConfigDumpInfo.xml`.
- **ВЫХОД:** `changes.txt` — отдельный UTF-8 отчёт; `patch-dir` — XML изменённых объектов и новый `ConfigDumpInfo.xml` согласно документации.
- **[ОПЫТ 2026-10-20]** Конфигуратор вышел с 0 и `changes.txt` существовал, но код не нашёл `patch-dir/ConfigDumpInfo.xml` и бросил `IOException`. **Содержимое отчёта неизвестно (старый плагин его удалил).**
- **[? НЕ ПОДТВЕРЖДЕНО]** Изменение кода, разрешающее отсутствие нового ConfigDumpInfo при ПУСТОМ `changes.txt`, НЕ доказано документацией как гарантия этой комбинации команд. Не объявлять его корректным без воспроизведения на отдельном тестовом наборе; **никакой подмены файла версий**.
- **Безусловно:** непустой changes.txt не доказывает, что каждый XML создан; каталог нужно проверять отдельно; пустой changes.txt не даёт права повышать REVIEWED, если источник/версия не доказаны.

### Режим C. Явный список объектов — НЕ автоматический поиск дельты
```text
/DumpConfigToFiles <empty-dir> -listFile <UTF-8 object-names.txt> /Out <log>
```
`SelectiveDumpCommand.arguments`, `SelectiveDumpRunner.export`.
- **ВХОД:** файл имён объектов для экспорта. `objects.txt` плагин записывает UTF-8 BOM + CRLF. Нужны правильные самостоятельные подчинённые объекты.
- **ВЫХОД:** XML указанных объектов + индексный файл, если платформа его создала, /Out. **Никаких автоматических решений Merge EDT.**
- **Проверка:** нельзя засчитывать одну только `ConfigDumpInfo.xml` как реально выгруженный XML объекта.
- **[?]** Нельзя утверждать, что каждый возможный вложенный объект уже корректно перечисляет `ConfigurationChangesParser.objectsToExport()`; это наше преобразование, не гарантия 1С.

### Режим D. Полная XML-выгрузка — ЯВНО, НЕ fallback
```text
/DumpConfigToFiles <empty-dir> -Format Hierarchical /Out <log>
```
`InitialFullDumpCommand.arguments`, `SelectiveDumpRunner.exportInitialFull`.
- **ВХОД:** вся конфигурация ИБ-посредника.
- **ВЫХОД:** полный набор XML, ресурсов, `ConfigDumpInfo.xml`.
- **Стоимость:** большая конфигурация; НЕ запускать при каждом неполном обновлении; только при первом/явном/доказанно необходимом полном сравнении и после подтверждения.

## 6. Формат changes.txt — КАЖДАЯ запись означает строго определённое

**[ДОК]** UTF-8; одна запись на строку; пустой файл при отсутствии дельты; `FullDump` — одна строка при необходимости полной выгрузки.
- `New:<full-metadata-name>` — новый объект.
- `Modified:<full-metadata-name>` — изменённый объект.
- Переименование может отражаться отдельной строкой: **реальные типы событий и их представление в конкретной версии проверить**; неизвестный статус НЕ считать отсутствием изменений.
- **[КОД]** `ConfigurationChangesParser.parse()` принимает строго `New:`, `Modified:`; `ChangedObjectsProbe.parseNativeText()` отдельно принимает `FullDump`. Неизвестные операции, включая удаления/переименования, пока приводят к отказу от selective: это не доказательство «нет изменений».
- **НЕЛЬЗЯ** путать `FullDump` с пустым отчётом. **НЕЛЬЗЯ** создавать объекты `PENDING` из полной `ConfigDumpInfo.xml`.

## 7. Формат ConfigDumpInfo.xml — ИНДЕКС, НЕ КОНФИГУРАЦИЯ И НЕ ДЕЛЬТА

[ДОК: справочник XML-выгрузки 1С; КОД: `ConfigDumpInfoIndex`]
- Корневой `ConfigDumpInfo`; в используемом формате `format="Hierarchical"`, атрибут `version` относится к **формату выгрузки**, НЕ к номеру версии хранилища.
- `ConfigVersions/Metadata`: отдельные метаданные с `name`; атрибуты `id` и `configVersion` — **непрозрачные идентификаторы** версии объектов, **не** номер 29437. Не вычислять собственную дельту через сравнение токенов вместо штатного `-getChanges`.
- У некоторых `Metadata` нет `configVersion`. `exportableNames()` намеренно их исключает из версии-индекса; `allMetadataNames()` включает при проверке полноты глобального импорта.
- Предыдущий `ConfigDumpInfo.xml` используется как **вход** `-configDumpInfoForChanges`; новый `ConfigDumpInfo.xml` — **выход** конкретной команды. Ни один из них не равен непосредственно HEAD хранилища.
- `ConfigDumpInfoIndex.readVersions` не обязан поддерживать неизвестные версии XML-схемы; ошибка парсинга не означает ошибку самой ИБ.

## 8. Файлы плагина — НЕ файлы платформы

| Файл/каталог | Кто пишет | Как используется | Когда удалять |
|---|---|---|---|
| `previous-ConfigDumpInfo.xml` | плагин копирует старый полный индекс | восстановление до/после UPDATE; источник старой дельты **не всегда** тот же, что предыдущее SCANNED | по журналу фаз, не при произвольной ошибке |
| `last-scanned-ConfigDumpInfo.xml` | плагин копирует актуальный полный индекс | начальная точка следующего штатного `-getChanges` | только контролируемый архивный reset |
| `last-scanned-native-revision.txt` | плагин | числовой HEAD + SHA256 конкретного полного индекса | НЕ передавать как XML |
| `receive-phase.txt` | плагин | NONE / SNAPSHOT_READY / UPDATE_ATTEMPTED / UPDATE_COMPLETED / CHANGES_JOURNALED | только по фазе |
| `initial-full-review-prepared` | плагин | отметка завершённого начального полного просмотра | НЕ доказательство APPLIED |
| `changes.txt` | штатный Конфигуратор | имена изменённых объектов; может быть пуст | сохранять для диагностики ошибок, обезличить перед отправкой |
| `1c-log.txt`, `designer.txt`, `stdout.txt`, `stderr.txt` | Конфигуратор / ProcessBuilder | диагностика, **не доказательство Merge** | хранить локально только при необходимости; возможны секреты |
| `objects.txt` для `-listFile` | плагин | перечень XML-объектов, НЕ Git и НЕ журнал решений | удалить вместе с временной выгрузкой |
| `history.txt` | штатный Конфигуратор | история версий хранилища, отдельный формат от changes.txt | хранить только в диагностических целях |

## 9. Запись в хранилище — РАБОТА ДРУГОГО НАПРАВЛЕНИЯ

[КОД: `OutgoingDesignerCommands.Stage`]
- `LOCK`: `/ConfigurationRepositoryLock -Objects <selectedObjectsXml>` — захват объектов хранилища. **МУТИРУЕТ** состояние захватов; не запускать в рамках receive.
- `LOAD`: `/LoadConfigFromFiles <exportRoot> -Format Hierarchical -listFile <selectedFilesList> -partial` — загрузка выбранных XML **в конфигурацию ИБ-посредника**, не напрямую в хранилище.
- `COMMIT`: `/ConfigurationRepositoryCommit -Objects <selectedObjectsXml> -comment <comment>` — помещение объектов в классическое хранилище.
- `<selectedObjectsXml>` для `-Objects` — XML перечень объектов хранилища; `<selectedFilesList>` для `-listFile` — текстовый список объектов/файлов платформенной загрузки. **ЭТО НЕ ОДНО И ТО ЖЕ.**
- `-comment`: текст комментария, в коде до 200 символов, одна строка.
- **[ЗАПРЕТ]** Эти команды не запускать/не тестировать на реальной ИБ и хранилище без отдельного разрешения. Семантика частичной записи, зависимостей и захватов пока НЕ подтверждена тестом; описание не является разрешением на publish.

## 10. Контрольные вопросы перед любым ответом

1. Какая конкретная команда запущена? Точный `argv`, но **без паролей**?
2. `-update` относится к XML или к хранилищу? Это РАЗНЫЕ операции.
3. На входе какой файл версий: из какого снимка ИБ, какой ветки и когда создан?
4. Какие **разные** файлы должны возникнуть: `changes.txt`, `ConfigDumpInfo.xml`, XML объекта, `/Out`?
5. Что фактически есть на диске, а чего не хватает? Какой exit и что в native /Out?
6. Если файл отсутствует: это документированное нормальное состояние или **НЕПРОВЕРЕННАЯ** гипотеза?
7. После операции база-посредник менялась? Нельзя повторить update вслепую.
8. Где заканчивается ответственность платформы и начинается EDT? Доказательство Merge — только EDT.
9. Не привели ли изменения к ложному REVIEWED/APPLIED, потере локального Git или 23 тысячам фиктивных PENDING?
10. Документируется ли в ответе реальная проверка, или это всего лишь изменение исходников?
