# Отправка изменений из 1С:EDT в классическое хранилище конфигурации 1С

**Статус: архитектурное решение / исследование. Реализация отправки НЕ начата.
Команды записи не запускать без отдельного согласия.** Целевая EDT: 2026.2.

## 1. Принятое направление

Сохраняем существующую базу-посредник, подключённую к классическому хранилищу.
Она не связана с рабочим проектом EDT и не является базой EDT.
Маршрут обратного обмена:

\`\`\`text
Рабочий проект EDT + Git
  -> определить локальные изменения относительно доказанного источника
  -> проверить последнюю реальную ревизию классического хранилища
  -> экспортировать ТОЛЬКО разрешённые объекты EDT -> XML во временную папку
  -> проверить результат в изолированной копии конфигурации 1С
  -> захватить ровно выбранные объекты через классический Designer
  -> повторно проверить ревизию и собственные захваты
  -> выборочно загрузить XML в существующую базу-посредник
  -> проверить итог, список реально затронутых объектов и журнал
  -> повторно проверить ревизию
  -> штатно поместить в хранилище с комментарием
  -> прочитать подтверждение новой ревизии, автора, комментарий, объекты
  -> обновить защищённую контрольную точку.
\`\`\`

Никакого переподключения EDT к посреднику, \`git reset\`, force-unlock,
безусловного перезаписывания конфигурации либо невидимого пользователю commit.

## 2. Варианты транспорта

1. **Основной:** выборочная EDT->XML выгрузка + частичная загрузка XML через
   \`/LoadConfigFromFiles\` + стандартный capture/commit через Конфигуратор.
   Главное преимущество — управляемая область изменений.
2. Полная EDT->XML выгрузка + полная загрузка посредника. **Не использовать по
   умолчанию:** затрагивание чужих объектов, объём и риски.
3. EDT->XML в отдельную тестовую базу -> CF -> сравнение с посредником.
   Хороший вариант предварительной независимой проверки сложных изменений,
   но не способ незаметно заменить рабочий посредник.

## 3. Штатные средства 1С

| Направление | Средство |
| --- | --- |
| EDT -> 1С XML | публичный EDT IExportService.work; альтернативно CLI \`1cedtcli export\` |
| XML -> конфигурация ИБ | Designer \`/LoadConfigFromFiles\`, опции \`-listFile\`, \`-Format Hierarchical\`, \`-partial\` (точную синтаксическую совместимость проверить на целевой платформе) |
| Захват метаданных | Designer \`/ConfigurationRepositoryLock\` + \`-Objects\` |
| Отмена захвата | Designer \`/ConfigurationRepositoryUnLock\` + \`-Objects\` без force |
| Создание новой версии | Designer \`/ConfigurationRepositoryCommit\` + \`-Objects\`, \`-comment\` |
| Номер/история версий | Designer \`/ConfigurationRepositoryReport\` (\`-NBegin -1\` или диапазон, текстовый формат) |

Схемы команд, НЕ проверенные готовые вызовы конкретной версии 8.5:

\`\`\`text
/ConfigurationRepositoryLock -Objects <объекты>
/LoadConfigFromFiles <временный_XML> -listFile <файлы_XML> -Format Hierarchical -partial
/ConfigurationRepositoryCommit -Objects <объекты> -comment <комментарий>
\`\`\`

Список \`-Objects\` и список \`-listFile\` — разные форматы и семантики.
Не переиспользовать список файлов XML напрямую как перечень захватов
хранилища. Захватывать владельцев форм, модулей и прочих вложенных ресурсов
с учётом правил классического хранилища.

Документация: https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/
SDK: https://edt.1c.ru/dev/edt/2025.2/apidocs/
Существующий односторонний пример, **не** решение обратной записи:
https://github.com/1C-Company/GitConverter

API и параметры выше требуют отдельной проверки в EDT 2026.2 и целевой
1C 8.5, прежде чем давать разрешение на реальные операции.

## 4. Необходимые условия отправки (fail closed)

Пусть BASE — реальная ревизия хранилища, для которой доказано успешное
получение всех входящих изменений рабочей Git-веткой, а HEAD —
**свежая** реальная последняя ревизия хранилища, считанная штатным отчётом.

- Если BASE неизвестна, HEAD неизвестна, BASE != HEAD — отправка **ЗАПРЕЩЕНА**.
  Кнопки «Отправить всё равно» не существует.
- Если есть ожидающие/неразрешённые изменения из хранилища или конфликт —
  отправка **ЗАПРЕЩЕНА**, даже если последние номера равны.
- Если сменились Git-ветка, Git HEAD, идентичность проекта или посредника,
  либо возникла незавершённая операция — отправка **ЗАПРЕЩЕНА**.
- Повторно сравнить ревизию перед подготовкой, после захвата, перед
  помещением, и проверить новую версию после помещения.
- Нельзя повышать BASE только по установленным галочкам EDT Merge.
  Нужна доказанная полная применённость или отдельно разработанная
  семантическая проверка конфликтов.

**Гонка версий:** отдельный чтение-HEAD и последующий Commit не атомарны.
Захваты выбранных объектов не блокируют одновременный Commit чужих объектов.
Пока не найден серверный compare-and-swap по номеру ревизии, абсолютную
линейризуемую гарантию не обещать. Нужна дополнительная защита от конкурентных
записей (права/регламент/эксклюзивная операция), иначе остановка при любом
обнаруженном расхождении.

## 5. Определение локальных изменений

Нельзя использовать только \`git diff HEAD~1\`, потому что локальные коммиты
могут накапливаться после последнего успешного получения.

Нужно сравнивать с ДОСТОВЕРНЫМ baseline — состояние содержимого объектов на
последней полностью подтверждённой ревизии хранилища. Учитывать:
- новые, изменённые и удалённые объекты;
- формы, модули, макеты, права, реквизиты, команды, внешние свойства;
- несколько локальных Git-коммитов и незакоммиченные изменения (с явной
  политикой блокировки либо включения в подготовку);
- объекты, не изменяющиеся содержательно вопреки изменениям в Git;
- выборочную отправку с учётом зависимостей и ссылок.

Сегодня \`ReceivePendingStore\` — журнал **входящих**, а не outgoing
изменений. Временная конвертированная конфигурация удаляется после закрытия
редактора. Для исходящих изменений необходим отдельный baseline или
проверенное восстановление состояния конкретной ревизии.

## 6. Изоляция, проверка и отказоустойчивость

1. Все экспорты/проверки — за пределами рабочего EDT и Git.
2. Перед реальной загрузкой в посредник проверить на копии базы, что
   командные привязки форм, подсказки, модули, свойства и ссылки сохранились.
   Известны расхождения XML -> EDT -> CF в формах (включая команды кнопок);
   без оценки этих расхождений автоматическая запись запрещена.
3. До загрузки убедиться, что посредник без посторонних незакоммиченных
   изменений и соответствует сохранённой точке; выполнить резервирование
   состояния и журнал операции.
4. Захват проверяется по точному списку и владельцам. Никакого
   \`-force\`, \`UnLock -force\` и «захватить всё».
5. После загрузки независимо проверить реальный diff посредника. Если
   изменились неожиданные объекты, не помещать.
6. Хранить durable журнал стадии: prepared -> locked -> loaded -> verified
   -> committing -> committed/unknown -> confirmed; исправлять состояние
   только после ручной сверки при uncertain outcome. Никакого слепого
   автоматического повторения Commit.
7. В логах не раскрывать пароли/токены/строки подключения; временные отчёты
   могут содержать имена объектов и должны удаляться контролируемо.
8. Git не коммитится автоматически. Комментарий новой версии хранилища
   вводится/подтверждается пользователем отдельно.

## 7. UI / порядок реализации

Добавить отдельную команду «Поместить изменения в хранилище».
До доказательства всех проверок она не должна разрешать реальную запись.

Этапы:
1. Read-only проверка HEAD/BASE/очереди/Git, подробная причина блокировки.
2. Вычисление локального diff относительно baseline; выбор объектов и
   отображение вложенных ресурсов.
3. Проверка публичного \`IExportService\` и команд частичной загрузки на
   одиночном модуле и форме в **копии**, без Commit.
4. Правила захватов, сохранение состояния посредника, верификация внешней
   загрузки.
5. Только затем отдельный явно подтверждённый штатный Commit.
6. Контроль отчёта новой версии и безопасное обновление checkpoint.

## 8. Связанные реализации в этом репозитории

- \`ReceiveChangesCoordinator\` / \`ReceivePendingStore\`: входящее получение,
  журнал ожидающих объектов и визуальное объединение;
- \`ReceiveRevisionStore\`: последняя обнаруженная и применённая ревизии;
- \`RepositoryLatestRevisionReader\` / \`RepositoryVersionReportParser\`:
  read-only номер и история классического хранилища;
- \`VerifiedReceiveContent\` / \`EdtOwnerContentVerifier\`: осторожная
  проверка входящего merge по содержимому с отчётом о несовпадениях.

Проверка с помощью **побайтового** равенства может быть излишне строгой
для EDT и не является доказательством семантического разрешения конфликтов.
Кандидаты для будущей проверки на уровне моделей — публичные
\`IComparisonManager\` / \`IComparisonSession\`, но точные сигнатуры 2026.2
и поведение при закрытии редактора нужно подтвердить отдельно.
