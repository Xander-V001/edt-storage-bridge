> **НЕ ПУТАТЬ СПИСКИ/ФАЙЛЫ. НЕ ПУТАТЬ ИСТОЧНИКИ ВЕРСИИ. НЕ ПРИНИМАТЬ ФАЙЛОВОЕ РАЗЛИЧИЕ ЗА ВЫБОР ПОЛЬЗОВАТЕЛЯ.**
>
> Сначала целиком перечитать [01: КОМАНДЫ 1С](01_ОБЯЗАТЕЛЬНО_1С_КОМАНДЫ_И_ФАЙЛЫ.md) и [02: EDT API](02_ОБЯЗАТЕЛЬНО_EDT_API_И_MERGE.md), далее этот документ, [AGENTS.md](../AGENTS.md) и [LESSONS_LEARNED.md](LESSONS_LEARNED.md). Проверить **текущий** Java-код.

**Цель:** быстрый безопасный receive из *одного существующего классического хранилища* через *уже существующую привязанную к хранилищу ИБ-посредник, не связанную с EDT* в *существующий Git-проект EDT*. Никаких новых баз, Git worktrees, автосбросов, автоматического повторного обновления, скрытых полных выгрузок. Документ описывает алгоритм и точки контроля; не гарантирует уже проверенную сборку.

## 0. ЧЕТЫРЕ РАЗНЫХ «ВЕРСИИ» — НИ ОДНУ НЕ ПОДМЕНЯТЬ

| Поле | Что это | Кто пишет/читает | Когда менять |
|---|---|---|---|
| `OBSERVED` | последний увиденный **нативный номер версии классического хранилища 1С**, например 29437 | `RepositoryLatestRevisionReader.latest`, `ReceiveRevisionStore.recordObserved` | прочитан достоверный отчёт, это НЕ получение EDT |
| `SCANNED` | последняя **полная опись** конфигурации ИБ-посредника и привязанный к ней нативный HEAD, если подтверждён | `ReceiveBaselineJournal.recordScannedInfo/recordScannedRevision` | после обновления ИБ, сверки снимка; ещё НЕ Merge |
| `REVIEWED` | пользователь завершил рассмотрение входящих изменений до конкретного HEAD, включая сознательно оставленные локальные варианты | `ReceiveCompletionRecorder` → `ReceiveRevisionStore.recordReviewed` | только по корректным доказательствам, даже если `APPLIED` старее |
| `APPLIED` | строгая отметка **полного совпадения**/применения доказанных входящих изменений | `ReceiveRevisionStore.recordApplied` | НЕ после выборочного Merge без глобальной доказанной эквивалентности |
| `Git HEAD` | SHA коммита локального Git проекта пользователя | `GitReceiveGuard` | может не меняться после Merge до коммита, не имеет числовой связи с 1С |
| `configVersion` | opaque token конкретного объекта в `ConfigDumpInfo.xml` | 1С генерирует, плагин только валидирует | **НЕ** сравнивать как номер версии хранилища |

### Два журнала различий
- `PENDING`: точное имя входящего изменения, которое **ещё не рассмотрено/не подтверждено**.
- `KEPT_LOCAL`: изменение рассмотрено, но пользователь **осознанно** сохранил свою локальную версию. **НИКОГДА не ставить из Files.mismatch без подтверждённого выбора**.

## 1. 10 обязательных стадий операции, каждый вход и выход

| № | Стадия/Java | Источник (ВХОД) | Что делает | Результат (ВЫХОД) | ЗАПРЕТ на переход |
|---|---|---|---|---|---|
| 1 | `GitReceiveGuard.requireCleanBranch`, `ReceiveChangesCoordinator` | существующий EDT project/Git | сверяет ветку, Git HEAD и чистоту до изменения | `Baseline(branch, head)` | незакоммиченные файлы — остановка ДО update; не удалять файлы |
| 2 | `ReceiveBaselineJournal.persist` | полный `ConfigDumpInfo.xml` **ИБ до update** | создаёт фазу `SNAPSHOT_READY` | `previous-ConfigDumpInfo.xml` + phase | неизвестная фаза — НЕ обновлять повторно |
| 3 | `RepositoryUpdateRunner.receive` | адрес ИБ, хранилища, учётные записи | **МЕНЯЕТ только ИБ-посредник**: UpdateCfg | обновлённая конфигурация ИБ + /Out | не менять EDT и не выдавать REVIEWED |
| 4 | `ConfigVersionSnapshotRunner.capture` | обновлённая ИБ | снимает полный индекс XML/версий метаданных | `ConfigDumpInfo.xml` **после update** | не считать опись списком дельты |
| 5 | `ChangedObjectsProbe.exportNative` | старый **последний SCANNED** + текущая ИБ | платформа создаёт `changes.txt` и XML-патч | список NEW/MODIFIED/FullDump и patch dir | не подменять 1C-отчёт собственным сравнением токенов; при отсутствии ожидаемых файлов не выдумывать |
| 6 | `ReceivePendingStore.add`, `ReceiveBaselineJournal.recordScannedInfo` | ТОЛЬКО доказанная дельта 1С | записывает реальные ожидающие имена, затем новый SCANNED | PENDING, full snapshot | не помещать 23 408 объектов в PENDING только из-за полного списка |
| 7 | `SelectiveDumpRunner` (при необходимости) | выбранные нативные имена и текущая ИБ | отдельная `-listFile`/глобальная выгрузка по необходимости | XML полного/выборочного набора | никакого самовольного full fallback |
| 8 | `IImportService.work(project,xml,externalTarget,monitor)` | XML платформы + модель EDT | **конвертирует во временный EDT источник** | `*.mdo`, `*.bsl`, resources в отдельной папке | НЕ трогать активный EDT проект во время импорта |
| 9 | `EdtSelectiveReviewService.prepare` + EDT editor | активный `IV8Project`, временная EDT-модель, scope | штатное TWO-WAY сравнение + Merge по выбору пользователя | событие `MERGE_PROCESS_FINISHED` и изменившиеся файлы проекта | закрытие окна ≠ Merge; содержимое .mdo ≠ автоматически принятая галочка |
| 10 | `ReceiveCompletionRecorder`, `ReceiveRevisionStore` | EDT evidence, версия 1С, PENDING, выбор пользователя, Git | фиксирует результат в хранилище ПЛАГИНА | REVIEWED, APPLIED если строго доказан, KEPT_LOCAL при явном решении | НЕТ доказанного HEAD/источника/выбора → не фиксировать |

**Принцип:** `/ConfigurationRepositoryUpdateCfg` работает с **ИБ**, `/DumpConfigToFiles -update` — с **XML файлами**, EDT `IImportService.work` — с **временным EDT источником**, EDT Merge — с **рабочим Git-проектом**. Ни один шаг не заменяет другой.

## 3. Как должна работать версионная последовательность

**Пример:** `REVIEWED=29437`, хранилище → `29438`, изменились общие модули и форма; пользователь принимает модуль, форму сознательно оставляет локальной.
1. Обычный receive → новая версия хранилища + нативный `changes.txt`, только реальные изменения.
2. Плагин подготавливает изменения XML во временный EDT источник.
3. Native compare показывает выбранные объекты. Пользователь вправе оставить свою форму.
4. Native Merge FINISHED; проверяется HEAD, Git, наличие всех предъявленных изменений и сам выбор.
5. `REVIEWED=29438`, форма — `KEPT_LOCAL`, `APPLIED` может остаться на прежней отметке.
6. Следующая версия `29439` — сравниваем **новую** дельту с SCANNED 29438, не всю конфигурацию. Если ту же форму снова поменяли в 1С, предлагаем её снова.
7. Не просмотренные объекты остаются PENDING, не записываем полный REVIEWED до разбора. Не запускать полную выгрузку без подтверждения.

**ВАЖНО:** отчёт EDT «6119/6121 файлов совпали» не опровергает факт, что пользователь выбрал всё. Bytewise `Configuration.distr` или `.mdo` не является native EDT семантическим сравнением.

## 5. Перед каждым изменением: ЧЕК-ЛИСТ ДОКАЗАТЕЛЬСТВА

- [ ] Перечитаны **01 + 02 + 03 + AGENTS + LESSONS + актуальные исходники**.
- [ ] Указана конкретная команда/сигнатура и **каждый аргумент**, а не только имя метода.
- [ ] Указаны **раздельно**: входные файлы, выходные файлы 1С, временные EDT файлы, файлы рабочего EDT.
- [ ] Указан результат native `changes.txt` и обнаруженный каталог XML; не делаем выводы по одному IOException.
- [ ] Знаем, изменили ИБ-посредник или только прочитали её? Повторное обновление безопасно?
- [ ] Платформа/EDT определяют результат штатными сервисами; собственные проверки не дублируют и не подменяют их без оснований.
- [ ] Достоверно различаем `PENDING`, `KEPT_LOCAL`, `REVIEWED`, `APPLIED`.
- [ ] Любое утверждение имеет метку [ДОК], [КОД], [ОПЫТ] или [?]; нет «я уверен» без теста.
- [ ] После кода: указаны файлы/коммиты, **сборка и тесты запущены только по отдельному разрешению**.
- [ ] Нет изменений на рабочем VPS, в реальной ИБ или локальном EDT без явного разрешения.

**НЕЛЬЗЯ:** скрыто запускать полную выгрузку; использовать рабочую EDT-подключённую ИБ как посредника; требовать удаления Git-коммитов; повышать числовую версию по configVersion; удалять диагностические файлы до разбора неизвестного штатного результата; выдавать подготовленный код за проверенный релиз.
