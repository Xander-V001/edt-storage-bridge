# MCP-сервер EDT Storage Bridge

**Статус ветки:** реализация исходного MCP-слоя, без запусков GitHub Actions, без установки и smoke-теста в EDT 2026.2. Пока не считать подтверждённой рабочей сборкой.

## Назначение

В окне **Работа с хранилищем** две вкладки: «Хранилище 1С» (без изменений существующего сценария) и новая «MCP».

Один встроенный MCP-сервер на всю текущую рабочую область EDT. Каждый проект задаётся явным именем в аргументе инструмента \`project\`; произвольный путь, командная строка, BSL-код или полный доступ к 1С через MCP не принимаются.

Сервер использует только java.base (локальный TCP/HTTP и JSON-RPC), чтобы не добавлять несовместимые сторонние зависимости к Tycho/OSGi runtime EDT. Это небольшой **ограниченный Streamable HTTP / JSON response** transport для MCP с \`initialize\`-handshake и \`tools/list\`, \`tools/call\`; не полный Java SDK. Поддерживаются классические протокольные версии \`2025-11-25\`, \`2025-06-18\`, \`2025-03-26\`, без SSE и без server-to-client requests. Современный \`2026-07-28\` \`server/discover\` **не реализован**: клиенты должны уметь использовать handshake-era protocol / legacy mode. Недоступность SSE сигнализируется HTTP 405 на GET.

Основа — существующие \`ReceiveChangesCoordinator\`, \`ReceiveRevisionStore\`, \`ReceivePendingStore\`, \`RepositoryLatestRevisionReader\`, \`OutgoingReadinessCoordinator\`. Никакой новой транспортной записи хранилища не добавлено, существующие алгоритмы не изменены.

## Настройки и безопасность

* Адрес фиксирован: \`http://127.0.0.1:8769/mcp\` (порт изменяемый, 1024–65535); внешний интерфейс и IPv6 не слушаются.
* Заголовок \`Authorization: Bearer <токен>\` обязателен для каждого запроса. 32-байтный случайный токен генерируется локально и сохраняется **зашифрованным в Eclipse Secure Storage**.
* Проверяются HTTP Host/Origin (от DNS-rebinding), число клиентов/очередь, размер тела (256 КиБ), заголовков (12 КиБ), read timeout (20 секунд). Не допускаются заголовки Transfer-Encoding и недостоверный Content-Length.
* Никакие токены, пароли и произвольные аргументы запросов не записываются в журнал MCP; сообщения ошибок в основном обезличены.
* **Нет автозапуска** и внешнего доступа. Смена порта/токена требует остановки и повторного запуска сервера.
* Кнопка **«Проверить»** реально посылает запросы \`initialize\`, \`notifications/initialized\`, \`tools/list\` через TCP/HTTP. Она не обращается к 1С.
* Кнопка **«Копировать MCP-конфигурацию»** помещает в буфер JSON с токеном. Не вставляйте этот JSON в Git/логи.

Пример структуры подключения (в UI можно скопировать готовый вариант с реальным секретом):

\`\`\`json
{
  "mcpServers": {
    "edt-storage-bridge": {
      "type": "http",
      "url": "http://127.0.0.1:8769/mcp",
      "headers": {
        "Authorization": "Bearer <ТОКЕН_ИЗ_SECURE_STORAGE>"
      }
    }
  }
}
\`\`\`

**Порт 8769 выбран по умолчанию**, чтобы не пересекаться с MCP-портами 8765 и 8768 других EDT-плагинов. Конкретный клиент может использовать иную форму настроек HTTP MCP; при этом endpoint и header остаются прежними.

## MCP tools

| Инструмент | Эффект |
|---|---|
| \`list_projects\` | Список открытых проектов; не изменяет данные |
| \`get_storage_status(project)\` | Обнаруженная/обработанная версия, ветка и число ожидающих объектов. Без паролей; не читает актуальную версию через 1С |
| \`get_pending_changes(project)\` | Названия объектов в журнале ожидания текущей Git-ветки |
| \`check_repository_revision(project)\` | Читает **фактическую** последнюю версию через штатный TXT-отчёт Конфигуратора 1С; не двигает checkpoint EDT |
| \`request_receive_changes(project)\` | Только ставит запрос подтверждения в окне EDT, затем запускает **существующее выборочное получение** через \`ReceiveChangesCoordinator\` |
| \`request_full_review(project)\` | Аналогично — штатная **полная сверка** \`ReceiveMode.FULL_REVIEW\` |
| \`request_publish_readiness(project)\` | Аналогично — существующая проверка Git/версий и исходящее сравнение \`OutgoingReadinessCoordinator\` |

У инструментов \`request_*\` ответ \`awaiting_user_confirmation_in_edt\` **не означает успех** и не подтверждает результат выполняемого Job/EDT Merge. Пользователь должен работать с реальным окном EDT.

### Почему нет \`publish_changes\` / \`commit\`

В текущей ветке есть экспериментальные \`Outgoing*WriteCoordinator\` для **тестовых копий** с дополнительными ограничениями. Они не квалифицированы для безопасной отправки в настоящее хранилище, не собраны и не испытаны в EDT 2026.2/1С. Их прямой MCP-вызов мог бы обойти ручные подтверждения и привести к неконтролируемой записи. Поэтому публичный MCP инструмент записи намеренно отсутствует. После квалификации существующего исходящего workflow можно будет добавить отдельную обёртку с явной human approval, проверкой HEAD/revision, отсутствия pending, review и fail-closed журналом неопределённых результатов — **не переписывая сам workflow**.

## Проверка в EDT (после отдельно запрошенной сборки)

1. Установить собранную feature-версию в тестовую EDT 2026.2. Сверить, что прежняя вкладка и её кнопки получения/полной сверки ведут себя без изменений.
2. Открыть вкладку MCP, сохранить порт и токен, нажать «Запустить», затем «Проверить». Убедиться, что ответ включает список инструментов.
3. Подключить MCP-клиент через скопированную конфигурацию, выполнить \`list_projects\`, \`get_storage_status\` и \`get_pending_changes\` на тестовом проекте.
4. Проверить отказ с неправильным токеном (HTTP 401), чужим Host/Origin (HTTP 403), закрытым портом и вторым сервером на том же порту.
5. \`check_repository_revision\` — исключительно на тестовом подключении: сверить номер из отчёта. Не считать полученный номер «обработанной версией».
6. \`request_receive_changes\`, \`request_full_review\`, \`request_publish_readiness\`: проверить окно подтверждения, отказ без последствий, запуск существующего сценария при согласии и защиту от повторного запуска. Для операций записи нужны отдельные утверждённые тесты.
7. Остановить сервер, убедиться в недоступности порта; закрыть EDT и убедиться, что listener завершён.

CI workflow остаётся \`workflow_dispatch\` **только вручную по запросу пользователя**. Этот коммит сборку/тесты не запускает.

## Рекомендации по развитию

После испытаний: ограничение количества одновременно запущенных тяжёлых отчётов 1С, пагинация больших журналов ожидающих объектов, structuredContent для результатов, явные идентификаторы job/request и polling реального прогресса, а также поддержка современного MCP \`2026-07-28\` через официальный SDK, если зависимость пройдет OSGi/Tycho-валидацию. Не смешивать статус *запрошено* с *выполнено*.
