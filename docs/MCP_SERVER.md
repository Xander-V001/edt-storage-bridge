# MCP-сервер EDT Storage Bridge

**Ветка:** `feature/edt-2026.2-integration`. **Статус:** изменение исходников, **не проверено компиляцией и в установленной EDT 2026.2**. Нельзя считать автоматическое помещение проверенным для рабочего хранилища.

## Режимы не пересекаются

**Из EDT:** старые контекстные команды, подтверждения, редакторы сравнения и сообщения об ошибках остаются как были. Существующие публичные UI-входы используют прежние маршруты.

**Через MCP:** вызов инструмента уже содержит полномочие исполнить операцию; дополнительное подтверждение из окна EDT не требуется. Длительная работа запускается штатным Eclipse Job. Возвращённый `operationId` означает только **принятие запроса**. По нему вызывают `get_operation_status` до терминального состояния. Кнопки и ручные сценарии EDT этим не изменяются.

### MCP-инструменты

| Имя | Назначение |
|---|---|
| `list_projects` | Список открытых проектов EDT |
| `get_storage_status(project)` | Локальные OBSERVED/REVIEWED, Git-ветка и число PENDING (не онлайн-HEAD) |
| `get_pending_changes(project,offset?,limit?)` | Журнал PENDING, постранично (максимум 200) |
| `check_repository_revision(project)` | Текущий HEAD 1С из штатного отчёта без записи |
| `receive_changes(project)` | **Без диалогов** запускает `ReceiveMode.AUTOMATIC`: нативное получение 1С, EDT import, штатный headless compare/merge `GET_FROM_OTHER` без редактора |
| `publish_changes(project)` | **Без диалогов** запускает проверку Git/HEAD и существующую цепочку нативного headless EDT compare → штатный EDT export → подготовка Lock/Load/Commit |
| `get_operation_status(operationId)` | Состояние `queued/running/completed/failed/uncertain`, фаза, причина остановки; `completed` — терминальное состояние Job, а не подтверждение независимой проверки содержимого хранилища |

`receive_changes` принимает все входящие отличия, в том числе удаление объектов. Независимые локальные изменения могут быть заменены. Нужны чистая Git-ветка и штатные подтверждения целостности источника. Если по требованиям корректности потребуется полная XML-выгрузка, она возможна **без открытия окна сравнения**, не как выбор пользователя в EDT. При неизвестной версии, неполных данных, неудачном Merge или иной неоднозначности операция останавливается.

`publish_changes` **не** вызывает существующий интерактивный вариант помещения, даже если в настройках выбран «Ручное помещение через Конфигуратор». Для MCP используется автоматическая ветка — но проверки и квалификация тех же данных. Если HEAD отличается от REVIEWED, есть PENDING, нарушена Git/ИБ-проверка или не доказан точный состав объектов для записи, помещение запрещается. Агент должен сперва обновить проект отдельной командой, а не автоматически запускать бесконечную цепочку повторов.

После начала нативных Lock/Load/Commit ошибка может означать **неопределённое состояние**. В таком случае инструмент сообщает `uncertain` и запрещено слепо повторять помещение; требуется сверка захватов, состояния базы и хранилища.

### Ограничения реализации

- Автоматическое помещение в проекте пока **TEST-ONLY**. В действующем коде отсутствует независимая проверка фактически загруженного содержимого **после LOAD и до COMMIT**. Проверки HEAD, Git и состава XML этот пробел не устраняют.
- Признак `completed` при помещении фиксирует завершённый Designer COMMIT с кодом 0, **не** отдельное доказательство состава новой версии хранилища.
- Состояния MCP-операций хранятся в памяти запущенного EDT; после перезапуска `operationId` недоступен. Не путать с долговременными журналами самой 1С-операции.
- MCP не предоставляет самостоятельных `Lock`, `Load`, `UnLock`, произвольного запуска Designer, выполнения BSL и обхода проверки версии.
- При длительных операциях MCP-клиент должен опрашивать `get_operation_status`. Отсутствие ответа не означает успешное завершение и не разрешает повторную запись.

## Подключение

В диалоге **«Работа с хранилищем» → «MCP»**: порт, **необязательный** токен, флажок **«Автоматически запускать MCP-сервер при старте EDT»**, «Запустить», «Остановить», «Проверить», «Создать новый токен», «Копировать MCP-конфигурацию». Сервер останавливается при закрытии EDT. Endpoint только локальный: `http://127.0.0.1:8769/mcp`. По умолчанию на **новом** рабочем пространстве токен пустой и для локального подключения нужен только URL. Если токен заполнен, требуется `Authorization: Bearer <token>`, а сам токен хранится в Eclipse Secure Storage. Существующий сохранённый токен от старой версии **не отключается автоматически**; для перехода к подключению по одному URL нужно остановить сервер, очистить поле токена на вкладке MCP, сохранить и снова запустить сервер (или перезапустить EDT). Открытые порты с внешних сетевых интерфейсов не поддерживаются независимо от настройки. Ограничены Host/Origin, размер сообщения и очередь. Порт 8769 не совпадает с существующими 8765/8768.

**Безопасность:** доступ без токена означает, что **любой локальный процесс**, способный обращаться к `127.0.0.1:8769`, может вызвать MCP-инструменты, включая автоматическое изменение проекта и экспериментальное помещение. Ограничение интерфейса и проверки Host/Origin уменьшают сетевые/browser-риски, но не изолируют недоверенные программы на том же ПК. Для более строгого доступа следует задать токен.

**Подключение в Codex без ручного редактирования файлов:** после запуска EDT добавить HTTP MCP-сервер с URL `http://127.0.0.1:8769/mcp` в интерфейсе Codex (если доступно в установленной версии) или штатной командой Codex `codex mcp add edt-storage-bridge --url http://127.0.0.1:8769/mcp`. Вносить токен или редактировать `config.toml` на новой установке не требуется. Сам факт регистрации MCP в Codex не означает, что сервер прошёл тест совместимости.

Пример конфигурации клиента без токена (вкладка MCP также позволяет скопировать JSON):

```json
{
  "mcpServers": {
    "edt-storage-bridge": {
      "type": "http",
      "url": "http://127.0.0.1:8769/mcp"
    }
  }
}
```

Реализован минимальный Streamable HTTP JSON-RPC: `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`. SSE, MCP ресурсы и prompts не реализованы.


### Автозапуск после открытия EDT

- Подключён штатным расширением Eclipse `org.eclipse.ui.startup` и реализацией `BridgeMcpStartup.earlyStartup()`. Оно вызывается после запуска workbench на фоновом потоке, даже если диалог настроек плагина не открывался. **Не** размещать это действие только в `BridgeActivator.start`: у бандла включена ленивая активация.
- Флажок автозапуска включён по умолчанию. На **новом** рабочем пространстве сервер стартует на `127.0.0.1:8769` **без токена и без предварительной настройки**. При запуске EDT новый токен не создаётся, настройки не перезаписываются. Если токен уже был сохранён раньше, автозапуск использует именно его и не отключает авторизацию.
- Изменение флажка действует после сохранения окна настроек; автостарт происходит при **следующем** запуске EDT. Выключение флажка не прерывает уже работающий сервер: для остановки в текущем сеансе служит кнопка «Остановить».
- Автостарт не открывает окна подтверждения и не запускает получение/помещение в хранилище. Ошибки доступа к Secure Storage (когда выбран режим с токеном), некорректных настроек или занятого порта регистрируются в **Error Log EDT** без токена/паролей и без блокировки запуска самой EDT.
- Eclipse позволяет отдельно отключать `org.eclipse.ui.startup` для плагина в **Preferences → General → Startup and Shutdown**. В таком случае собственный установленный флажок не сможет принудительно запустить сервер.

**Режимы работы:** команда из меню EDT остаётся интерактивной; отсутствие диалогов относится только к командам MCP. Автостарт сервера не меняет сценарии получения и помещения.

## Сверка с DitriXNew/EDT-MCP и спецификацией MCP (14.11.2026)

Референс для **архитектуры**, без копирования исходного кода: [DitriXNew/EDT-MCP](https://github.com/DitriXNew/EDT-MCP), AGPL-3.0-or-later. Исходники проекта опубликованы под AGPL; при использовании конкретного кода потребуется отдельно соблюдать условия лицензии. Реализация нашего сервера остаётся самостоятельной.

**Фактически изучены:**

- `mcp/bundles/com.ditrix.edt.mcp.server/plugin.xml` — штатная точка `org.eclipse.ui.startup`.
- `McpServerStartup.java` — класс `IStartup`, чтение сохранённых настроек и старт сервера; проверка `shouldStartHttp` отделена от реализации запуска, покрыта `McpServerStartupTest`.
- `PreferenceInitializer.java`, `PreferenceConstants.java` — явный сохранённый флажок автозапуска (у DitriXNew по умолчанию **выключен**). У нас он по умолчанию включён, токен на новом рабочем пространстве необязателен.
- `McpServer.java`, `transport/McpHttpHandler.java`, `transport/HttpTransport.java` — готовая HTTP-инфраструктура JDK, отдельные обработчики транспорта, ограничение очередей, авторизация, Origin, управление сессиями, SSE.
- `mcp/tests/.../McpServerStartupTest.java`, `McpServerTest.java`, тесты протокола и GitHub CI conformance — важность проверки не только появления TCP-порта, но и реальных MCP-вызовов.

**Сопоставление:**

| Направление | Наш плагин | Оценка |
|---|---|---|
| Eclipse/EDT автозапуск | `org.eclipse.ui.startup` → `IStartup.earlyStartup()` | Совпадает с подходом DitriXNew и документацией Eclipse. Требует проверки в установленной EDT |
| Сохранённые настройки | `InstanceScope` + `Secure Storage` для токена | Локальный режим, секрет не пишется в открытый текст preference |
| Старт без готовой конфигурации | Автозапуск на локальном интерфейсе **без токена**, если нет прежних настроек | Пользовательский сценарий, аналогичный DitriXNew; есть риск вызовов от любых локальных процессов |
| HTTP | Собственный ограниченный HTTP/1.1 parser поверх `ServerSocket` | **Риск совместимости:** не принимает `Transfer-Encoding: chunked`; надо проверить реального клиента Hermes и рассмотреть перенос на стандартный `HttpServer` при подтверждённой OSGi-доступности |
| Streamable HTTP | POST JSON, GET возвращает 405; нет SSE и сессий | Допускается [MCP 2025-11-25 transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) как статeless-вариант. SSE/сессии DitriXNew не обязательны для наших 7 простых инструментов |
| Контроль вызовов | Необязательный Bearer (только локальный bind), Host/Origin, максимальный размер/очередь, статусы длинных операций | В режиме с токеном проверяем отказ HTTP 401, в режиме без токена — обычное подключение по URL. Нужны негативные тесты и проверки параллельных запросов |
| Разделение UI/MCP | Ручной UI остаётся интерактивным, MCP без диалогов | Не переносить правила ручных подтверждений из DitriXNew в наш workflow |

**Что улучшено по результатам аудита:** локальный `BridgeMcpServer.probe()` проверяет `initialize`, `tools/list`, наличие всех 7 инструментов и реальный безопасный вызов `list_projects`. При настроенном токене дополнительно проверяется HTTP 401 при неправильном токене. При пустом токене проверяется подключение без заголовка Authorization. Он не запускает 1С и не меняет проект. Это **проверки в исходниках**, до сборки они не исполнялись.

**Что остаётся непроверенным:** совместимость с реальным Hermes и его HTTP-стеком, запуск после перезапуска EDT и разблокировка Secure Storage без UI, повторный запуск после занятого порта, большие/параллельные запросы, `POST chunked`, завершение операций без интерактивных окон и post-LOAD в 1С. Не копировать исходники DitriXNew без юридической оценки AGPL и не считать его успешный CI доказательством работоспособности нашего сервера.

## Проверки перед использованием

1. **Только по отдельному запросу пользователя**: собрать текущий HEAD ветки, проверить импорты Java/OSGi, вкладку, сохранение флажка, фактический автозапуск сервера без открытия окна настроек и работу в EDT 2026.2. Пройти безопасный встроенный HTTP self-test и отдельно проверить подключение Hermes: initialize → tools/list → list_projects → get_operation_status.
2. Проверить вызов `receive_changes` на изолированных копиях проекта, ИБ-посредника и хранилища: без диалогов, с правильным результатом и с сохранением ручного режима EDT.
3. Для `publish_changes` сначала отрицательные кейсы: HEAD ушёл вперёд, PENDING, грязный Git, недостоверный XML, ошибка Lock/Load/Commit, неоднозначное состояние.
4. **Не выполнять пробную запись в рабочем хранилище.** Проверить на изолированных копиях post-LOAD результат, все виды метаданных, добавления и удаления, захваты, неизменённые объекты. Закрыть пробел независимой проверки содержимого до оценки готовности к промышленной записи.
5. Не включать автоматический запуск CI по push/commit. Не использовать пользовательский VPS и реальную ИБ без отдельного разрешения.
