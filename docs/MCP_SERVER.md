# MCP-сервер EDT Storage Bridge — интеграция

**Рабочая ветка:** \`feature/edt-2026.2-integration\`. 
**Статус:** только исходники. CI-сборка, проверка OSGi и smoke-test в EDT **не запускались**.

## Вкладка

**Работа с хранилищем → MCP**. Существующие вкладки «Основная» и «Подключение к хранилищу» не заменены. Новая вкладка добавлена к уже существующим TabFolder/диалогу. Существующие формы, команды и механизмы обновления/помещения не менялись.

Настройки: порт, защищённый токен, локальный endpoint. Кнопки «Запустить», «Остановить», «Проверить», «Создать новый токен», «Копировать MCP-конфигурацию». Сервер запускается только вручную и автоматически останавливается при завершении EDT.

### MCP protocol

Встроенный небольшой обработчик **Streamable HTTP / JSON-RPC**, отдельный TCP-порт, который слушает \`127.0.0.1\` (не 0.0.0.0 и не IPv6).
Адрес по умолчанию: \`http://127.0.0.1:8769/mcp\`.
MCP handshake \`initialize\`, уведомление \`notifications/initialized\`, \`ping\`, \`tools/list\`, \`tools/call\`.
Проект явно указывается в аргументе \`project\` каждого инструмента.
Протокол реализован в локальном Java-коде без новых внешних зависимостей. Это ограниченная реализация; SSE/ресурсы/prompts/jobs/notifications кроме инициализации не поддерживаются. Полноценное взаимодействие разных MCP-клиентов нужно испытать.

### Безопасность

Токен создаётся случайно, сохраняется в **Eclipse Secure Storage**. Каждый запрос требует \`Authorization: Bearer <token>\`. Проверяется Host и Origin против локального адреса, установлены ограничения размера запросов и очереди подключений. Удалённый доступ отключён.
Порт по умолчанию 8769 отличается от 8765/8768, используемых соседними MCP-серверами EDT; при конфликте можно выбрать другой.
Смена токена/порта при работающем сервере блокируется до остановки. Данные токена передаются только в буфере обмена при явном действии пользователя. Не отправляйте скопированную конфигурацию в репозитории или логи.

Пример формата (не реальный токен):

\`\`\`json
{
  "mcpServers": {
    "edt-storage-bridge": {
      "type": "http",
      "url": "http://127.0.0.1:8769/mcp",
      "headers": {
        "Authorization": "Bearer <Токен_из_вкладки_MCP>"
      }
    }
  }
}
\`\`\`

Конкретный MCP-клиент может требовать другое имя корневого поля; настройки endpoint и заголовок остаются теми же.

## Инструменты

| Имя | Что делает |
|---|---|
| \`list_projects\` | Список открытых проектов рабочей области EDT |
| \`get_storage_status(project)\` | Сохранённая наблюдаемая и обработанная версия, ветка Git, число ожидающих объектов |
| \`get_pending_changes(project,offset?,limit?)\` | Журнал ожидающих объектов, постранично (по умолчанию 100, максимум 200) |
| \`check_repository_revision(project)\` | Читает фактическую текущую версию из штатного отчёта 1С; **не** обновляет базу и не подтверждает применённую версию EDT |
| \`request_receive_changes(project)\` | Запрашивает подтверждение в EDT и затем вызывает существующее **ручное** выборочное получение с native merge |
| \`request_full_review(project)\` | Запрашивает подтверждение в EDT и вызывает существующую полную сверку/ручной native compare |
| \`request_publish_changes(project)\` | Запрашивает подтверждение в EDT и вызывает **существующий** путь \`OutgoingReadinessCoordinator.check\`. В зависимости от настроек он может выполнить автоматическую запись в классическое хранилище или начать подготовку к ручному помещению |

### Ограничения и правила работы агентов

- \`request_*\` возвращают **только принятие запроса к показу окна** (\`awaiting_user_confirmation_in_edt\`), а не факт завершения/успеха. После подтверждения в EDT запускаются существующие операции и их штатные охранные проверки.
- MCP **не** содержит отдельного \`repository_commit\`, \`Lock\`, \`Load\`, \`UnLock\` или BSL execution tool. Он не обходит существующие подтверждения, проверки версий и Git.
- Новая вкладка не запускает 1С при открытии. \`check_repository_revision\` — отдельный явный вызов. Внутри 1С он читает отчёт через существующий класс \`RepositoryLatestRevisionReader\`.
- \`get_storage_status\` отражает локальные сохранённые checkpoints, а не реальный текущий HEAD 1С. Для актуальной версии отдельно вызывайте \`check_repository_revision\`.
- Из-за ограничения транспорта/операции в EDT пока нет отдельного MCP polling успешности/отказа после запуска Job. Нельзя выдавать агенту предварительный ответ за успешное помещение.

## Smoke test после отдельного разрешения на сборку

1. Собрать **только по явному запросу пользователя** рабочую ветку \`feature/edt-2026.2-integration\` под EDT 2026.2 / Java 25.
2. Проверить разрешение target platform и наличие вкладок, ранее существовавших на этой ветке. Сохранить старую функциональность.
3. Создать/сохранить MCP-токен и запустить сервер на 8769. Нажать «Проверить»: реальный HTTP \`initialize\` + \`notifications/initialized\` + \`tools/list\`.
4. Подключить MCP-клиент, вызвать \`list_projects\` и read-only инструменты; отрицательные проверки: неверный токен, чужой Host/Origin, занятый порт, остановка EDT.
5. Проверить подтверждения \`request_*\` и отказ, не влияющий на Git, EDT, ИБ и хранилище. Проверку самого реального помещения выполнять **только с отдельным разрешением на тестовую копию**.

**Не запускать CI/тесты автоматически** на push/коммит. Сама реализация ещё не доказана сборкой и испытаниями.
