# MCP-сервер EDT Storage Bridge

**Ветка:** `feature/edt-2026.2-integration`. **Статус:** изменение исходников, **не проверено компиляцией и в установленной EDT 2026.2**. Нельзя считать автоматическое помещение проверенным для рабочего хранилища.

## Режимы не пересекаются

**Из EDT:** старые контекстные команды, подтверждения, редакторы сравнения и сообщения об ошибках остаются как были. Существующие публичные UI-входы используют прежние маршруты.

**Через MCP:** вызов инструмента уже содержит полномочие исполнить операцию; дополнительное подтверждение из окна EDT не требуется. Длительная работа запускается штатным Eclipse Job. Возвращённый `operationId` означает только **принятие запроса**. По нему вызывают `get_operation_status` до терминального состояния. Кнопки и ручные сценарии EDT этим не изменяются.

### MCP-инструменты

| Имя | Назначение |
|---|---|
| `list_projects` | Список открытых проектов EDT |
| `get_storage_status(project)` | Локальные OBSERVED/REVIEWED, Git-ветка и число PENDING (не онлайн-HEAD) |
| `get_pending_changes(project,offset?,limit?)` | Журнал PENDING, постранично (максимум 200) |
| `check_repository_revision(project)` | Текущий HEAD 1С из штатного отчёта без записи |
| `receive_changes(project)` | **Без диалогов** запускает `ReceiveMode.AUTOMATIC`: нативное получение 1С, EDT import, штатный headless compare/merge `GET_FROM_OTHER` без редактора |
| `publish_changes(project)` | **Без диалогов** запускает проверку Git/HEAD и существующую цепочку нативного headless EDT compare → штатный EDT export → подготовка Lock/Load/Commit |
| `get_operation_status(operationId)` | Состояние `queued/running/completed/failed/uncertain`, фаза, причина остановки; `completed` — терминальное состояние Job, а не подтверждение независимой проверки содержимого хранилища |

`receive_changes` принимает все входящие отличия, в том числе удаление объектов. Независимые локальные изменения могут быть заменены. Нужны чистая Git-ветка и штатные подтверждения целостности источника. Если по требованиям корректности потребуется полная XML-выгрузка, она возможна **без открытия окна сравнения**, не как выбор пользователя в EDT. При неизвестной версии, неполных данных, неудачном Merge или иной неоднозначности операция останавливается.

`publish_changes` **не** вызывает существующий интерактивный вариант помещения, даже если в настройках выбран «Ручное помещение через Конфигуратор». Для MCP используется автоматическая ветка — но проверки и квалификация тех же данных. Если HEAD отличается от REVIEWED, есть PENDING, нарушена Git/ИБ-проверка или не доказан точный состав объектов для записи, помещение запрещается. Агент должен сперва обновить проект отдельной командой, а не автоматически запускать бесконечную цепочку повторов.

После начала нативных Lock/Load/Commit ошибка может означать **неопределённое состояние**. В таком случае инструмент сообщает `uncertain` и запрещено слепо повторять помещение; требуется сверка захватов, состояния базы и хранилища.

### Ограничения реализации

- Автоматическое помещение в проекте пока **TEST-ONLY**. В действующем коде отсутствует независимая проверка фактически загруженного содержимого **после LOAD и до COMMIT**. Проверки HEAD, Git и состава XML этот пробел не устраняют.
- Признак `completed` при помещении фиксирует завершённый Designer COMMIT с кодом 0, **не** отдельное доказательство состава новой версии хранилища.
- Состояния MCP-операций хранятся в памяти запущенного EDT; после перезапуска `operationId` недоступен. Не путать с долговременными журналами самой 1С-операции.
- MCP не предоставляет самостоятельных `Lock`, `Load`, `UnLock`, произвольного запуска Designer, выполнения BSL и обхода проверки версии.
- При длительных операциях MCP-клиент должен опрашивать `get_operation_status`. Отсутствие ответа не означает успешное завершение и не разрешает повторную запись.

## Подключение

В диалоге **«Работа с хранилищем» → «MCP»**: порт, токен, «Запустить», «Остановить», «Проверить», «Создать новый токен», «Копировать MCP-конфигурацию». Сервер запускается вручную и останавливается при закрытии EDT. Endpoint только локальный: `http://127.0.0.1:8769/mcp`, токен в Eclipse Secure Storage, обязательный `Authorization: Bearer <token>`. Ограничены Host/Origin, размер сообщения и очередь. Порт 8769 не совпадает с существующими 8765/8768.

Формат примера, **не реальный токен**:

```json
{
  "mcpServers": {
    "edt-storage-bridge": {
      "type": "http",
      "url": "http://127.0.0.1:8769/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}
```

Реализован минимальный Streamable HTTP JSON-RPC: `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`. SSE, MCP ресурсы и prompts не реализованы.

## Проверки перед использованием

1. **Только по отдельному запросу пользователя**: собрать текущий HEAD ветки, проверить импорты Java/OSGi, вкладку и работоспособность сервера в EDT 2026.2.
2. Проверить вызов `receive_changes` на изолированных копиях проекта, ИБ-посредника и хранилища: без диалогов, с правильным результатом и с сохранением ручного режима EDT.
3. Для `publish_changes` сначала отрицательные кейсы: HEAD ушёл вперёд, PENDING, грязный Git, недостоверный XML, ошибка Lock/Load/Commit, неоднозначное состояние.
4. **Не выполнять пробную запись в рабочем хранилище.** Проверить на изолированных копиях post-LOAD результат, все виды метаданных, добавления и удаления, захваты, неизменённые объекты. Закрыть пробел независимой проверки содержимого до оценки готовности к промышленной записи.
5. Не включать автоматический запуск CI по push/commit. Не использовать пользовательский VPS и реальную ИБ без отдельного разрешения.
