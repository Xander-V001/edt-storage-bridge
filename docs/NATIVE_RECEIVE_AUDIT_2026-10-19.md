# Отчёт: аудит получения изменений из классического хранилища 1С

**Дата:** 2026-10-19  
**Ветка:** feature/edt-2026.2-integration  
**Цель:** существующий EDT 2026.2 проект с Git, одна существующая база-посредник, подключённая к классическому хранилищу 1С (не подключённая к EDT).  
**Статус:** изменения кода и тестов в GitHub; новой сборки, JUnit/Tycho и испытаний с EDT/ИБ не было. Рабочая готовность НЕ доказана.

## 1. Исправленные архитектурные ошибки

### Устранена двойная выгрузка

Прежде ChangedObjectsProbe.detectNative делал штатную 1С инкрементальную выгрузку + report изменений, но после получения report удалял XML. Затем ReceiveChangesCoordinator снова запускал Конфигуратор через SelectiveDumpRunner.export с самодельным -listFile. Повторный список сам добавлял владельцев/подчинённые ресурсы и мог не совпасть с фактическим платформенным патчем.

Теперь ChangedObjectsProbe.exportNative за ОДИН запуск Конфигуратора создаёт XML и список изменений. Объект NativeExport удерживает фактически сформированный платформой XML до окончания Merge EDT. ReceiveChangesCoordinator использует этот каталог напрямую, без повторного -listFile. Прежний SelectiveDumpPlanner больше не вызывается из входящего координатора.

### Удалён обход с изменением штатного XML

Раньше EdtRootXmlGuard временно перемещал папку Ext из выгрузки, чтобы выборочный XML был приемлем для импортёра EDT. Это меняло структуру штатного источника и могло скрывать контент.

Теперь EdtSelectiveReviewService передаёт импортёру EDT тот же XML без сокрытия файлов. EdtRootXmlGuard.java и его тест удалены. Если импортёр не может преобразовать частичный источник, пользователь может явно подтвердить ПОЛНУЮ выгрузку для глобального EDT-сравнения или отменить без списания pending. Автоматической корректировки XML нет.

### Исправлено безусловное списание всех ожидающих объектов

Раньше MERGE_PROCESS_FINISHED плюс подтверждение источника приводили к снятию ВСЕХ pending-идентификаторов, попавших в область EDT-сравнения. Это неверно, если разработчик оставил локальный код.

Теперь завершение штатного Merge — необходимое, но НЕ достаточное условие. VerifiedReceiveContent.verifyAndClear сверяет итоговое содержимое рабочей EDT модели с временной платформенной моделью и снимает только подтверждённые записи. Намеренно сохранённые локальные различия не объявляются автоматически принятыми. Отчёт перечисляет неразобранные изменения.

### Исправлена обработка удалений

Полное сравнение раньше добавляло только существующие имена из текущего снимка и могло потерять информацию об исчезнувших объектах. RemoteReceiveScopePlanner.fullInventory(previous,current) теперь сохраняет исчезнувшие имена, используя лишь ДВА исходных платформенных набора имён, без анализа внутренних version-токенов.

Удаление вложенной формы/модуля подтверждается только если итоговый владелец совпал с правой EDT-моделью (либо доказано удаление владельца целиком). Верхнеуровневое удаление требует фактического отсутствия объекта в обоих источниках.

### Штатный FullDump — отдельное решение

Если native -getChanges вернул FullDump, выборочный XML не объявляется достаточным; импортируется отдельный полный XML после подтверждения. Отсутствие версии в неполном выходе FullDump само по себе не ошибочно. Конфигурация базы-посредника повторно из хранилища не обновляется.

## 2. Текущий маршрут получения

1. Проверка EDT-проекта и Git-ветки, отдельные блокировки для конкретной базы-посредника и проекта.
2. Перед подтверждённым обновлением базы-посредника из классического хранилища сохраняется контрольный снимок. Числовой native HEAD проверяется отдельно.
3. 1С формирует ConfigDumpInfo.xml штатным /DumpConfigToFiles ... -configDumpInfoOnly. Java НЕ создаёт и НЕ редактирует этот XML.
4. Если есть исходный native ConfigDumpInfo.xml, ОДИН native вызов:
   DESIGNER /DumpConfigToFiles <EMPTY_OUTPUT> -update -configDumpInfoForChanges <NATIVE_BASELINE> -getChanges <REPORT>.
   Выходом являются и XML-патч, и список New/Modified. Параметры приведены к документированному порядку 1С.
5. 1С сама определяет изменения. Java читает точные имена из отчёта. Два platform-native индекса имён дополнительно позволяют заметить исчезнувшие объекты, что не является самостоятельным пересчётом изменений по id/configVersion.
6. Временный XML без исправлений передаётся штатному IImportService.work EDT и штатному редактору сравнения/объединения. Git checkout/reset, создание ИБ, технических веток, прямое копирование кода в рабочий проект запрещены и не выполняются.
7. При FullDump, удалениях, прежних неразрешённых pending, первом получении либо неподдерживаемой частичной структуре используется полная выгрузка только по подтверждению. Это не означает новую команду получения изменений в базу.
8. После терминального результата EDT фактически проверяется принятый контент. Ожидающие записи не списываются по факту закрытия окна, наличия галочек или начатого асинхронного Merge.
9. Подтверждённый numeric HEAD и факт применённого в EDT контента ведутся отдельно, не подменяя друг друга.

### Проверка неизменности базы без ложного сравнения XML-патча

Платформа имеет право сформировать ConfigDumpInfo.xml внутри инкрементального XML-патча с составом, отличающимся от полного снимка конфигурации. Поэтому координатор больше **не сравнивает индекс патча с полным ConfigDumpInfo**. Вместо этого Конфигуратор отдельно формирует read-only полные снимки версий до и после команды выгрузки изменений. Проверка неизменности базы сравнивает исключительно эти два штатных полных снимка, без собственной генерации или подмены версий. Дополнительное чтение версий может увеличивать время получения; оно не является повторной полной XML-выгрузкой.

## 3. Главное оставшееся ограничение

VerifiedReceiveContent сейчас требует строгого совпадения файлов/деревьев для части проверок. EDT может иначе сериализовать одинаковый по смыслу XML/BSL, а разработчик может намеренно сохранить локальный вариант. Тогда некоторые pending останутся, хотя человек рассмотрел их в EDT. Это БЕЗОПАСНЕЕ ложного утверждения «всё принято», но не даёт требуемой безупречной семантики «рассмотрел, но оставил своё». Для неё нужно подтверждённое документированное свидетельство native EDT о решениях по каждому изменению; такой механизм пока не доказан на EDT 2026.2.

Прямой инкрементальный XML может не содержать первичный .mdo владельца. Совместимость такого патча с IImportService.work без дополнительных преобразований не доказана испытаниями. При отказе импортёра пользователь выбирает полный режим или отмену. Поэтому ускорение пока НЕ ДОКАЗАНО. После выпуска возможен частый переход на полное сравнение, что должно считаться неисправностью критического пути и исследоваться по native диагностике, а не скрываться.

Старые две «ожидающие записи» со скриншота нельзя идентифицировать по их количеству. Их реальные имена хранятся отдельно и не должны удаляться без проверки. Старые артефакты предыдущего синтетического pending не мигрируются автоматически: это небезопасно.

## 4. Файлы и тесты

Изменены:
- ChangedObjectsProbe.java — единый вызов 1С, NativeExport сохраняет штатный XML.
- ReceiveChangesCoordinator.java — прямой native источник, отдельное подтверждение глобального сравнения, проверяемое списание, безопасная жизнь временных файлов.
- EdtSelectiveReviewService.java — никакого скрытия каталогов Ext.
- VerifiedReceiveContent.java — обработка удалённых вложенных объектов при фактическом совпадении родителя.
- RemoteReceiveScopePlanner.java — в полном режиме сохранение исчезнувших native имён.

Удалены: EdtRootXmlGuard.java и EdtRootXmlGuardTest.java как ненужный обход.

Добавлены/обновлены регрессионные тесты:
- ChangedObjectsProbeNativeTest — lifecycle родного XML-патча.
- ChangeDetectionCommandTest — корректная последовательность native аргументов, без -listFile.
- RemoteReceiveScopePlannerTest — удалённые имена при полном режиме.
- EdtOwnerContentVerifierTest — проверка удаления вложенной формы без потери других данных.

Не запускались никакие сборки, CI, unit-tests, рабочие ИБ или VPS. Пакет P2 не опубликован; установленная версия EDT не содержит эти новые изменения.

## 5. Обязательные проверки перед объявлением готовности

1. Разрешённая пользователем сборка Tycho под EDT 2026.2 и все JUnit.
2. Изолированное полное первоначальное получение с подтверждённым ConfigDumpInfo.xml/HEAD.
3. Небольшое изменение только ManagerModule: одна инкрементальная команда и реальное применение в EDT без полной выгрузки.
4. Проверка форм, модулей, шаблонов, изображений, языка/корня конфигурации и FullDump.
5. Локально закоммиченный Документ1: возможность сохранить собственный код и принять остальные изменения без повреждения Git.
6. Удаления/переименования, частичный Merge, отмена, сбой 1С, восстановление, изменение HEAD во время Merge.
7. Проверка семантического результата EDT, а не только побайтового равенства. Измерение времени на большой конфигурации.

Пока эти проверки не выполнены, фраза «рабочий плагин полностью готов» будет недостоверной.
