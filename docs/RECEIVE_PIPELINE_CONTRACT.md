# Получение изменений из классического хранилища 1С — действующий контракт

**Актуально для кода ветки `feature/edt-2026.2-integration`, `4fab919` от 21.10.2026 (до документальных изменений).** Новый учёт решений Merge в установленной EDT ещё не подтверждён. Редактировать этот текст только вместе с проверкой `ReceiveChangesCoordinator` и реальных логов.

## Входы, ограничения и участники

1. Существующее классическое хранилище 1С и настоящая версия его HEAD из `/ConfigurationRepositoryReport -NBegin -1`.
2. Существующая ИБ-посредник, уже привязанная к хранилищу; она **не является** одной из ИБ, подключённых к проекту EDT. Только здесь Конфигуратор может обновить конфигурацию.
3. **Существующий** проект EDT 2026.2 с собственным локальным Git. Плагин не создаёт новую ИБ/проект/worktree/служебную ветку, не выполняет checkout/reset/rebase и не коммитит пользовательские изменения.
4. Настройки хранилища и учётные данные ИБ — разные сущности. Время/адреса/логины задаются в `StorageProjectSettings`. Секреты не попадать в logs.

## Быстрое «Получить изменения» — реализованная последовательность [КОД]

1. `StorageSettingsDialog` запускает `ReceiveChangesCoordinator.receive(..., INCREMENTAL)`. `GitReceiveGuard` подтверждает допустимое состояние текущей ветки/коммита, ставится блокировка проекта/посредника. Состояние предыдущей операции проверяется в `ReceiveBaselineJournal`.
2. Если есть уже учтённый `PENDING`, пользователь видит выбор: новая выгрузка актуальных изменений либо повторная обработка сохранённого источника **при доказанном совпадении версии**. Режим повтора не должен повторять `RepositoryUpdateCfg` только ради уже известного pending.
3. Перед обновлением сохраняется **нативный полный** `ConfigDumpInfo.xml` конфигурации базы через `ConfigVersionSnapshotRunner.capture` с `-configDumpInfoOnly`. Это индекс ИБ, **не список дельты** и **не** ревизия хранилища.
4. По явному согласию `RepositoryUpdateRunner.receive` выполняет `/ConfigurationRepositoryUpdateCfg` в **ИБ-посреднике**. Штатное обновление может менять всю конфигурацию посредника; это **не полное копирование в EDT**. До native действия сохраняется фаза; при неизвестном результате нельзя вслепую повторить Update.
5. После обновления снова создаётся полный штатный `ConfigDumpInfo.xml`. Читается версия хранилища; изменение HEAD во время обмена запрещает поднимать REVISION и применять неподтверждённый снимок.
6. Если есть предыдущий достоверный полный индекс, `ChangedObjectsProbe.exportNative` запускает **одну нативную** выгрузку:
   ```text
   1cv8 DESIGNER /DumpConfigToFiles <empty-patch-dir>
       -update
       -configDumpInfoForChanges <last-scanned-ConfigDumpInfo.xml>
       -getChanges <changes.txt>
   ```
   Эти параметры принадлежат выгрузке XML; они не выполняют `ConfigurationRepositoryUpdateCfg`. Отчёт `changes.txt` даёт имена объектов/состояния `New`, `Modified` или `FullDump`; Java **не вычисляет** самостоятельную дельту по числам `id/configVersion`. Сравнение множеств двух **полных** штатных индексов дополнительно обнаруживает исчезновение имён.
7. `RemoteReceiveScopePlanner.reconcileNative` определяет точные идентификаторы; `ReceivePendingStore.add` сохраняет **только реальные поступившие изменения**, а не всю опись конфигурации. `ReceiveBaselineJournal` сохраняет полный индекс и версионное подтверждение только при совпадающем HEAD.
8. Для выборочного импорта EDT используется фактически подготовленный платформой XML-патч с возможной **контролируемой довыгрузкой зависимых объектов** `SelectiveDumpPlanner.supplementsForNativePatch`, `SelectiveDumpRunner.supplement/completeNativeRoot`. При replay накопленного PENDING может использоваться отдельная `-listFile`-выгрузка; **не** повторное обновление ИБ. Файлы сохраняются вне рабочего проекта и Git. Не утверждать, что абсолютно каждый вызов обходится одним процессом Designer: есть отдельные индексные проверки, дозагрузка и версии.
9. `IImportService.work(project, xml, externalTarget, monitor)` через `EdtSelectiveReviewService.prepare` преобразует XML во временную EDT-модель. `ComparisonScope` создаётся **только для выбранных владельцев**, без самостоятельного изменения активного проекта. Список неподдерживаемых/отсутствующих корневых объектов — ошибка подготовки, а не основание молча расширить область.
10. В SWT открывается **штатный** редактор двухстороннего сравнения EDT. `NativeEdtMergeWitness` слушает жизненный цикл асинхронного Merge через `IComparisonManager`: закрытие окна, запуск сравнения и `IStatus.OK` предварительной операции не доказывают завершение Merge.
11. После подтверждённого native Merge проверяются Git, native HEAD, полнота выбранного источника и неизменность посредника. В выборочном режиме `NativeEdtMergeWitness.classifyPending` использует наблюдённые штатные решения EDT. `ReceiveCompletionRecorder.reviewedNativeObserved` фиксирует `accepted/keptLocal/unclassified` по идентификаторам изменений 1С и поднимает `REVIEWED`; после записи результатов очищает обработанные `PENDING`. `APPLIED` этот путь не повышает. Новая ветка классификации пока [КОД], но не [ОПЫТ].
12. Исходящие файлы, промежуточные каталоги и снимки удаляются/сохраняются с учётом живой асинхронной операции. Если статус Merge неизвестен, нельзя преждевременно освободить staging или отмечать состояние завершённым.

**Важная текущая оговорка:** исходящий `SelectiveReceiveStagingService`/старый `SelectiveDumpPlanner` существуют как вспомогательные классы и тесты. Не путать их с главным маршрутом `ReceiveChangesCoordinator` и не описывать старый самодельный двойной экспорт как обязательное действие.

## «Полная сверка с хранилищем» — отдельный маршрут [КОД]

- Пункт контекстного меню `FullStorageReviewHandler` и кнопка диалога выбирают `ReceiveMode.FULL_REVIEW`.
- После явного решения об обновлении посредника снимается **полный native inventory**; для глобального сравнения выполняется отдельно `SelectiveDumpRunner.exportInitialFull` / `InitialFullDumpCommand` → штатная полная `/DumpConfigToFiles`.
- `EdtSelectiveReviewService.prepare(... initialFullReview=true)` использует **полный** импорт во временный источник и `ComparisonScope.EMPTY_SCOPE`, чтобы сама EDT сравнила **всю конфигурацию**, в том числе добавленные, изменённые, отсутствующие локально объекты/ресурсы.
- Это **не** тихая альтернатива быстрому пути: пользователь выбирает глобальную сверку. При `FullDump`, несовместимом/неполном XML-патче или неполном выборочном scope координатор может **предложить** полный путь, но не делать неявное применение.
- Full-review не должен добавлять в `PENDING` каждый объект из полного `ConfigDumpInfo.xml`. Если native Merge закончен и доказана полнота source, может фиксироваться `REVIEWED`; `APPLIED` отдельно и строже.

## Статусы и неизменные правила

| Термин | Значение и достоверный источник |
|---|---|
| `OBSERVED` | Нативный HEAD классического хранилища из отчёта Designer; не доказывает применение |
| `SCANNED` | Полная опись посредника и (при attestation) связанная с ней числовая ревизия |
| `PENDING` | Точные изменения из нативной дельты/подтверждённых удалений, ожидающие рассмотрения |
| `REVIEWED` | Входящие изменения данной версии **разобраны** разработчиком, даже при сознательно сохранённых локальных вариантах |
| `APPLIED` | Более сильная отметка: **строго доказанная** полнота фактического применения; не равно REVIEWED |
| `KEPT_LOCAL` | Отмеченное наблюдателем решение оставить локальную реализацию на реально отличающемся узле EDT; хранится по native идентификатору изменения 1С |
| `Git HEAD` | Состояние локального Git проекта EDT; не равно числовой ревизии |
| `ConfigDumpInfo id/configVersion` | Непрозрачные свойства объекта в полном индексе, не номер хранилища |
| `UNKNOWN` (внутреннее) | Не удалось классифицировать наблюдённый выбор. Не означает отказ EDT принять изменение |

Классы: `ReceiveBaselineJournal` (снимки/попытки), `ReceivePendingStore`, `ReceiveRevisionStore`, `ReceiveCompletionRecorder`, `ReceiveStateMaintenance`, `VerifiedReceiveContent` (вспомогательная проверка содержимого, **не** замена штатного решения EDT). UI может исторически показывать REVIEWED в поле «версия, применённая...» — различать внутреннюю семантику от старой подписи.

## Сбои, которые необходимо понимать и не «обходить»

- **Пустой `changes.txt` без `ConfigDumpInfo.xml`:** это не полноценный патч. `ChangedObjectsProbe.validateNativeStage` различает `FullDump`, пустую дельту и отсутствие манифеста; `ReceiveChangesCoordinator` вправе признать «нет изменений» только при дополнительных независимых проверках двух *полных* native индексов и HEAD. Нельзя создать фальшивый manifest или считать exit=0 достаточным.
- **Непустые изменения и неполный XML:** сохраняются диагностические данные/имена; не подменять missing XML произвольной загрузкой или потерей PENDING. Возможна дозагрузка по штатному `-listFile`, но без циклических повторов.
- **Частичный EDT импорт ошибочен:** `NativeEdtImportFailure` сохраняет дерево `IStatus` в локальном файле. Не изменять платформенный XML, выкидывая `Ext`, и не расширять сравнение без решения пользователя.
- **Конкурентная новая ревизия хранилища:** HEAD до и после должен совпадать с подтверждённым источником; иначе journal/PENDING остаются, REVIEWED/APPLIED не присваиваются.
- **Git изменился при Merge:** не переписывать Git; `GitReceiveGuard.requireSafePostMergeGit` различает подтверждённый сценарий и недостоверное изменение ветки/индекса.
- **Отмена, прерывание, зависший Merge:** фазовый журнал и блокировки предотвращают слепой native UPDATE и раннее списание ожиданий.
- **Большая полная опись (десятки тысяч):** ни одно полное множество имён не должно превращаться в десятки тысяч фиктивных PENDING. Байтовые отличия форм/.mdo/.distr не равны решению оставить локальное.

## Граница заимствованной идеи 1С:ГитКонвертера

Проект 1С:ГитКонвертер ([README](https://github.com/1C-Company/GitConverter/blob/master/README.md)) применяет нативный инкрементальный экспорт классического хранилища в Git/EDT; он **односторонний**. Плагин использует этот принцип, но **не** интегрирует код ГитКонвертера и **не** создаёт/не обслуживает Git-историю хранилища. Вместо неё — временный EDT импорт и штатный Merge в пользовательский проект.

## Наблюдатель выбора штатного EDT Merge [КОД]

- `NativeEdtMergeChoiceObserver` подписывается на события нативного дерева сравнения `IComparisonSession`, читает ID узлов, их `MergeSettings` и владельцев через read-only BM task. Только узлы с `hasDiffsMainOther()` считаются реальными отличиями; неизменённый `DoNotMerge` не трактуется как отказ.
- После успешного native Merge `Snapshot.classifyPending` группирует по native идентификаторам изменений 1С: все подходящие `[x] GetFromOther` → accepted; изменённый `[ ]` / `DoNotMerge` / `nestedExcluded` → keptLocal; отсутствие узлов или иные правила → unclassified.
- `ReceivePendingStore.acknowledgeNativeObservedChoices` записывает решение перед удалением `PENDING`; `REVIEWED` фиксируется после прежних проверок Git/HEAD/ИБ. `APPLIED` не повышается. Нет побайтовой сверки файлов EDT. Повторный список выбора `chooseKeptLocalOnUi` отключён, временное окно событий наблюдателя — тоже.
- Старые `unknown-choice-*` не архивируются и не объявляются принятыми после полного Merge. В Error Log остаётся техническая диагностика. В обычном окне — факт native Merge, оставшиеся ожидания и обработанная версия.

**Важно о следующем получении.** Новый `-getChanges` вычисляет *новую* native-дельту относительно сохранённого полного `ConfigDumpInfo`. Старый `KEPT_LOCAL` **не добавляется автоматически в область выборочного сравнения**. Пока хранилище снова не изменило этот объект, быстрый приём может вообще его не показывать. При новой ревизии объекта EDT сравнит актуальный локальный проект с новым источником; **явная полная сверка** сравнит все объекты независимо от старой дельты. При этом решения `KEPT_LOCAL` не читаются и исходящим помещением.

**Ограничение точности:** EDT наблюдает узлы до процедуры, но `ReceivePendingStore` хранит решения по идентификаторам 1С, не по процедурам; несколько вложенных объектов одного верхнего владельца могут быть сопоставлены нераздельно. Новая запись observer → journal из `4fab919` ещё не испытана в установленной EDT. Конкретный прежний тест: версии 29453/29454, две принятые процедуры `ПрочийДоход`, старый путь сохранил две `UNKNOWN`; это не подтверждение и не опровержение новой классификации.
