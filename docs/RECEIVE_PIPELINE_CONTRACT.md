# EDT Storage Bridge — единый контракт получения изменений

Дата: 2026-10-20. Это обязательная схема выполнения **только получения** в EDT
2026.2 из существующего классического хранилища через существующую
подключённую к хранилищу базу-посредник. Это не API синхронизации ИБ EDT.
Этот документ описывает ТРЕБОВАНИЯ и изменённую реализацию, но **не**
удостоверяет её работу в установленной EDT без отдельного теста.

## 1. Данные — четыре независимых сущности

| Данные | Значение | Источник и правило |
| --- | --- | --- |
| `OBSERVED` | последний прочитанный HEAD хранилища | Только штатный отчёт 1С; никогда не означает, что EDT обновлена |
| `SCANNED` | версия + SHA-256 точного снимка базы-посредника | Фиксируется после обновления 1С, но НЕ означает Merge/принятие |
| `PENDING` | конкретные ещё не подтверждённые изменения | Только реальная дельта 1С и доказанные удаления; полный список метаданных НЕ является дельтой |
| `REVIEWED` / `APPLIED` | рассмотрена разработчиком / все входящие изменения строго проверены | Записываются исключительно после завершённого Merge, проверки исходника и ветки, чтения результата и при необходимости подтверждения |

Сохранённые записи относятся строго к проекту, классическому хранилищу,
базе-посреднику и Git-ветке. История Git пользователя не равна ревизиям 1С.

## 2. Последовательность

1. **Preflight:** валидировать настройки, ветку/HEAD Git, отсутствие
   незакоммиченного состояния до старта. Проверить журнал прерванного
   запуска. Не изменять Git и другие ИБ EDT.
2. **Источник:** новый запуск «Получить изменения» или «Полная сверка»
   запрашивает текущий HEAD 1С, с разрешения пользователя обновляет
   базу-посредник и читает полный ConfigDumpInfo. Старое сравнение —
   отдельное явное действие; его нельзя выдавать за обновление до HEAD.
3. **Изменения:** при предыдущем достоверном снимке список изменений
   и XML-патч предоставляет штатный `-getChanges` 1С. Отсутствующие
   имена обнаруживаются по двум ПОЛНЫМ штатным ConfigDumpInfo.
   При первой полной сверке точной предыдущей дельты нет: сравнить
   всю конфигурацию, не заносить тысячи объектов в PENDING.
4. **Аттестация:** прочитать HEAD ещё раз. Если до/после обновления
   подтверждённо разные положительные версии, остановиться ДО Merge
   EDT. Не выдавать старую базу за обновление до нового HEAD.
   При неизвестном HEAD разрешать только консервативное сравнение
   содержимого без фиксации версии.
5. **Подготовка:** создать временный источник EDT ВНЕ Git пользователя
   из штатной выгрузки 1С. В первую очередь выборочная выгрузка;
   полную только при первичном, явном или необходимом глобальном сравнении.
6. **Merge:** открыть штатный EDT compare/merge. Разработчик выбирает
   содержимое. Закрытие редактора, незакоммиченные файлы и появление
   журнала — не доказательство нажатия «Объединить».
   Дождаться собственного терминального события Merge EDT.
7. **Проверка:** после завершения проверить: сохранение Git-ветки и
   непрерывности истории, HEAD хранилища, точный временный источник,
   реально полученные файлы EDT и те имена, которые вообще вошли
   в сравнение. Этот шаг ТОЛЬКО ЧИТАЕТ журнал PENDING.
8. **Единственный commit результата:**
   - FULLY_APPLIED: проверена вся конфигурация, не только XML-патч;
     нет необработанных входящих изменений, все проверенные владельцы
     совпали с источником, проверка не была пустой; записать REVIEWED
     и APPLIED после верификации;
   - REVIEWED_EXACT_SCOPE: при выборочной проверке все фактически
     представленные входящие изменения совпали с источником. Записать
     REVIEWED, но **никогда** не записывать APPLIED как результат
     одного лишь выборочного сравнения;
   - REVIEWED_WITH_LOCAL: все оставшиеся имена присутствовали
     в сравнении, пользователь явно подтвердил сохранение локальных
     отличий; удалить только явные имена, записать REVIEWED, но
     не записывать APPLIED;
   - PARTIAL: списать только точно проверенные имена, не менять
     полный номер обработанной версии;
   - UNPROVEN_SOURCE: номер исходной ревизии не доказан или изменился
     HEAD во время проверки. Не менять ни номера версий, ни PENDING,
     даже если содержимое совпало с устаревшим временным источником;
   - AUDIT_INCOMPLETE: EDT не предоставила ни одного проверяемого
     владельца, «0/0 совпало» не считается успехом;
   - NOT_MERGED/ABORTED: никаких подтверждений Merge.
9. **Завершение:** понятный результат: HEAD, источник, что реально
   рассмотрено, что осталось, какие отличия намеренно сохранены.
   Временному сравнению нельзя приписывать новую версию из журнала.

## 3. Необходимые гарантии

- Нет повторного запуска `/ConfigurationRepositoryUpdateCfg` из обработчика
  результата EDT, даже если запись версии не удалась.
- Журнал `SCANNED` обновляется отдельно от `REVIEWED`/`APPLIED`.
  Повторное сравнение старого снимка не меняет его номер на новый HEAD.
- Если Git-ветка переключилась или история переписана, завершающая
  отметка блокируется; изменение обычных файлов после Merge допустимо.
  Новый коммит в той же ветке допустим только с доказанной непрерывной
  историей; во время собственно аудита HEAD должен быть стабилен.
- Ошибка после Merge никогда не откатывает изменения EDT автоматически
  и никогда не заставляет повторно применять их вслепую.
- При сбое записи журнал остаётся консервативным: можно сохранить
  недоотмеченную операцию и потребовать повторной проверки; запрещено
  выдавать неразобранное за успешно применённое.
- Управляемый сброс истории создаёт резервную копию и не затрагивает
  Git, другие проекты, Secure Storage и существующую 1С-базу.

## 4. Приёмочные проверки перед словом «работает»

1. Чистый EDT на 29432 → хранилище 29434 → только реальные изменённые
   объекты → успешный Merge → REVIEWED 29434; APPLIED 29434 только при
   строгом принятии.
2. В локальном Git уже закоммичен свой Документ1; хранилище меняет
   тот же Документ1 и другой объект. Сохранить локальную версию первого,
   принять второй, не потерять коммит и не создать ложный APPLIED.
3. Первый полный проход большой конфигурации не создаёт 23 408
   фиктивных ожидающих изменений.
4. Отмена в EDT, ошибка конвертации, таймаут, смена ветки, reset/rebase
   во время Merge, новая версия 1С во время получения и после него.
5. Падение EDT до/после записи каждого контрольного состояния.
   Повторный запуск НЕ обновляет посредника второй раз без
   установленного исходного состояния и явного подтверждения.
6. Возврат исходного состояния после ручного/штатного архивного сброса.
   Нельзя автоматически восстанавливать прежнюю версию из мусора.
7. Сборка EDT 2026.2 (Java 25, Eclipse 2025-12), чистая установка,
   smoke-test на отдельном разрешённом тестовом проекте.

**Статус на момент написания:** source-level правки закоммичены,
регрессионные тесты добавлены. Сборка/CI и реальный тест EDT не
проводились без явного разрешения.

## 5. Результаты повторного статического аудита — 2026-10-20

После объединения кода обнаружены и исправлены:
1. Выборочный Merge мог ложно записать глобальный `APPLIED`: теперь
   выборочная полная приёмка имеет только `REVIEWED_EXACT_SCOPE`.
2. Если HEAD хранилища становился недоказанным, прежний код всё ещё
   списывал точно совпавшие объекты по потенциально старому источнику.
   Теперь `UNPROVEN_SOURCE` ничего не подтверждает.
3. Пустой аудит 0/0 мог считаться полным успехом. В контракт введён
   `AUDIT_INCOMPLETE`, запись версии запрещена.
4. Пакетное `clearVerified` раньше могло удалить часть PENDING до
   обнаружения некорректной записи. Теперь все записи предварительно
   проверяются перед первым изменением.

**Открытый риск, НЕ объявлять закрытым:** отдельные Eclipse Preferences
для PENDING и REVIEWS/APPLIED не образуют одну атомарную транзакцию.
Сбой между их `flush()` может оставить частично списанный журнал и
неподтверждённую версию. Консервативные проверки уменьшают риск, но не
дают полноценного crash recovery. Для релиза нужна отдельная
восстанавливаемая операция фиксации или атомарное хранение контрольного
состояния с испытаниями падения в каждой точке.

**Контроль полноты конвертации:** теперь глобальное сравнение
сопоставляет каждое отображаемое штатное имя из полного
`ConfigDumpInfo.xml` (плюс отдельно известные непроиндексированные
имена) с верхнеуровневыми дескрипторами временного EDT-проекта.
Неизвестные типы и пропущенные владельцы приводят к `SOURCE_INCOMPLETE`:
не подтверждается ни `REVIEWED`, ни `APPLIED`. Это улучшает безопасность,
но всё ещё не доказывает корректность каждой вложенной формы или бинарного
ресурса, преобразованного импортёром EDT. Полнота таких преобразований
должна проверяться отдельными интеграционными испытаниями.

Ни сборка, ни тесты в EDT 2026.2 по этим новым коммитам не запускались.
