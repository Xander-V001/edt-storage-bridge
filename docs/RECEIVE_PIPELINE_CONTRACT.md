# EDT Storage Bridge — единый контракт получения изменений

Дата: 2026-10-20. Это обязательная схема выполнения **только получения** в EDT
2026.2 из существующего классического хранилища через существующую
подключённую к хранилищу базу-посредник. Это не API синхронизации ИБ EDT.
Этот документ описывает ТРЕБОВАНИЯ и изменённую реализацию, но **не**
удостоверяет её работу в установленной EDT без отдельного теста.

## 1. Данные — четыре независимых сущности

| Данные | Значение | Источник и правило |
| --- | --- | --- |
| `OBSERVED` | последний прочитанный HEAD хранилища | Только штатный отчёт 1С; никогда не означает, что EDT обновлена |
| `SCANNED` | версия + SHA-256 точного снимка базы-посредника | Фиксируется после обновления 1С, но НЕ означает Merge/принятие |
| `PENDING` | конкретные ещё не подтверждённые изменения | Только реальная дельта 1С и доказанные удаления; полный список метаданных НЕ является дельтой |
| `KEPT_LOCAL` | просмотренные изменения хранилища, для которых разработчик сознательно сохранил локальный результат | Отдельные сохранённые имена; не превращаются обратно в PENDING без новой дельты и не позволяют объявлять APPLIED |
| `REVIEWED` / `APPLIED` | рассмотрена разработчиком / все входящие изменения строго проверены | Записываются исключительно после завершённого Merge, проверки исходника и ветки, чтения результата и при необходимости подтверждения |

Сохранённые записи относятся строго к проекту, классическому хранилищу,
базе-посреднику и Git-ветке. История Git пользователя не равна ревизиям 1С.

## 2. Последовательность

1. **Preflight:** валидировать настройки, ветку/HEAD Git, отсутствие
   незакоммиченного состояния до старта. Проверить журнал прерванного
   запуска. Не изменять Git и другие ИБ EDT.
2. **Источник:** новый запуск «Получить изменения» или «Полная сверка»
   запрашивает текущий HEAD 1С, с разрешения пользователя обновляет
   базу-посредник и читает полный ConfigDumpInfo. Старое сравнение —
   отдельное явное действие; его нельзя выдавать за обновление до HEAD.
3. **Изменения:** при предыдущем достоверном снимке список изменений
   и XML-патч предоставляет штатный `-getChanges` 1С. Отсутствующие
   имена обнаруживаются по двум ПОЛНЫМ штатным ConfigDumpInfo.
   При первой полной сверке точной предыдущей дельты нет: сравнить
   всю конфигурацию, не заносить тысячи объектов в PENDING.
4. **Аттестация:** прочитать HEAD ещё раз. Если до/после обновления
   подтверждённо разные положительные версии, остановиться ДО Merge
   EDT. Не выдавать старую базу за обновление до нового HEAD.
   При неизвестном HEAD разрешать только консервативное сравнение
   содержимого без фиксации версии.
5. **Подготовка:** создать временный источник EDT ВНЕ Git пользователя
   из штатной выгрузки 1С. В первую очередь выборочная выгрузка;
   полную только при первичном, явном или необходимом глобальном сравнении.
6. **Merge:** открыть штатный EDT compare/merge. Разработчик выбирает
   содержимое. Закрытие редактора, незакоммиченные файлы и появление
   журнала — не доказательство нажатия «Объединить».
   Дождаться собственного терминального события Merge EDT.
7. **Проверка:** после завершения проверить: сохранение Git-ветки и
   непрерывности истории, HEAD хранилища, точный временный источник,
   реально полученные файлы EDT и те имена, которые вообще вошли
   в сравнение. Этот шаг ТОЛЬКО ЧИТАЕТ журнал PENDING.
8. **Единственный commit результата:**
   - FULLY_APPLIED: проверена вся конфигурация, не только XML-патч;
     нет необработанных входящих изменений, все проверенные владельцы
     совпали с источником, проверка не была пустой; записать REVIEWED
     и APPLIED после верификации;
   - REVIEWED_EXACT_SCOPE: при выборочной проверке все фактически
     представленные входящие изменения совпали с источником. Записать
     REVIEWED, но **никогда** не записывать APPLIED как результат
     одного лишь выборочного сравнения;
   - REVIEWED_WITH_LOCAL: все оставшиеся имена присутствовали
     в сравнении, пользователь явно подтвердил сохранение локальных
     отличий; перенести проверенные имена из PENDING в KEPT_LOCAL,
     записать REVIEWED, но не записывать APPLIED.
     При следующем получении эти решения видны отдельно, но не
     вызывают постоянный повтор полного сравнения;
   - PARTIAL: списать только точно проверенные имена, не менять
     полный номер обработанной версии;
   - UNPROVEN_SOURCE: номер исходной ревизии не доказан или изменился
     HEAD во время проверки. Не менять ни номера версий, ни PENDING,
     даже если содержимое совпало с устаревшим временным источником;
   - AUDIT_INCOMPLETE: EDT не предоставила ни одного проверяемого
     владельца, «0/0 совпало» не считается успехом;
   - NOT_MERGED/ABORTED: никаких подтверждений Merge.
9. **Завершение:** понятный результат: HEAD, источник, что реально
   рассмотрено, что осталось, какие отличия намеренно сохранены.
   Временному сравнению нельзя приписывать новую версию из журнала.

## 3. Необходимые гарантии

- Нет повторного запуска `/ConfigurationRepositoryUpdateCfg` из обработчика
  результата EDT, даже если запись версии не удалась.
- При очередной версии хранилища без изменений объектов штатный
  `-getChanges` может вернуть пустой список. Тогда REVIEWED можно
  продвинуть без EDT Merge **только** если предыдущий SCANNED был
  полностью рассмотрен на той же ветке, не осталось PENDING, native
  дельта действительно пуста, HEAD подтверждён до/после Designer и
  повторно перед записью. Это не даёт права повышать APPLIED.
- Принятые штатные изменения могут удалить прежнюю запись KEPT_LOCAL
  по этому имени. Доказанное глобальное совпадение конфигурации удаляет
  все прежние KEPT_LOCAL данного проекта/ветки.
- Журнал `SCANNED` обновляется отдельно от `REVIEWED`/`APPLIED`.
  Повторное сравнение старого снимка не меняет его номер на новый HEAD.
- Если Git-ветка переключилась или история переписана, завершающая
  отметка блокируется; изменение обычных файлов после Merge допустимо.
  Новый коммит в той же ветке допустим только с доказанной непрерывной
  историей; во время собственно аудита HEAD должен быть стабилен.
- Ошибка после Merge никогда не откатывает изменения EDT автоматически
  и никогда не заставляет повторно применять их вслепую.
- При сбое записи журнал остаётся консервативным: можно сохранить
  недоотмеченную операцию и потребовать повторной проверки; запрещено
  выдавать неразобранное за успешно применённое.
- Управляемый сброс истории создаёт резервную копию и не затрагивает
  Git, другие проекты, Secure Storage и существующую 1С-базу.

## 4. Приёмочные проверки перед словом «работает»

1. Чистый EDT на 29432 → хранилище 29434 → только реальные изменённые
   объекты → успешный Merge → REVIEWED 29434; APPLIED 29434 только при
   строгом принятии.
2. В локальном Git уже закоммичен свой Документ1; хранилище меняет
   тот же Документ1 и другой объект. Сохранить локальную версию первого,
   принять второй, не потерять коммит и не создать ложный APPLIED.
3. Первый полный проход большой конфигурации не создаёт 23 408
   фиктивных ожидающих изменений.
4. Отмена в EDT, ошибка конвертации, таймаут, смена ветки, reset/rebase
   во время Merge, новая версия 1С во время получения и после него.
5. Падение EDT до/после записи каждого контрольного состояния.
   Повторный запуск НЕ обновляет посредника второй раз без
   установленного исходного состояния и явного подтверждения.
6. Возврат исходного состояния после ручного/штатного архивного сброса.
   Нельзя автоматически восстанавливать прежнюю версию из мусора.
7. Сборка EDT 2026.2 (Java 25, Eclipse 2025-12), чистая установка,
   smoke-test на отдельном разрешённом тестовом проекте.

**Статус на момент написания:** source-level правки закоммичены,
регрессионные тесты добавлены. Сборка/CI и реальный тест EDT не
проводились без явного разрешения.

## 5. Результаты повторного статического аудита — 2026-10-20

После объединения кода обнаружены и исправлены:
1. Выборочный Merge мог ложно записать глобальный `APPLIED`: теперь
   выборочная полная приёмка имеет только `REVIEWED_EXACT_SCOPE`.
2. Если HEAD хранилища становился недоказанным, прежний код всё ещё
   списывал точно совпавшие объекты по потенциально старому источнику.
   Теперь `UNPROVEN_SOURCE` ничего не подтверждает.
3. Пустой аудит 0/0 мог считаться полным успехом. В контракт введён
   `AUDIT_INCOMPLETE`, запись версии запрещена.
4. Пакетное `clearVerified` раньше могло удалить часть PENDING до
   обнаружения некорректной записи. Теперь все записи предварительно
   проверяются перед первым изменением.
5. Отдельная запись REVIEWED/APPLIED могла отказать после удаления PENDING
   из-за устаревшего HEAD или регресса контрольной версии. Теперь
   `ReceiveCompletionRecorder` заранее проверяет HEAD, монотонность
   отметок и полное совпадение подтверждаемых PENDING с активным журналом
   ДО первого изменения.

**Открытый риск, НЕ объявлять закрытым:** отдельные Eclipse Preferences
для PENDING и REVIEWS/APPLIED не образуют одну атомарную транзакцию.
Сбой между их `flush()` может оставить частично списанный журнал и
неподтверждённую версию. Консервативные проверки уменьшают риск, но не
дают полноценного crash recovery. Для релиза нужна отдельная
восстанавливаемая операция фиксации или атомарное хранение контрольного
состояния с испытаниями падения в каждой точке.

**Контроль полноты конвертации:** глобальное сравнение
сопоставляет все штатные имена `Metadata` из полного
`ConfigDumpInfo.xml`, **включая элементы без `configVersion`**
(плюс отдельно известные непроиндексированные изменения),
с верхнеуровневыми дескрипторами временного EDT-проекта.
Инкрементальный индекс при этом, как и ранее, содержит только записи
со штатным `configVersion`.
Неизвестные типы и пропущенные владельцы приводят к `SOURCE_INCOMPLETE`:
не подтверждается ни `REVIEWED`, ни `APPLIED`. Это улучшает безопасность,
но всё ещё не доказывает корректность каждой вложенной формы или бинарного
ресурса, преобразованного импортёром EDT. Полнота таких преобразований
должна проверяться отдельными интеграционными испытаниями.

Ни сборка, ни тесты в EDT 2026.2 по этим новым коммитам не запускались.

## 6. Повторная проверка решений с сохранением локальных изменений

Ранее `ReceivePendingStore.acknowledgeReviewed` удалял сознательно
оставленные локальные версии без сохранения решения. После получения
следующей версии хранилища приложение теряло факт неравенства по
этому объекту. Теперь обработанные, но отличающиеся от источника имена
сохраняются в отдельных `kept-*` записях того же защищённого узла
Eclipse Preferences; при точно проверенном применении объектной дельты
они удаляются, а при подтверждённом глобальном совпадении очищаются все.
Это **не** является подтверждением, что импорт EDT гарантированно
содержит все внешние бинарные ресурсы; проверка сохраняет отдельные
инварианты `REVIEWED` и `APPLIED`.

Ограничение: при первой глобальной сверке, когда ещё нет исходного
списка PENDING, локальные объекты, которых вовсе нет в хранилище,
нельзя представить классическим именем полученного изменения. Они
остаются локальным отличием и запрещают `APPLIED`; точный пообъектный
журнал KEPT_LOCAL пока охватывает лишь явно рассмотренные PENDING.

Новая запись в Preference добавлена статически, без запуска EDT или
тестов; перед релизом необходимо проверить сохранение между сессиями.

## 7. Завершённое полное объединение без ожидающих изменений (29437)

Реальный случай: пользователь полностью принял изменения EDT, штатный
`MERGE_PROCESS_FINISHED`, `PENDING = 0`; временный EDT-импорт из 1С
и рабочий EDT дали 6119/6121 побайтно совпавших владельцев.
Различия `Configuration.distr` и `ExchangePlans/МиграцияПриложений.mdo`
**не доказывают отказ пользователя от входящих изменений**.

Исправление: при НУЛЕ ожидающих пообъектных изменений и ПОЛНОМ
штатном сравнении EDT плагин НЕ читает все деревья ресурсов для
побайтового сравнения. После native Merge FINISHED он удостоверяется,
что все имена из полного `ConfigDumpInfo.xml` представлены во временном
EDT-импорте, HEAD хранилища подтвердился непосредственно перед
записью, а Git-ветка и её текущий HEAD стабильны. После этого записывает
только `REVIEWED`, при первом полном просмотре устанавливает
соответствующий маркер, **не** утверждает `APPLIED`, **не** создаёт
выдуманный `KEPT_LOCAL` и **не** показывает диалог «проект не совпадает»
из-за двух различающихся по байтам файлов.

При наличии конкретных `PENDING` продолжает действовать консервативная
проверка выбранных ресурсов. Её отдельная переработка требует
подтверждённого механизма получения выбранных в штатном EDT решений:
одного факта несовпадения байтов недостаточно для маркировки
`KEPT_LOCAL`. Не объявлять этот случай полностью устранённым.

Статус: изменение только в исходниках, без сборки/теста в EDT.

## 8. Штатная выборочная выгрузка с пустым отчётом изменений (2026-10-20)

Пользовательский случай: после успешного REVIEWED 29437 проверка локального
Git с незакоммиченными файлами корректно остановила первый запуск.
Следующий запуск дошёл до команды платформы
`/DumpConfigToFiles <inspection> -update -configDumpInfoForChanges
<prior ConfigDumpInfo.xml> -getChanges <changes.txt>`, но
`ChangedObjectsProbe.exportNative:182` требовал наличие
`inspection/ConfigDumpInfo.xml` и выбросил IOException.

Строка 182 — именно собственное условие обязательного наличия manifest,
а не лог с доказанной ошибкой Конфигуратора 1С. По этому логу известно:
команда завершилась с кодом 0, сформировала файл changes.txt, в нём не
было маркера FullDump; но содержание самого changes.txt было удалено
вместе с временным каталогом и неизвестно. Нельзя утверждать, что
у пользователя на самом деле ноль изменений.

Правило:
- `FullDump` — отдельное штатное требование глобального сравнения,
  не наличие/отсутствие индексного файла.
- **ПУСТОЙ** штатный `-getChanges` при отсутствии нового
  `ConfigDumpInfo.xml` — НЕ успешная XML-выгрузка. В этом исключении
  допускается только доказанный NO-OP: XML-каталог полностью пуст,
  прежний и текущий ПОЛНЫЕ индексы от отдельных вызовов
  `-configDumpInfoOnly` совпали байт-в-байт; отдельно доказаны
  исходный REVIEWED/SCANNED и неизменный нативный HEAD. Только тогда
  нет ресурсов для импорта EDT и версия может быть признана
  рассмотренной без Merge. При изменении индекса — ошибка, НЕ
  предположение «ничего не изменилось».
- **НЕПУСТОЙ** штатный `-getChanges` требует и manifest, и реальных
  XML-ресурсов. Нет их — `NativeStageIncomplete` с проверяемым
  числом изменённых имён и отметкой наличия manifest. Нельзя
  подставлять выдуманный `ConfigDumpInfo.xml` или считать
  исчезнувшие изменения принятыми. В этом случае исходные небольшие
  отчёты платформы 1С сохраняются в отдельной локальной папке
  (`1c-log.txt`, `changes.txt`, `stdout.txt`, `stderr.txt`),
  а XML-ресурсы и копия исходного полного индекса удаляются.
  Отчёты могут содержать имена объектов/пути/учётные данные,
  их нельзя автоматически отправлять третьим лицам.
- Странный случай «пустой native список, но не пустой XML stage»
  — ошибка, а не отсутствие изменений.
- База-посредник могла быть уже обновлена до ошибки чтения patch.
  На повторном запуске нельзя запускать native update повторно до
  подтверждения сохранённого состояния предыдущей операции.

Статус: код и unit-тесты добавлены статически без запуска сборки,
CI или реальных 1С/EDT. Для реально непустой дельты без manifest
необходима дополнительная диагностика платформы по локальному /Out.

**Восстановление предыдущей попытки с пустой дельтой:** если ранее
завершённый `UPDATE_COMPLETED` оставил журнальную запись после ошибки
`ChangedObjectsProbe`, новая попытка не должна повторно обновлять ИБ.
При совпадении полного снимка с предыдущим `SCANNED`, наличии
`REVIEWED=SCANNED`, отсутствии ожидающих изменений и пустом ответе
`-getChanges` допускается подтверждение `REVIEWED` после повторной
проверки HEAD. Если состав изменился или отчёт не пустой,
этот ускоренный путь запрещён. Код не был собран/проверен в EDT.

## 9. Выборочное получение: пересмотр транспорта и фиксации (2026-10-20)

**Фактические команды, без выдуманных XML и без обновления ИБ второй раз:**

1. Предпочтительно один вызов `/DumpConfigToFiles -update
   -configDumpInfoForChanges <old ConfigDumpInfo.xml>
   -getChanges <changes.txt>`. Его список NEW/MODIFIED —
   единственный источник новых изменённых имён. Результат `FullDump`
   требует отдельно подтверждённой глобальной сверки.
2. Если список непуст, но родной XML-патч 1С оказался непригоден,
   список не теряется. После повторного чтения полного ConfigDumpInfo
   и проверки неизменности ИБ используется **другой штатный способ**:
   `/DumpConfigToFiles <empty-dir> -listFile <object-names.txt>`.
   Имена формируются `SelectiveDumpPlanner.planIncludingRelated` из
   того же отчёта 1С, дополняясь отдельно разрабатываемыми ресурсами
   соответствующих владельцев из текущей полной описи ИБ. Нет
   *никакой* полной выгрузки и повторного `RepositoryUpdateCfg`.
3. Ранее незакрытые `PENDING` имена входят в этот же `-listFile`
   на текущем проверенном составе ИБ. Одна отложенная форма НЕ
   запускает полную сверку из-за наличия PENDING.
4. `Configuration` и `Language` корни, реальные удаления,
   неустановленные состояния после прежнего сбоя и `FullDump` остаются
   особыми случаями; они не превращаются в неподтверждённую частичную
   выдачу. Полная сверка только после отдельного подтверждения.
5. После `MERGE_PROCESS_FINISHED` **выборочный** путь НЕ использует
   `Files.mismatch` файлов EDT для определения принятых галочек.
   Сначала проверяет, были ли предъявлены все текущие PENDING.
   Затем просит пользователя подтвердить, что он завершил выбор
   каждого предъявленного изменения. Далее отдельно проверяет HEAD 1С,
   стабильность Git и сохраняет **REVIEWED**, но **не APPLIED**.
   Используемый EDT API подтверждает завершение Merge, но не предоставляет
   достоверную готовую пообъектную квитанцию выбранных галочек после
   закрытия редактора. Поэтому пользователь В ОТДЕЛЬНОМ СПИСКЕ явно
   отмечает объекты, оставленные полностью/частично локально;
   они записываются в `KEPT_LOCAL`, остальные считаются рассмотренными
   и принятыми. Отмена оставляет все `PENDING`, не повышая `REVIEWED`.
   Побайтовое сравнение EDT-сериализаций не участвует в этой классификации.
6. Если отчёт `-getChanges` пуст, но новый
   `ConfigDumpInfo.xml` не создан, это **не** успешная XML-выгрузка.
   При строго пустом XML-каталоге допускается только отдельное
   подтверждение NO-OP двумя совпадающими полными индексами 1С и
   стабильной проверенной версией HEAD (см. раздел 8). При малейшем
   расхождении индексов/истории версия не фиксируется. Малые
   диагностические файлы сохраняются локально.

**Статус:** изменены только исходники и тесты. Сборка/CI и испытания
импорта на EDT 2026.2 НЕ выполнялись. Особенно не испытаны
`-listFile` при каждой группе вложенных объектов, 1С-команда
на конкретной версии платформы пользователя и возобновление
прежней попытки в состоянии `UPDATE_COMPLETED`. Без этих
испытаний НЕ объявлять плагин проверенным рабочим релизом.

### Дополнительный аудит целостности выборочного импорта (2026-10-20)

- Если нативный `-getChanges` создал пригодный XML-патч, но
  `IImportService.work(project, xml, target, monitor)` или проверка
  представления EDT-владельцев отказала из-за неполного XML одного
  объекта, выполняется **не более одного** повторного штатного
  `-listFile` по тем же изменённым идентичностям, дополненным
  самостоятельными дочерними ресурсами из полного индекса 1С.
  До и после этой дополнительной выгрузки сверяется неизменность
  **полного** `ConfigDumpInfo.xml` базы-посредника; исходный
  `/ConfigurationRepositoryUpdateCfg` НЕ повторяется.
- Только если оба выборочных XML-источника не могут быть импортированы,
  отдельно предлагается полная выгрузка. Отказ сохраняет PENDING;
  никаких автоматических изменений Git.
- Полный нативный Merge с НЕПУСТЫМ PENDING, если нет доказанных
  удалений и ВСЕ владельцы полной выгрузки представлены во временной
  EDT-модели, получает тот же диалог явных локальных решений.
  Побайтовый аудит тысяч EDT-файлов в этом сценарии не производится.
  Неохваченные имена и неполный импорт НЕ подтверждают REVIEWED.
- Перед фиксацией `REVIEWED` после выборочного Merge снимок
  ИБ-посредника сверяется вновь с точным ранее зафиксированным
  полным индексом, независимо от проверки числового HEAD хранилища.
- Этапы классификации пользователя хранятся в Eclipse Preferences
  `REVIEWED`, `PENDING` и `KEPT_LOCAL`. Между разными узлами
  Preferences НЕТ атомарной транзакции: после сбоя возможна
  повторная обработка PENDING. НЕ объявлять это доказанно
  восстановленным без crash-тестов и реальной EDT.

**Предел доказательств:** только source-level аудит. CI/сборки/
интеграционного теста EDT 2026.2 не было с этими изменениями.

### Диагностика неудачного обновления ИБ и очистка staging (2026-10-20)

Если `/ConfigurationRepositoryUpdateCfg` вернул ошибку после запуска,
состояние ИБ остаётся НЕИЗВЕСТНЫМ. `RepositoryUpdateRunner.UpdateFailure`
сохраняет только ограниченные по размеру `designer.log`, `stdout.txt`,
`stderr.txt` в приватном локальном каталоге через
`ConfigVersionSnapshotRunner.saveFailureDiagnostics`.
Содержимое 1С-консоли не попадает в штатные логи EDT/Git. Кнопка
«Повторить update» не предлагается как безопасная, пока фаза/снимок
ИБ не установлены независимо.

При втором `-listFile` после ошибки EDT-импортёра новые XML/EDT
каталоги освобождаются после любых неожиданных исключений и отказа
от полной сверки. Необходимо отдельное испытание отмены между каждой
точкой переноса владения staging: source-level просмотр НЕ является
доказанным отсутствием утечек.

**Версия сборки после этих изменений отсутствует. Сборку/CI/1С не запускали.**
