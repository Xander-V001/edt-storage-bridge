# Штатное объединение EDT — единственный источник решения пользователя

Дата: 2026-10-19. Компонент: получение из классического хранилища в существующий проект EDT.

## Исправлено

При закрытии редактора сравнения EDT плагин больше НЕ вызывает
`VerifiedReceiveContent.verifyAndClear()`: функция сравнивала BSL/XML/бинарные
ресурсы байт-в-байт и сама снимала часть записей ожидания до подтверждения
разработчика. Это ошибочно считало результат native Merge незавершённым,
например при текстовых отличиях в 5 байт в длинном ManagerModule.bsl.

Вместо вторичного сравнения программа спрашивает, выполнил ли разработчик
объединение и завершил ли разбор ВСЕХ изменений, представленных в EDT.
«Нет»/отмена оставляет pending-список неизменным. «Да» означает принятие
результата штатного объединения, включая явно оставленные локальные отличия.
Побайтовый diff не входит в условие подтверждения.

После «Да» отдельная штатная проверка реального HEAD хранилища подтверждает,
что в ходе объединения не появился новый Commit. Только подтверждённая
ревизия позволяет снять ожидание по тем объектам, которые входили в открытое
сравнение. Непоказанные/отложенные объекты остаются pending; пока они есть,
нельзя отмечать ВСЮ ревизию как рассмотренную. Если реальный HEAD не
определён или изменился, подтверждение EDT показывается, но pending не
очищается, версия не придумывается. Не устанавливать полную байтовую
идентичность с хранилищем, когда пользователь сохранил собственный код.

## Ограничения

- Редактор EDT предоставляет штатное объединение, но обычное событие
  закрытия окна Eclipse само по себе не удостоверяет, что пользователь
  нажал «Объединить». Поэтому необходимо явное подтверждение.
- Аутентификация актуальной версии хранилища остаётся независимой
  проверкой, не проверкой BSL. Если текущая операция не имеет достоверной
  привязки снимка к номеру ревизии, отметка обработки откладывается.
- Ранее потерянное состояние или старые pending нельзя автоматически
  объявлять завершёнными без нового подтверждения пользователя.
- Код не собран и не проверен на фактической EDT 2026.2. Автоматическая
  сборка запрещена; ручная — только по отдельному разрешению.

## Контрольные тесты

`EdtMergeAcceptanceTest` проверяет: принятие всех показанных ресурсов
без сравнения текста BSL; отказ при закрытии/отмене; запрет списания без
подтверждённого HEAD; сохранение не показанных в EDT объектов в pending.


## 2026-10-19: восстановление детализации сравнения BSL по процедурам

В предыдущей правке был ошибочно отключён флаг
`parseBslModuleStructure(true)` на основании неподтверждённой гипотезы,
будто сравнение по процедурам мешает штатному объединению. Это было неверно.

Флаг **возвращён в значение true**. EDT вновь показывает изменения
по конкретным процедурам и функциям. При этом вызывается прежний штатный
редактор объединения EDT с `noMerge=false`, а возможность выбора удаления
объектов сохранена.

Причина повторного появления одного и того же изменения
`Document.НачислениеПоСреднему.ManagerModule` НЕ УСТАНОВЛЕНА.
Не считать отключение/включение разбора BSL исправлением повторного
получения. Для диагностики отдельно проверять исполнение/сохранение
штатного merge и повторную подачу хранилищем уже обработанных ревизий.
Сборка и проверка в EDT 2026.2 после этих изменений не выполнялись.

## 2026-10-19 — проверенная причина повторного предложения изменений

До исправления плагин мог передать в штатное EDT сравнение старые pending записи,
затем после окончания native Merge оставить их в ReceivePendingStore, если
штатный номер HEAD хранилища не удалось достоверно прочитать.
Следующее получение снова передавало тот же набор объектов, даже если
пользователь уже объединял их штатным редактором EDT.

Реальная ошибка находилась в связке подтверждения источника и снятия pending:
проверка номера версии использовалась одновременно как доказательство
выполнения EDT объединения. Это разные факты.

Исправлено:

1. В момент открытия штатного compare/merge редактора подписываемся на
   публичный IComparisonManager.ICompareMergeStatusListener. Храним
   MERGE_PROCESS_FINISHED даже после MERGE_PROCESS_DISCARDED; отмену
   фиксируем отдельно. Чтение getStatus только после закрытия было
   ненадёжно: сама EDT может уже удалить сведения о завершении.
2. Если HEAD точно не подтвердился, перед списанием ожидающих объектов
   выполняется read-only снимок ConfigDumpInfo из той же базы-посредника
   и сверка с исходным снимком, по которому был подготовлен merge.
3. Только при совпадении снимков и подтверждённом результате EDT снимаются
   записи pending из показанной области. Если отчёт версии недоступен,
   номер последней обработанной ревизии НЕ записывается, а отправка в
   хранилище остаётся запрещённой до подтверждения HEAD.
4. Если положительные native HEAD до/после получения различаются, такая
   смена запрещает переход на слабую проверку по ConfigDumpInfo.
5. Git фиксирует только число изменившихся путей после Merge, без файлов
   и содержимого. Это диагностика, не условие принятия результата EDT.

Ограничение: скриншоты показывают штатную настройку «Взять справа», но
не доказывают, был ли исполнен завершающий native Merge. При следующей
проверке это различает подписка на события EDT. Если после её события
MERGE_PROCESS_FINISHED никаких файлов рабочего Git не изменилось,
диагностика позволит исследовать именно применение изменений, а не
повторную выдачу pending.

Работа EDT 2026.2 и сборка Tycho после внесения изменений не проверялись;
workflow запускается только по отдельному разрешению пользователя.


## 2026-10-19 — исправление гонки при завершении асинхронного Merge

При нажатии штатной кнопки «Объединить» EDT запускает асинхронный merge
через `IComparisonManager.startMerge`: успешная постановка задания ещё
не означает, что запись в рабочий проект завершена. Обычное событие
Eclipse `IPartListener2.partClosed` также не подтверждает завершение native
merge. Ранее `ReceiveChangesCoordinator` **в `partClosed` сразу закрывал
`NativeEdtMergeWitness`**, а фоновая завершающая задача без ожидания
освобождала временный XML и преобразованную EDT-выгрузку. Эта гонка могла
удалить источник до окончания асинхронного объединения и потерять
`MERGE_PROCESS_FINISHED`.

Теперь на закрытии редактора состояние только записывается в журнал;
подписка остаётся действующей. В отдельном фоновом Job ждём терминальный
сигнал EDT `MERGE_PROCESS_FINISHED`, `MERGE_PROCESS_DISCARDED` или
`COMPARISON_MERGE_PROCESS_CANCELLED`. Только после подтверждённой
терминальной операции снимаем подписку и удаляем staging. Если EDT не
подтвердила окончание за ограниченное время, не считаем объединение
выполненным, сохраняем временные данные и запрещаем повторное получение
в текущей сессии (для исключения гонки с ещё выполняющимся native Merge).

Сохранено: главный источник = открытый EDT-проект; второй источник =
отдельная выгрузка из хранилища; `noMerge=false`; сравнение BSL по процедурам.
Никакой самостоятельной замены модулей и байтовой блокировки нет.

Данное исправление устраняет доказанную ошибку **нашего кода в управлении
асинхронной операцией**, но без запуска EDT 2026.2 нельзя гарантировать,
что именно эта гонка была причиной каждого ранее наблюдавшегося
неприменения изменений. Сборка и испытание не выполнялись.


## 2026-10-19: повторная выгрузка — ошибка чтения и сверки базы

При наличии pending старый путь выполнял read-only ConfigDumpInfo.xml из
базы-посредника и сравнивал со снимком предыдущего получения. Отличие
снимков вызывало IOException; обработчик скрывал конкретное сообщение
общим «Тип ошибки: IOException». Прежние объекты невозможно безопасно
выгружать из уже изменённой базы.

Теперь snapshot-проверка перенесена до решения об обновлении базы. Если
версии/состав изменились, плагин сообщает об этом и предлагает обычное
штатное получение; переход требует отдельного явного согласия на
обновление базы-посредника. При отказе 1С Designer не запускается, pending
не очищается. Если версии совпали, повторная выборочная выгрузка проходит
без лишнего обновления базы. Если не удалось получить сам ConfigDumpInfo,
операция прерывается с конкретным разрешённым сообщением или кодом и
путём сохранённого лога Конфигуратора, без автоматической записи в базу.

Это исправление пути ошибки; сборка и реальное получение в EDT 2026.2
после изменения не выполнялись.


## 2026-10-19 — понятные подтверждения получения

При обычном получении показывается короткое окно с названием хранилища и
базы-посредника (без полного технического пути), предстоящим обновлением,
последующим выбором изменений в EDT и предупреждением о возможной потере
непомещённых изменений базы. Кнопки: «Обновить и сравнить» и «Отмена».
При полной сверке дополнительно говорится о выгрузке всей конфигурации.

Если есть ожидающие изменения, показывается один диалог с тремя разными
действиями: «Повторно сравнить» (база не обновляется), «Обновить и сравнить»
(новое получение) и «Отмена». Отмена действительно отменяет операцию,
а не открывает вслед за собой подтверждение обновления базы.

Если снимок базы изменился, старые объекты больше не выгружаются. Пользователь
может отдельно подтвердить новое обновление или отменить всё без вызова
Designer. Предупреждение о передаче паролей в параметрах запуска 1С теперь
находится в настройках подключения, а не в обычном подтверждении.

Именование и тексты покрыты unit-тестами ReceiveConfirmationTextsTest;
сборка и запуск EDT 2026.2 после этого изменения не выполнялись.


## 2026-10-19 — причина «991 принято, 2 ожидают» и исправление

В обычном выборочном получении `SelectiveDumpPlanner` намеренно
исключал `Configuration.*`, `Language.*` и похожие корневые записи из
отдельной XML-выгрузки EDT (их нельзя безопасно импортировать как
независимые ресурсы). Остальные объекты успешно отдавались штатному EDT
merge, затем pending-записи этих корней оставались, но сообщение показывало
только общее количество и сваливало причину на неполное объединение.

Теперь при наличии таких изменений, ПОСЛЕ штатного получения в
существующую базу-посредник, но ДО создания сравнения EDT, предлагается
**переключить этот же цикл на ПОЛНУЮ сверку**. Для неё делается полная
временная XML-выгрузка и глобальное EDT-сравнение, но вторая команда
получения в базу НЕ выполняется. Пользователь может явно отказаться и
сравнить только остальные объекты; корневые останутся необработанными.
Выбор всегда показывается, а не выводится из наличия галочек EDT.

После закрытия EDT точные НЕобработанные имена приводятся в результате:
корневые/языковые отложенные записи отдельно от объектов, отсутствующих
в актуальном хранилище (удаления/переименования). Последние никогда не
помечаются принятыми лишь потому, что пользователь выполнил полное
сравнение: пока нет доказательства принятого удаления, они остаются
неподтверждёнными. Ревизия в целом подтверждается только при отсутствии
остающихся неподтверждённых изменений и при достоверном native HEAD.

Проверки в `ReceiveReviewScopeTest` и `ReceivePendingExplanationTest`
охватывают выборочную отсрочку, переключение на глобальное сравнение,
реальные имена и недопустимость списания удалённого объекта. Сборка
после правок не запускалась.


## 2026-10-19 — native Designer owns incremental change detection

The actual receive now treats Designer's `-getChanges` report as the ONLY
source of NEW and MODIFIED object names. The previous Java comparison of
`ConfigDumpInfo.xml` `id` and `configVersion` tokens was REMOVED. Those
values are opaque platform internals, not a public delta API. Two genuine
native ConfigDumpInfo name inventories are still compared ONLY for vanished
names, because native New/Modified reports do not provide a verified deletion
proof. Lost names require a FULL global EDT merge; accepted top-level
deletions are marked reviewed only after checking the actual EDT project.
Nested deletes without a verified outcome remain pending.

The native `-update -getChanges -configDumpInfoForChanges` command's target
folder must initially be EMPTY. Earlier code copied the baseline
ConfigDumpInfo.xml into that folder, contradicting the documented platform
contract. That copy is removed. A PRIVATE, byte-identical baseline copy is
kept alongside, never inside, the target. The original native file is never
modified; any unexpected change to the copy during Designer is an error.

The native `-listFile` command is still used as a SEPARATE SECOND transport
command to export entire affected metadata owners plus separately developed
children for the detached EDT importer. This does NOT compute changed names:
it only prepares a complete export from the names reported by 1C and from
previously unresolved pending entries. Native `FullDump` and unknown
non-versioned native names switch to global full review, never partial
acceptance. Snapshot and merge checkpoints still require their separate
existing safety proofs. No live-base or EDT execution has been done.

Official basis: https://kb.1ci.com/1C_Enterprise_Platform/What___s_New/Functional_Highlights/Incremental_export_of_configurations_to_XML_files/ and the 1C Administrator Guide section `/DumpConfigToFiles`.
