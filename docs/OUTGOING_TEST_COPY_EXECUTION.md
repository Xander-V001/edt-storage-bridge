# Универсальное исходящее помещение EDT → хранилище: состояние перед сборкой

Дата: 2026-10-18. Новый код не собран и не испытан в EDT 2026.2.

## Что реализовано в исходниках

- Сверка версии классического хранилища, отсутствие необработанных входящих изменений и неизменность чистого Git.
- Штатная полная контрольная выгрузка из существующей базы-посредника, импорт во временные файлы EDT, native EDT сравнение без объединения.
- Автоматическое группирование файловых отличий по владельцам ВСЕХ видов метаданных с отдельным учётом новых/удалённых объектов.
- Штатный экспорт существующих полных EDT объектов с подчинёнными/внешними ресурсами независимо от типа: формы, права, макеты, модули, реквизиты, регистры и т. д.
- Проверка фактического состава платформенного XML по выбранным владельцам. Неполная или расширенная область загрузки блокируется.
- Для подтверждённых существующих объектов: два явных подтверждения TEST, Lock -Objects includeChildObjects=true, LoadConfigFromFiles -partial -listFile, независимая XML/BSL выгрузка и побайтовая проверка, контроль ConfigDumpInfo вне выбранных владельцев, Commit -Objects и повторная проверка HEAD.
- Журнал операций хранит события и точные этапы UNKNOWN до каждого native вызова, SHA-256, размеры файлов, версию хранилища, продолжительность и причины ошибок; после неопределённого результата автоматические повторы запрещены.
- После подтверждённого Commit повторно проверяется HEAD, обновляются снимок ConfigDumpInfo, последняя просмотренная версия и привязка Git SHA к версии хранилища.

## Что остаётся НЕДОКАЗАННЫМ или ограниченным

- Сборка Tycho/OSGi против EDT 2026.2 ещё не запускалась, сигнатуры SDK и нативная загрузка не проверены.
- Создание/удаление объектов ВЕРХНЕГО уровня и изменение корня Configuration пока запрещены для записи. Штатная 1С требует при этом загрузку родительского Configuration.xml, а не только объекта. Без доказанных правил захвата родителя и проверки поддержки включать их в Commit нельзя.
- Файловое отличие — только кандидат. Просмотр native EDT comparison и двойное подтверждение обязательны.
- После обратной выгрузки несовпадение даже одного файла блокирует Commit. Байтовое различие может оказаться только нормализацией XML, но разрешать такую разницу автоматически нельзя.

## Как проводить первую ручную сборку

GitHub → Actions → Build and test (manual) → Run workflow → ветка feature/edt-2026.2-integration. Это ручной workflow; коммиты сами ничего не собирают.

После успешной сборки установить свежий p2 ZIP в EDT 2026.2. Все тесты проводить ТОЛЬКО на копии ИБ, привязанной к ТЕСТОВОЙ копии хранилища. Сначала проверить существующие объекты: реквизит справочника, форму документа, права роли, регистр, макет, два разных вида объектов, затем BSL. Сверить каждое изменение по штатному Конфигуратору.

Обязательно проверить отказ на новой/удалённой метадате, ошибке после Lock, изменении HEAD, частично отсутствующем XML и отмене. После неопределённого выполнения не удалять active.txt ради повторной попытки.

Найти диагностику: <Eclipse state>/org.xander.edt.storagebridge.ui/outgoing/<scope hash>/<UUID>/events.log; Error Log EDT; при неуспешном CI — артефакт tycho-test-reports.

# EDT Storage Bridge — экспериментальное помещение в тестовое хранилище

18.10.2026. Статус: КОД НЕ СОБРАН И НЕ ПРОВЕРЕН В EDT 2026.2.

## Сценарий в EDT

1. Разработчик завершает и сохраняет изменения EDT, делает обычный Git-коммит.
2. Плагин сверяет настоящий HEAD хранилища с подтвержденной полученной версией, проверяет непринятые входящие изменения.
3. Штатная XML-выгрузка из уже подключённой к хранилищу базы → временное представление EDT. Создаётся список всех отличий файлов; показывается штатный редактор сравнения с noMerge=true.
4. После закрытия редактора кнопка тестового помещения активна только если ВСЕ найденные отличия относятся к модификации существующих BSL: общие модули, менеджер/объект документа. Форма, реквизит, удаление, добавление файла или неизвестный тип БЛОКИРУЮТ весь Commit.
5. Оператор подтверждает, что подключена именно ТЕСТОВАЯ КОПИЯ хранилища: вводит ТЕСТ и отдельно подтверждает запись.
6. Штатный экспорт из Big Model EDT во временную папку; проверка конкретных BSL. Генерируются два раздельных файла:
   - objects.xml — XML-список ровно захватываемых объектов хранилища;
   - load-list.txt — пути ровно загружаемых BSL.
7. Команды Designer: ConfigurationRepositoryLock -Objects; LoadConfigFromFiles -Format Hierarchical -listFile -partial; независимая выборочная XML-выгрузка загруженных BSL и сверка каждого с экспортом EDT; проверка ConfigDumpInfo за пределами выбора; ConfigurationRepositoryCommit -Objects -comment.
8. После Commit ещё раз читается реальная версия хранилища. Подтверждение успеха — ровно следующая версия и неизменный Git. Текущая полученная EDT-версия НЕ повышается автоматически.

## Журналирование

Локальный путь Eclipse состояния плагина:

  <workspace state>/org.xander.edt.storagebridge.ui/outgoing/<SHA256 контекста>/<UUID>/

Содержимое:
- events.log: время в UTC, входной Git SHA, исходная ревизия, имена объектов/файлов, размеры и SHA-256 экспортированных BSL, начало каждой команды, код завершения, имена локальных redacted-логов, проверка round-trip, подтверждённый HEAD, тип ошибки.
- state.txt: PREPARED, LOCK_UNCERTAIN, LOCK_PROCESS_OK, LOAD_UNCERTAIN, LOAD_PROCESS_OK, COMMIT_UNCERTAIN, COMMIT_PROCESS_OK, COMPLETED или ABORTED.
- objects.xml, load-list.txt, export/ — выбранные файлы и исходный код локально; никому автоматически не передаются.
- lock/load/commit-stdout.tmp.redacted.txt и lock/load/commit-designer.log.redacted.txt — диагностический текст 1С с маскированием известных учётных данных.
- active.txt на уровень выше — блокировка нового помещения после неопределённой операции.

Перед каждым изменяющим вызовом запоминается UNCERTAIN и лишь затем запускается Designer. Никаких автоматических повторов или force-откатов. При сбое после LOCK тестовая база может остаться с захватами. Перед удалением active.txt нужно вручную выяснить реальную версию хранилища, изменения в базе и захваченные объекты. Не удаляйте его просто ради повторного запуска. Java stack trace доступен в Error Log EDT. Не загружайте полные логи на GitHub: в них могут присутствовать имена и исходный код.

## Недоказанное и заблокированное

- Нет успешной сборки под установленную EDT 2026.2, интеграционного испытания OSGi, API Big Model и формата XML.
- Формы, новые/удалённые объекты, реквизиты и структурные изменения НЕ выполняются. Для них нужен отдельный, доказанный модельный round-trip и проверка зависимостей.
- Путь независимого native DumpConfigToFiles для ObjectModule/ManagerModule/CommonModule должен подтвердиться на фактической платформе. Если команда не выгрузила ожидаемые BSL, Commit не выполняется; локальные захваты/изменения базы проверяются вручную.
- Сравнение BSL байт-в-байт может остановить операцию из-за перевода строк/кодировки: лучше безопасно остановиться, чем списать несовпадение на нормализацию.
- Если другие разработчики помещают в хранилище одновременно, до Commit обязательно повторно читается HEAD. Полная транзакционная защита распределённого хранилища пока не доказана.
- Только тестовая копия. Плагин не способен самостоятельно доказать, что адрес репозитория тестовый.

Рекомендуемая последовательность испытаний: (1) общий модуль, (2) ManagerModule, (3) ObjectModule, (4) два BSL одного документа, (5) изменение реквизита/формы — ожидается запрет, (6) устаревший HEAD — ожидается запрет, (7) прерванный Load/Commit — ожидается запрет повторения. Всегда сравнивайте модель 1С до/после штатным Конфигуратором.
