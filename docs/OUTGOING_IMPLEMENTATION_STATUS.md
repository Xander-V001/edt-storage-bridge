# EDT → классическое хранилище: практический выборочный режим

Рабочая ветка: `feature/edt-to-storage-push`.  
Основа: `EDT_TO_CLASSIC_STORAGE_PUSH_ARCHITECTURE.md`.

## Выбранный рабочий сценарий

1. Пользователь выбирает изменённые метаданные EDT, в том числе формы,
   модули, макеты и вложенные ресурсы. Git-коммит не обязателен.
2. Плагин получает свежее состояние **этих объектов** из классического
   хранилища, сравнивает с выбранной EDT-моделью и показывает разницу.
   Если объект одновременно меняли в хранилище, пользователь должен
   разрешить конфликт; изменения в других объектах не блокируют процесс.
3. Штатный `IExportService` выгружает выбранное EDT-содержимое во
   временный XML, включая нужные вложенные и внешние ресурсы.
4. После явного подтверждения плагин штатно захватывает ровно нужные
   объекты через Designer (`-Objects` обязателен), выборочно загружает
   XML в существующую базу-посредник, независимо проверяет затронутые
   метаданные и вызывает штатное помещение в хранилище с комментарием.
5. Итоговая ревизия и список действительно помещённых объектов
   проверяются через 1С. Неопределённый результат Commit не повторяется
   автоматически.

Не допускаются незапрошенное полное обновление посредника,
`-force`, silent Commit и применение изменений в чужие объекты.

## Упрощение от 2026-10-18

Предыдущий черновик ошибочно делал **обязательными для каждого
выборочного помещения** все следующие глобальные условия:

- Полностью подтверждённая версия хранилища для ВСЕЙ конфигурации;
- Нулевая входящая очередь для ВСЕХ объектов;
- Чистый рабочий Git и предварительный Git-коммит;
- Отдельный сохранённый baseline всей конфигурации;
- Предварительная тестовая информационная база для КАЖДОЙ отправки.

Это лишние препятствия: они отменены как требования для подготовки
выборочной операции. Вместо них используется свежее состояние и
проверка конфликтов **выбранных объектов**. Для сложных изменений
(новые типы, формы, удаления, конфликтующие зависимости) проверка в
изолированной базе остаётся полезным способом отладки/квалификации,
но не отдельной глобальной обязанностью для каждого простого модуля.

Отсутствие общего checkpoint или сбой TXT-отчёта о последней ревизии
не мешают **подготовить и просмотреть** изменение. Для РЕАЛЬНОГО
помещения перед записью всё равно потребуется достоверно подтвердить
актуальность и захваты выбранных объектов штатными средствами 1С.
Если это невозможно — не записывать вслепую.

## Уже сделано, но ещё не проверено в установленной EDT

- Отдельная команда `Проверить возможность помещения в хранилище
  (только чтение)`. Теперь она позволяет готовить выборочную операцию,
  показывая общие показатели как предупреждения, а не запреты.
- `OutgoingSafetyGate`: выдаёт предупреждения о глобальном состоянии
  вместо ложного "нельзя отправлять ничего". **Никогда не выдаёт
  разрешение на реальную запись в хранилище.**
- `OutgoingDeltaScanner`: автономный read-only сканер изменений между
  двумя явно заданными EDT-каталогами. Пока не подключён к рабочей
  команде и не должен использовать Git HEAD~1 как baseline.
- `OutgoingStorageObjectsXml`: формирование явно перечисленных объектов
  для `-Objects`, не смешивая этот формат с `-listFile`.
- Тесты `OutgoingSafetyGateTest`, `OutgoingDeltaScannerTest`,
  `OutgoingStorageObjectsXmlTest`.

Реальная выборка EDT, экспорт, проверка конкретных конфликтов,
захват, загрузка и Commit **ещё не реализованы**. На текущем этапе
пункт меню только читает информацию. Он не изменяет базу-посредник,
хранилище, Git или состояние проекта.

В репозитории эти изменения лежат в отдельной ветке и не затрагивают
`ReceiveChangesCoordinator`, `VerifiedReceiveContent`,
`SelectiveDumpRunner` и другие обработчики входящего получения.

## Следующий код, который действительно нужен

1. Подключить штатный `IExportService.work(EObject,
   IExportArtifactBuilder, boolean, boolean, IProgressMonitor)` с
   реальным builder EDT 2026.2; получить корректный список связанных
   ресурсов без собственного перечня типов.
2. Прочитать в стороне актуальное содержимое выбранных объектов из
   хранилища и показать EDT diff; не сравнивать всё дерево проекта.
3. Реализовать изолированный от входящего механизма Designer-процесс
   `Lock -Objects` → `LoadConfigFromFiles -listFile -partial` →
   верификация изменения только выбранных объектов →
   `Commit -Objects -comment`, с точными проверками до/после каждого
   шага, явным подтверждением и безопасным журналом неопределённого
   результата. Для изменений форм, макетов и удалений выполнять
   дополнительную проверку их round-trip семантики.

## Статус

Исходящая операция ещё не работает end-to-end. Новый исходящий код не
проверен сборкой Tycho/OSGi или реальным запуском EDT 2026.2.
Сборка GitHub Actions запускается вручную; без отдельного разрешения
её не запускать. VPS пользователя и его 1С не использовать.
