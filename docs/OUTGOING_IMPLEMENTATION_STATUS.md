# Исходящая отправка EDT → классическое хранилище 1С

**Рабочая ветка:** `feature/edt-to-storage-push`  
**Источник:** [архитектура обратного обмена](EDT_TO_CLASSIC_STORAGE_PUSH_ARCHITECTURE.md)  
**Начало реализации:** 2026-10-18

## Решение

Выбрана **выборочная отправка через штатный XML-транспорт**.

Рабочая конфигурация EDT → проверенная локальная выборка → публичный
экспорт модели `IExportService` во временные XML → загрузка только этих
объектов в изолированную тестовую информационную базу → проверка
round-trip → захват ровно указанных объектов в классическом хранилище
→ повторная сверка реального HEAD → частичная загрузка в существующую
базу-посредник → независимая проверка фактических изменений → штатный
`/ConfigurationRepositoryCommit -Objects ...` с комментарием → проверка
созданной ревизии.

**Запрещено:** полная замена базы-посредника, неявный `-force`,
отсутствующий `-Objects` (это означало бы все объекты хранилища),
переключение ветки Git, безусловная загрузка, фоновый Commit без явного
подтверждения и повторение Commit после неопределённого результата.

## Выполнено в этой ветке — этап 1

- `OutgoingSafetyGate`: независимый fail-closed контроль нативного HEAD,
  последней полностью применённой ревизии, очереди входящих изменений,
  чистоты рабочей Git-ветки, проверенного базового состояния содержимого
  и проверки на изолированной базе.
- `OutgoingReadinessCoordinator` + `OutgoingReadinessHandler`: отдельная
  команда меню **«Проверить возможность помещения в хранилище (только чтение)»**.
  Выполняет только Git-чтения, чтение локальных отметок и штатный
  `/ConfigurationRepositoryReport`. Показывает причины запрета.
  Не изменяет отметку `ReceiveRevisionStore`, не очищает ожидающие
  записи `ReceivePendingStore`; существующий getter последнего может
  лишь инициализировать локальный узел настроек Eclipse при первом чтении.
- `OutgoingDeltaScanner`: read-only поиск добавленных, удалённых и
  изменённых EDT-файлов относительно ПЕРЕДАННОГО проверенного исходного
  состояния, с отказом при непонятном расположении файла, символических
  ссылках, перекрывающихся каталогах. Результат пока только
  **кандидаты для просмотра**, не разрешение на Commit.
- `OutgoingStorageObjectsXml`: автономный сериализатор XML для
  `-Objects` с явным непустым списком и
  `includeChildObjects="false"`. Не допускает корневую конфигурацию,
  неизвестные имена, XML-инъекцию и список «все объекты».
  Не перепутать с `-listFile` для частичной XML-загрузки.
- Новые тестовые классы `OutgoingSafetyGateTest`,
  `OutgoingDeltaScannerTest`, `OutgoingStorageObjectsXmlTest`.
- Никаких изменений в Java-файлы входящего `ReceiveChangesCoordinator`,
  `VerifiedReceiveContent` и других обработчиков получения не вносилось.
  Не трогали реальный Git проекта пользователя или существующую
  информационную базу.

## Важные результаты проверки документации

1. Публичный EDT SDK описывает точную сигнатуру:
   `IExportService.work(EObject eObject, IExportArtifactBuilder builder,
   boolean exportSubordinateObject, boolean exportExternalProperties,
   IProgressMonitor monitor)`. Значит, на этапе 2 надо построить
   штатный artifact builder и получить реальный объект модели. Нельзя
   выдумывать упрощённый `work(project, directory)`.
   https://edt.1c.ru/dev/edt/2025.2/apidocs/com/_1c/g5/v8/dt/export/IExportService.html
2. Файл `-Objects` — **XML** с namespace
   `http://v8.1c.ru/8.3/config/objects`, а НЕ построчный список имён.
   https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.23_Administrator_Guide/Appendix_3._Description_and_location_of_internal_files/3.30._Object_list_file/3.30.1._General_description/
3. Для `/ConfigurationRepositoryLock` и
   `/ConfigurationRepositoryCommit` пропуск `-Objects` означает
   работу со ВСЕЙ конфигурацией. `-force` при Commit и UnLock запрещён.
   https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.27_Administrator_Guide/Appendix_7._Startup_command-line_options_of_1C_Enterprise/7.4._Running_Designer_in_batch_mode/7.4.15._Configuration_repository_operations/
4. У Designer `/LoadConfigFromFiles` параметры `-listFile`,
   `-Format Hierarchical` и `-partial` описаны для частичной загрузки.
   Реальное поведение необходимо проверить в тестовой ИБ той же версии
   1С, что и целевая база-посредник.

## Следующие этапы реализации

**Этап 2 — доверенный BASE.** Не считать Git HEAD~1 базовым состоянием
хранилища. Создать изолированное, отдельно проверенное содержимое
нативной ревизии без изменений проекта, определить Git delta за несколько
коммитов и построить список владельцев/вложенных ресурсов. Для
публикации новых объектов, переименований и удалений предусмотреть
явное согласование и отдельную проверку.

**Этап 3 — штатный экспорт EDT.** На целевой EDT 2026.2 подтвердить
`IExportArtifactBuilder` и экспорт EObject с дочерними объектами и
внешними свойствами, сохранить XML за пределами рабочего проекта.
Перепроверить формы, команды, рисунки, скриптовые модули и права.

**Этап 4 — независимая пробная загрузка.** Подготовить изолированную
копию ИБ, проверить `-listFile` и `-partial` с конкретным модулем
и формой, сверить изменённые объекты после загрузки.

**Этап 5 — безопасная подготовка реального Commit.** Snapshot/backup
базы-посредника, проверка её соответствия хранилищу, точный список
`-Objects`, штатный захват, проверка HEAD и захватов после операции,
частичная загрузка, контроль посторонних изменений.

**Этап 6 — подтверждённая запись.** Отдельное явное действие
пользователя, запись durable стадии перед `Commit`, запрет
автоповтора после неопределённого исхода, независимый отчёт о новой
ревизии и обновление собственной исходящей контрольной точки.

## Текущие ограничения и статус проверки

Новая команда **ТОЛЬКО ЧИТАЕТ**. Никакого механизма записи/захвата
в этой ветке пока не подключено. Проверенный BASE ещё не создаётся,
а проверка в изолированной ИБ ещё не реализована. Поэтому отправка
остаётся заблокированной **даже когда HEAD=applied и входящая очередь пуста**.

Изменения размещены в отдельной ветке. Сборка Tycho/OSGi и тестирование
в EDT 2026.2 **ещё не выполнены**: в основном проекте GitHub Actions
запускается вручную. Перед интеграцией рабочей входящей ветки обязательно
проверить компиляцию, новые тесты и входящие сценарии полной и выборочной
загрузки. Никакого автоматического запуска CI/Gradle/VPS.
